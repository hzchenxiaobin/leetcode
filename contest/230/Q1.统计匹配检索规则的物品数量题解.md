# LeetCode 统计匹配检索规则的物品数量 题解

## 1. 题目概述

- **标题 / 题号**：统计匹配检索规则的物品数量（#1773，easy）
- **链接**：https://leetcode.cn/problems/count-items-matching-a-rule/
- **来源**：LeetCode 第 230 场周赛 Q1
- **难度**：简单
- **标签**：数组、字符串、哈希表

**题意**：
给定物品数组 `items`，其中 `items[i] = [type_i, color_i, name_i]`，按固定顺序描述第 $i$ 件物品的**类型**、**颜色**、**名称**。再给定由字符串 `ruleKey` 与 `ruleValue` 组成的检索规则。第 $i$ 件物品**匹配**检索规则，当且仅当下列条件之一成立：

- `ruleKey == "type"` 且 `type_i == ruleValue`；
- `ruleKey == "color"` 且 `color_i == ruleValue`；
- `ruleKey == "name"` 且 `name_i == ruleValue`。

统计并返回**匹配检索规则的物品数量**。

**约束**：

- $1 \le \text{items.length} \le 10^4$
- $1 \le \text{type}_i.\text{length},\ \text{color}_i.\text{length},\ \text{name}_i.\text{length},\ \text{ruleValue}.\text{length} \le 10$
- `ruleKey` 只能取 `"type"`、`"color"`、`"name"` 三者之一
- 所有字符串均由小写英文字母组成

> 💡 **签到题最短路径**：`ruleKey` 整次调用恒定不变，每件物品又固定是 `[type, color, name]` 三元组——所以先把「列名」一次性翻译成「列下标」$idx \in \{0, 1, 2\}$，再对这一列做一遍相等过滤计数，两步之内出解。

## 2. 示例

**示例 1**

```text
输入：items = [["phone","blue","pixel"],["computer","silver","lenovo"],["phone","gold","iphone"]],
     ruleKey = "color", ruleValue = "silver"
输出：1
解释：只有 ["computer","silver","lenovo"] 的颜色是 "silver"。
```

**示例 2**

```text
输入：items = [["phone","blue","pixel"],["computer","silver","phone"],["phone","gold","iphone"]],
     ruleKey = "type", ruleValue = "phone"
输出：2
解释：["phone","blue","pixel"] 与 ["phone","gold","iphone"] 的类型是 "phone"。
注意 ["computer","silver","phone"]：它的名称 name 恰好也是 "phone"，但 ruleKey 是 "type"，
看的是第 0 列而非第 2 列，因此不匹配。
```

**示例 3**

```text
输入：items = [["phone","blue","pixel"],["computer","silver","lenovo"],["phone","gold","iphone"]],
     ruleKey = "name", ruleValue = "iphone"
输出：1
解释：只有第 2 件物品的名称是 "iphone"。
```

## 3. 解题思路

### 3.1 暴力思路：循环内三路分支

最直接的写法是在循环体内对每件物品做三路 `if-else`：先判断 `ruleKey` 是哪一个，再比对对应字段：

```text
count = 0
for item in items:
    if   ruleKey == "type"  and item[0] == ruleValue: count += 1
    elif ruleKey == "color" and item[1] == ruleValue: count += 1
    elif ruleKey == "name"  and item[2] == ruleValue: count += 1
return count
```

结果正确，时间 $O(n)$、空间 $O(1)$，作为签到题可以直接 AC。

> ⚠️ **症结**：`ruleKey` 在整次调用中是**常量**，却在循环里被反复比较——$n$ 件物品就要做 $n$ 次结论相同的字符串判断，且三路分支里的三个下标 `0/1/2` 容易抄错。更稳的组织方式是：**循环前一次性完成「列名 → 下标」的翻译**，循环体退化为无分支的单列比较。

### 3.2 核心观察：列名 → 列下标的一次性翻译

![核心观察：ruleKey 一次性翻译成列下标，整趟只比对一列](images/wc230_q1_rule_match_concept.svg)

两个关键事实：

1. `ruleKey` 只有三种取值，分别对应物品三元组的第 $0, 1, 2$ 列；
2. 题面三个匹配条件**互斥**（`ruleKey` 只能等于其中一个字符串），任一时刻**恰好激活一个**。

因此用一张哈希映射把列名翻成下标，循环前查一次：

$$
idx = \mathrm{mp}[\text{ruleKey}], \qquad \mathrm{mp} = \{\text{"type"} \to 0,\ \text{"color"} \to 1,\ \text{"name"} \to 2\}
$$

物品 $i$ 匹配规则便等价于一行判定：$\text{items}[i][idx] = \text{ruleValue}$。循环体只剩**一次下标访问 + 一次字符串比较**，无任何分支。

### 3.3 算法流程

![算法流程：建映射、定下标、单遍扫描计数](images/wc230_q1_rule_match_flow.svg)

1. **建映射**：`mp = {"type": 0, "color": 1, "name": 2}`。
2. **定下标**：循环前查一次 `idx = mp[ruleKey]`（循环不变量外提）。
3. **扫描计数**：`count = 0`；对每件物品，若 `item[idx] == ruleValue` 则 `count += 1`。
4. **返回** `count`。

### 3.4 示例演算

以示例 1 为例：`ruleKey = "color"` → `idx = 1`，`ruleValue = "silver"`，整趟只看颜色列：

![示例演算：锁定颜色列逐行比对，仅 silver 命中](images/wc230_q1_rule_match_walkthrough.svg)

| $i$ | type（列 0） | color（列 1） | name（列 2） | `item[1] == "silver"`? | count |
|-----|-------------|---------------|--------------|------------------------|-------|
| $0$ | phone | blue | pixel | × | $0$ |
| $1$ | computer | **silver** | lenovo | √ | $1$ |
| $2$ | phone | gold | iphone | × | $1$ |

- `idx = 1` 锁定**颜色列**，第 0、2 列整趟不被访问；
- 仅第 1 件 `"silver"` 命中，最终 `count = 1` ✓。

## 4. 算法细节

1. **映射的两种等价实现**：
   - 哈希表：`mp = {"type":0, "color":1, "name":2}`，$O(1)$ 查表，语义集中，扩展到更多列只需改表；
   - 条件表达式：`idx = (ruleKey == "type") ? 0 : (ruleKey == "color" ? 1 : 2)`，无哈希开销，但列数一多就退化成长链。
   本题两者皆可，首选哈希表——**数据驱动优于分支驱动**。
2. **C++ 用 `static const` 修饰映射表**：LeetCode 会用同一实例跑多个测试用例，`static` 保证映射只构造一次，摊薄常数。
3. **遍历取引用**：C++ 范围 `for` 用 `const auto& item`，避免逐个拷贝 `vector<string>`。
4. **计数的惯用法**：Python 用 `sum(item[idx] == ruleValue for item in items)` 直接对布尔值求和（`True == 1`）；C++ 用显式 `++cnt`。
5. **字符串比较语义**：`==` 先比长度再逐字符比较，长度不同立即为 `false`；本题全小写、无空白，无需任何归一化预处理。

## 5. 正确性证明

**引理 1（单列判定等价）**：设 $idx = \mathrm{mp}[\text{ruleKey}]$。第 $i$ 件物品匹配检索规则，当且仅当 $\text{items}[i][idx] = \text{ruleValue}$。

**证明**：由约束，`ruleKey` 恰取 `"type"`、`"color"`、`"name"` 三者之一，且三字符串两两不同，故题面的三个匹配条件**互斥且必有一个被激活**。若 `ruleKey = "type"`，则匹配 $\iff \text{type}_i = \text{ruleValue} \iff \text{items}[i][0] = \text{ruleValue}$，此时 $\mathrm{mp}[\text{ruleKey}] = 0$；`"color"`、`"name"` 两种情形同理分别对应下标 $1$、$2$。三种情形统一写作 $\text{items}[i][\mathrm{mp}[\text{ruleKey}]] = \text{ruleValue}$。∎

**引理 2（遍历完备且不重复）**：单层循环对 `items` 中每件物品的判定**恰好执行一次**。

**证明**：范围 `for` 按下标 $0, 1, \dots, n-1$ 依序迭代，无跳过、无重复。∎

**定理**：算法返回值等于匹配检索规则的物品数量。

**证明**：`count` 初值为 $0$，仅在「判定为真」时自增 $1$。由引理 2，每件物品被判定恰一次；由引理 1，每次判定与「该物品匹配规则」等价。故循环结束时

$$
\text{count} = \left|\{\, i : \text{items}[i][idx] = \text{ruleValue} \,\}\right|,
$$

即所求的匹配物品数。∎

## 6. 复杂度分析

- **时间复杂度**：$O(n)$，其中 $n = \text{items.length}$。循环前一次 $O(1)$ 哈希查表；循环 $n$ 轮，每轮一次下标访问加一次长度 $\le 10$ 的字符串比较（视为 $O(1)$）。
- **空间复杂度**：$O(1)$。仅常数个变量 `idx`、`count`；映射表大小固定为 $3$，与 $n$ 无关。

## 7. 参考代码

### C++

```cpp
class Solution {
public:
    int countMatches(vector<vector<string>>& items, string ruleKey, string ruleValue) {
        static const unordered_map<string, int> mp = {
            {"type", 0}, {"color", 1}, {"name", 2}
        };
        int idx = mp.at(ruleKey);
        int cnt = 0;
        for (const auto& item : items) {
            if (item[idx] == ruleValue) ++cnt;
        }
        return cnt;
    }
};
```

### Python

```python
class Solution:
    def countMatches(self, items: List[List[str]], ruleKey: str, ruleValue: str) -> int:
        idx = {"type": 0, "color": 1, "name": 2}[ruleKey]
        return sum(item[idx] == ruleValue for item in items)
```

> 💡 两版都是「先翻译、后扫描」两段式：映射查询严格放在循环外；Python 的 `sum` 直接累加布尔值，是「计数型过滤」的惯用法。

## 8. 边界情况与易错点

1. **`ruleKey` 合法性由约束保证**（三选一），无需防御；若写成工程级代码，可用 `mp.find(ruleKey) == mp.end()` 显式报错，而不是默默当作合法。
2. **`item[idx]` 不会越界**：$idx \in \{0, 1, 2\}$ 且每件物品恒为 3 元组。
3. **别把映射查询写进循环**：`idx = mp[ruleKey]` 放循环内虽结果正确，但每轮多一次哈希查表与字符串比较，退化为 3.1 的低效版本。
4. **看清 `ruleKey` 再比对**：示例 2 中 `["computer","silver","phone"]` 的 `name` 恰等于 `ruleValue`，但 `ruleKey = "type"` 看的是第 0 列——签到题最常见的 WA 来源就是比对错列。
5. **无溢出风险**：计数上界 $10^4$，`int` 绰绰有余；$n \ge 1$ 无空数组情形（即便为空，返回 $0$ 也自然正确）。
6. **字符串无需预处理**：全小写、无空白，直接 `==` 比较；长度不等时立即判 `false`。
