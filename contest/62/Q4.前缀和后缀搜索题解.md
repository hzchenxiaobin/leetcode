# LeetCode 前缀和后缀搜索 题解

## 1. 题目概述

- **标题 / 题号**：前缀和后缀搜索（#745，hard）
- **链接**：https://leetcode.cn/problems/prefix-and-suffix-search/
- **来源**：LeetCode 第 62 场周赛 Q4
- **难度**：困难
- **标签**：设计、字典树、数组、哈希表、字符串

**题意**：设计一个词典类 `WordFilter`。构造函数接收字符串数组 `words`（下标即编号）；查询 `f(pref, suff)` 返回「同时以 `pref` 为前缀、以 `suff` 为后缀」的单词下标，若有多个则返回**最大下标**，没有则返回 `-1`。

**约束**：

- $1 \le \lvert \text{words} \rvert \le 10^4$
- $1 \le \lvert \text{words}[i] \rvert \le 7$
- $1 \le \lvert \text{pref} \rvert, \lvert \text{suff} \rvert \le 7$
- 所有字符串仅含小写英文字母
- `f` 最多被调用 $10^4$ 次

> 💡 三个数字定了算法的形状：词长 $\le 7$、词数 $10^4$、查询 $10^4$。词长的平方 $L^2 \le 49$ 可以接受，而 $N \times Q = 10^8$ 不能接受——**把代价从「每次查询乘上词数」搬到「建表时乘上 $L^2$」**，就是本题的主线。

## 2. 示例

**示例 1**（官方示例）

```text
输入：
["WordFilter", "f"]
[[["apple"]], ["a", "e"]]
输出：[null, 0]
解释：下标 0 的 "apple" 以 "a" 为前缀、以 "e" 为后缀，故返回 0。
```

**示例 2**（补充示例：同一词出现多次，考察「取最大下标」）

```text
输入：
["WordFilter", "f", "f", "f", "f"]
[[["apple", "apply", "app", "apple"]], ["app", "le"], ["app", "y"], ["app", "p"], ["ap", "z"]]
输出：[null, 3, 1, 2, -1]
解释：f("app","le") 有下标 0 与 3 两个答案，取 3；
      f("app","y") 只有 apply → 1；f("app","p") 只有 app → 2；
      f("ap","z") 没有任何词以 "z" 结尾 → -1。
```

**示例 3**（补充示例：前缀、后缀跨越整词）

```text
输入：
["WordFilter", "f", "f", "f"]
[[["abcde", "bcdea", "cdeab"]], ["cde", "ab"], ["a", "e"], ["bcd", "dea"]]
输出：[null, 2, 0, 1]
解释：f("bcd","dea") 中 "bcdea"（下标 1）前缀 bcd、后缀 dea，恰好该词整体被覆盖。
```

## 3. 解题思路

### 3.1 暴力思路

每次查询遍历整个词典，用 `startswith(pref) && endswith(suff)` 判断，取最大下标。

- 单次查询 $O(N \cdot L)$，总时间 $O(Q \cdot N \cdot L) \approx 10^4 \times 10^4 \times 7 = 7 \times 10^8$ 次字符比较，稳定超时。
- 想用「前缀表 / 后缀表」分别哈希也不行：答案是**两个候选集合的最大交集**，两个 `set` 求交仍然要枚举集合大小，最坏还是 $O(N)$。

### 3.2 核心观察：后缀 + 分隔符 + 整词

![核心观察：用分隔符把后缀与整词拼成一个键](images/wc62_q4_key_design.svg)

前缀条件是「$w$ 以 `pref` 开头」，天生适合 Trie；后缀条件却是「从末尾数」，方向相反。**关键技巧是强行把后缀掰到前面**：对词 $w$ 的每个后缀 $s = w[j:]$，拼一个键

$$k(s, w) = s + \{ + w$$

把所有键插进 Trie。查询时拼出 $q = \text{suff} + \{ + \text{pref}$，于是：

> $q$ 是某个存储键的前缀 $\iff$ 存在一个词 $w$ 使 $w[j:] = \text{suff}$ 且 $w$ 以 `pref` 开头。

`'{'`（ASCII 123）紧跟 `'z'`，不在小写字母表内，所以它是**唯一**的分隔符：键里第一个 `'{'` 的位置恰好等于后缀长度。后缀必须**完全相等**而非「以 suff 开头」，正是这一点让只插后缀就够用。

### 3.3 算法流程

![算法流程：建表插入全部后缀键，查询沿 Trie 下降](images/wc62_q4_trie_flow.svg)

**建表**（一次，$O(N L^2)$）：

1. 顺次枚举词 $w$ 与下标 $i$（$i$ 递增，这一点后面很关键）。
2. 枚举 $w$ 的全部后缀 $s = w[j:]$，$j = 0..L$。
3. 把 $s + \{ + w$ 插入 Trie，沿途每个结点写 `weight = i`。

**查询**（每次 $O(L)$）：沿 `suff + '{' + pref` 从根下降，中途断链返回 `-1`，走完返回终点结点的 `weight`。

### 3.4 示例演算

![示例演算：四个词、三个查询](images/wc62_q4_walkthrough.svg)

对 `words = ["apple", "apply", "app", "apple"]` 与 `f("app", "le")`：

| 下标 | 词 | 前缀 `app` | 后缀 `le` | 结论 |
|------|----|-----------|-----------|------|
| 0 | apple | ✓ | ✓ | 候选 |
| 1 | apply | ✓ | ✗ | 排除 |
| 2 | app | ✓ | ✗ | 排除 |
| 3 | apple | ✓ | ✓ | 候选，返回 3 |

Trie 这边看到的现象是：键 `le{apple` 在 $i=0$ 与 $i=3$ 各插入一次，覆盖写后该结点 `weight = 3`，查询键 `le{ap` 恰好在此结点路径上，直接 `return 3`。

## 4. 算法细节

1. **字符到分支的映射**：小写字母 `'a'..'z'` 映射到 $0..25$，`'{'` 映射到 $26$，因此每个结点是 27 叉数组，而不是 26 叉——少一个就会越界访问。
2. **权重覆盖写而非取 max**：建表按 $i$ 递增顺序进行，路径上每一层都执行 `weight[u] = i`，写入天然单调，最后一次写入就是最大下标；既不需要 `max()`，也不需要额外记录——但**必须逐层写**，不能只在键的末端写（见 §8 第 5 条）。
3. **后缀要枚举 $L$ 个而不是「所有前缀」**：只插后缀（$j = 0..L-1$）就能覆盖所有合法查询，因为后缀条件要求完全相等。若改插前缀，键长会退化成 $O(L^2)$ 且语义错乱。
4. **空后缀键 `{w` 可以省**：查询要求 $\lvert \text{suff} \rvert \ge 1$，故空后缀键永远不可能被命中，插入它只是浪费 $O(NL)$ 个结点；保留它则可让 `suff == ""` 也正确（与官方提示一致）。
5. **两种落地等价**：Trie 版把键共享的前缀压成树结点；等价的「全量配对哈希表」在建表时就把每个词的 $L^2$ 个 $(\text{pref}, \text{suff})$ 组合展开成键 `pref + '{' + suff`，查询退化成一次哈希查找。后者代码更短，但空间常数更大。
6. **语言选择影响内存**：C++ 的 27 叉数组每结点 112 字节，最坏 $6.9\times10^5$ 个结点约 80 MB；Python 若用「每结点一个 dict」的实现，同样规模会飙到近 200 MB，容易被卡内存，改用全量配对 `dict` 后约 83 MB。
7. **查询键长度上界**：$\lvert \text{suff} \rvert + 1 + \lvert \text{pref} \rvert \le 15$，任何超过该长度的查询键都不可能存在，走两步自然断链，无需特判。

## 5. 正确性证明

**引理 1（分隔符唯一）**：对任意词 $w$ 与后缀 $s = w[j:]$，键 $k = s + \{ + w$ 中 `'{'` 恰好出现一次，且位于下标 $\lvert s \rvert$ 处（从 0 计数）。

**证明**：$w$ 由小写字母组成（题面约束），而 `'{'` 不属于小写字母表，故 $k$ 中唯一可能出现的 `'{'` 就是拼接处插入的那一个，位置为 $\lvert s \rvert$。∎

**引理 2（查询键命中 $\iff$ 双条件成立）**：设 $q = \text{suff} + \{ + \text{pref}$。$q$ 是某存储键 $k = s + \{ + w$ 的前缀，当且仅当 $s = \text{suff}$ 且 $w$ 以 `pref` 开头。

**证明**：

- ($\Leftarrow$) 若 $s = \text{suff}$ 且 $w$ 以 `pref` 开头，则 $k = \text{suff} + \{ + \text{pref} + \cdots$，前 $\lvert q \rvert$ 个字符与 $q$ 逐一相同，即 $q$ 是 $k$ 的前缀。
- ($\Rightarrow$) 设 $q$ 是 $k$ 的前缀，比较两者的 `'{'` 位置。由引理 1，$k$ 的 `'{'` 在位置 $\lvert s \rvert$；$q$ 的 `'{'` 在位置 $\lvert \text{suff} \rvert$。若 $\lvert s \rvert > \lvert \text{suff} \rvert$，则 $q$ 在位置 $\lvert \text{suff} \rvert$ 处是 `'{'`，而 $k$ 在该位置仍是后缀中的字母，矛盾；若 $\lvert s \rvert < \lvert \text{suff} \rvert$，则 $k$ 在位置 $\lvert \text{suff} \rvert$ 已进入词体（纯字母），而 $q$ 在该位置是 `'{'`，同样矛盾。故 $\lvert s \rvert = \lvert \text{suff} \rvert$，即 $s = \text{suff}$；此时 $q$ 在 `'{'` 之后的部分就是 `pref`，而 $k$ 在 `'{'` 之后的部分是 $w$，前缀相等即 $w$ 以 `pref` 开头。∎

**引理 3（结点权重即最大下标）**：建表结束后，任一结点 $u$ 的 `weight` 等于「所有键经过 $u$ 的词」中的最大下标。

**证明**：对插入次数归纳。插入第 $i$ 个词时，沿其每个键的路径把 `weight` 覆写为 $i$；由于下标 $i$ 严格递增，每次覆写后「经过该结点的词的已插入最大下标」就等于 $i$。归纳结束时即为全体词中的最大下标。∎

**定理**：`f(pref, suff)` 的返回值就是题面要求的答案。

**证明**：沿 $q$ 下降成功时，终点的整条祖先链经过的键都以 $q$ 为前缀；由引理 2，这些键对应的词恰好是「后缀为 `suff` 且前缀为 `pref`」的全部词；由引理 3，终点 `weight` 是这些词的最大下标。下降断链时不存在任何以 $q$ 为前缀的键，由引理 2 知无词满足双条件，返回 `-1` 正确。∎

## 6. 复杂度分析

- **时间**：建表 $O(\sum_i L_i^2)$——每个词插入 $L$ 个键、每个键长度 $\le 2L+1$，$L \le 7$ 时每词至多 84 个字符，总计 $\le 8.4\times10^5$ 步。查询 $O(\lvert \text{suff} \rvert + \lvert \text{pref} \rvert + 1) = O(L) \le 15$ 步，与 $N$ 无关。总时间 $O(NL^2 + QL)$，实测最坏数据建表 + $10^4$ 次查询约 0.05 秒。
- **空间**：Trie 结点数上界 $O(NL^2)$，每个结点 27 个 `int` 分支 + 1 个权重，最坏约 $6.9\times10^5$ 结点、80 MB（$N = 10^4$、$L = 7$ 的随机数据实测）。等价哈希表实现同样 $O(NL^2)$ 个键，但每个键是长度 $\le 15$ 的短字符串。

## 7. 参考代码

### C++

```cpp
#include <string>
#include <vector>
#include <array>
using namespace std;

class WordFilter {
public:
    explicit WordFilter(vector<string>& words) {
        nxt.reserve(1 << 20);
        newNode();
        for (int i = 0, n = (int)words.size(); i < n; i++) {
            const string& w = words[i];
            int L = (int)w.size();
            for (int j = 0; j <= L; j++) {        // j == L 是空后缀，可省
                int u = 0;
                for (int k = j; k < L; k++) u = step(u, w[k] - 'a');  // 后缀部分
                u = step(u, 26);                                     // 分隔符 '{'
                for (int k = 0; k < L; k++) {
                    u = step(u, w[k] - 'a');      // 整词
                    weight[u] = i;                // 每层都写：查询键可能停在词中间
                }
            }
        }
    }

    int f(string pref, string suff) {
        int u = 0;
        for (char c : suff) { u = nxt[u][c - 'a']; if (u < 0) return -1; }
        u = nxt[u][26]; if (u < 0) return -1;
        for (char c : pref) { u = nxt[u][c - 'a']; if (u < 0) return -1; }
        return weight[u];
    }

private:
    vector<array<int, 27>> nxt;   // 27 = 26 个小写字母 + '{'
    vector<int> weight;

    void newNode() {
        nxt.push_back({});
        nxt.back().fill(-1);
        weight.push_back(-1);
    }

    int step(int u, int c) {      // 不存在就新建结点，并把它接上
        if (nxt[u][c] < 0) {
            nxt[u][c] = (int)nxt.size();
            newNode();
        }
        return nxt[u][c];
    }
};
```

> ⚠️ 注意 `step` 里先算编号再 `newNode()` 的顺序不能反：`nxt[u][c] = nxt.size()` 必须在 `push_back` 之前，否则新结点的下标会错位。更隐蔽的一点是 **`weight` 必须写在整词路径的每一层**——查询键 `pref` 只是词的一个前缀，终点往往落在词中间的结点上；若只写末端，`f("a", "e")` 就会沿 `e{a` 走到一个 `weight = -1` 的内部结点而错返 `-1`。这是本题最容易写错的地方。

### Python

```python
class WordFilter:
    def __init__(self, words: list[str]):
        # 等价实现：建表时把每个词的 L^2 个 (前缀, 后缀) 组合全部展开
        self.best = {}                     # 键 pref + '{' + suff -> 最大下标
        for i, w in enumerate(words):
            L = len(w)
            for p in range(1, L + 1):
                pref = w[:p]
                for s in range(1, L + 1):
                    self.best[pref + '{' + w[L - s:]] = i   # 覆盖写即最大值

    def f(self, pref: str, suff: str) -> int:
        return self.best.get(pref + '{' + suff, -1)
```

> 💡 Python 想写严格同构的 Trie 也可以：`child = [{}]`、`weight = [-1]`，插入 `w[j:] + '{' + w`，查询走 `suff + '{' + pref`。但 $N=10^4$、$L=7$ 时结点数可达 $6.9\times10^5$，每个结点一个 `dict` 的内存开销约 200 MB，非常接近评测上限；上面的全量配对写法只有约 83 MB，且代码更短。两者时间复杂度同为 $O(NL^2 + QL)$。

## 8. 边界情况与易错点

1. **重复词必须返回较大下标**：`["apple", ..., "apple"]` 时两个下标都满足条件，答案是后者。靠「按 $i$ 递增覆盖写 `weight`」天然保证；若改成只在 `weight[u] == -1` 时写入，就会返回 0 而非 3。
2. **`suff` 比词长**：键 `suff + '{' + pref` 根本不存在，走两步就断链，返回 `-1`。切勿先 `substr` 截断后缀，那样会把长后缀错认成短后缀。
3. **分隔符必须出字母表**：用 `'{'`（`'z' + 1`）或任意非小写字母字符；若误用 `'a'` 这类字母表内字符，引理 1 失效，`pref` 与 `suff` 会出现错位匹配。
4. **27 叉数组别写成 26**：C++ 里 `array<int, 27>`，`'{'` 的编号 26 必须落在界内，否则是静默越界写。
5. **权重必须写满整词路径的每一层**：查询键以 `pref` 结尾，终点可能停在词中间的结点（`f("a", "e")` 走的是 `e{a`，终点是 `e{apple` 路径上的第 3 层），只写末端会读到 `-1`；后缀部分则不必写，因为查询键一定经过 `'{'`。
6. **空后缀键的取舍**：合法输入下 `|suff| >= 1`，`j = L` 的键不会被命中，插入它只是多花 $O(NL)$ 空间；删掉可省内存，保留则支持 `suff == ""`。
7. **内存预估别按「字符串总长」算**：Trie 的结点数是所有键长度之和的上界，别用 $N \times L$ 估，否则容易低估 $L$ 倍而 MLE。

**延伸思考**：

1. 若把词长上限放大到 $10^5$，$O(NL^2)$ 的键空间立刻爆掉。此时可改用「前缀索引 + 后缀索引 + 二分下标」：对每个前缀存出现下标的有序列表，对后缀同样处理，查询取两个有序列表的最大公共元素（双指针或对较小集合逐个二分），复杂度变成 $O(\log N)$ 级别的「交集最大」问题。
2. 若要求返回**最短**的匹配词而非最大下标，`weight` 就要换成「长度」并配一个次级关键字，Trie 依然直接可用，只需改聚合量的定义。
3. 若查询条件是「前缀 `pref` **或** 后缀 `suff`」，问题变成两个答案集的并；Trie 无法一次回答，需要分别查询再合并，这也是本题技巧不适用的典型场景。
