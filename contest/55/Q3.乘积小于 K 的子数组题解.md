# LeetCode 乘积小于 K 的子数组 题解

## 1. 题目概述

- **标题 / 题号**：乘积小于 K 的子数组（#713，medium）
- **链接**：https://leetcode.cn/problems/subarray-product-less-than-k/
- **来源**：LeetCode 第 55 场周赛 Q3
- **难度**：中等
- **标签**：数组、二分查找、前缀和、滑动窗口

**题意**：给定一个正整数数组 `nums` 和一个整数 $k$，统计满足

$$\prod_{i=l}^{r} nums[i] < k$$

的**连续子数组** $[l, r]$ 的个数（子数组非空，即 $0 \le l \le r < n$）。

**约束**：

- $1 \le n \le 3 \times 10^4$：$O(n^2)$ 的 $4.5 \times 10^8$ 次乘法处在危险边缘，$O(n^3)$ 直接出局
- $1 \le nums[i] \le 1000$：元素**全为正整数**，向右扩展乘积只增不减，这是滑窗可行的根
- $0 \le k \le 10^6$：$k$ 很小时几乎全是「无解」，$k = 0$ 或 $k = 1$ 必须整体返回 $0$

> 💡 **关键前提**：`nums[i] >= 1` 保证了乘法的单调性。若允许 0 或负数，向右扩展时乘积可能变小，「右端点增大则窗口变长」的直觉立刻失效，本题的双指针也就不再成立。

## 2. 示例

**示例 1**

```text
输入：nums = [10,5,2,6], k = 100
输出：8
解释：8 个乘积小于 100 的连续子数组分别是
     [10]、[5]、[2]、[6]、[10,5]、[5,2]、[2,6]、[5,2,6]
     注意 [10,5,2] 的乘积为 100，不满足「严格小于」，不计入。
```

**示例 2**

```text
输入：nums = [1,2,3], k = 0
输出：0
解释：nums 中元素都 >= 1，任何非空子数组的乘积 >= 1 > 0，
     不存在严格小于 0 的子数组。
```

## 3. 解题思路

### 3.1 暴力思路

枚举左端点 $l$，向右累乘，乘积一旦 $\ge k$ 就停（正整数保证后续只会更大）：

$$\text{ans} = \sum_{l=0}^{n-1} \#\{r \ge l : nums[l] \times \cdots \times nums[r] < k\}$$

单次扩展 $O(1)$，总量 $O(n^2)$。当 $n = 3 \times 10^4$ 且 $k$ 很大（例如全部为 $1$、$k = 10^6$）时，内层要一路走到末尾，总操作数 $\frac{n(n+1)}{2} \approx 4.5\times10^8$，C++ 已接近时限，Python 必超时。

暴力的浪费在于：$n$ 个左端点各自往右扫一趟，共扫了 $n$ 趟，可每一趟的结论几乎都能从上一趟推出来——以 $r$ 结尾的合法起点是一条后缀（见 3.2），$r$ 增大时这条后缀的左边界只会**单向右移**、从不回退。既然边界单调，就不必每次都从 $0$ 重新找：把 $n$ 趟扫描合并成一根同向滑动的指针即可。

### 3.2 核心观察：固定右端点，合法起点是一段后缀

![以 right 结尾的合法子数组构成后缀区间](images/wc55_q3_window_count.svg)

固定右端点 $r$，考察起点 $l$ 从右往左移动时乘积的变化。因为所有因子 $\ge 1$：

$$nums[l] \ge 1 \implies \prod_{i=l}^{r} nums[i] \;=\; nums[l] \cdot \prod_{i=l+1}^{r} nums[i] \;\ge\; \prod_{i=l+1}^{r} nums[i]$$

即**起点越靠左，乘积越大（不减）**。于是满足「乘积 $< k$」的起点集合必然形如一段后缀 $[left, r]$：一旦某个 $l$ 让乘积 $\ge k$，它左边所有起点只会更差。

由此得到本题最重要的一句话：

> 对每个 $r$，合法子数组的个数恰好是窗口长度 $r - left + 1$，其中 $left$ 是**最小**的合法起点。

更进一步，$left$ 随 $r$ 增大**单调不减**：把 $r$ 换成 $r+1$ 只是给窗口多乘一个 $\ge 1$ 的数，原来合法的起点可能变非法，但绝不可能让一个原本非法的起点变合法。所以 $left$ 只用一个指针向右滑，永不回退——总移动次数 $O(n)$。

### 3.3 算法流程

![滑窗流程：扩张、收缩、结算](images/wc55_q3_algorithm_flow.svg)

1. **特判**：$k \le 1$ 时直接返回 $0$（任何非空乘积 $\ge 1 \ge k$）。
2. **初始化**：`left = 0`，窗口乘积 `prod = 1`（空窗口的乘积），`ans = 0`。
3. **扩张**：对 $right = 0, 1, \dots, n-1$，执行 `prod *= nums[right]`。
4. **收缩**：当 `prod >= k` 时反复执行 `prod /= nums[left]`、`left++`，直到 `prod < k`。
5. **结算**：`ans += right - left + 1`，把「以 $right$ 结尾」的全部合法子数组一次性计入。
6. **返回**：循环结束后 `ans` 即为答案。

窗口始终维持**最小合法窗口**：`prod = nums[left..right] < k`，且 $left$ 不能再左移一格（否则 $\ge k$）。这正是「滑动窗口」在两个单调性（扩张使乘积不减、收缩使乘积不增）夹逼下的标准形态。

### 3.4 示例演算

对 `nums = [10,5,2,6]`、`k = 100` 逐轮走查：

![示例演算表：扩张、收缩、结算](images/wc55_q3_walkthrough.svg)

| right | nums[right] | 扩张后 prod | 收缩动作 | left | 新增 | ans |
|-------|-------------|-------------|----------|------|------|-----|
| 0 | 10 | 10 | 无（10 < 100） | 0 | 1 | 1 |
| 1 | 5 | 10 × 5 = 50 | 无（50 < 100） | 0 | 2 | 3 |
| 2 | 2 | 50 × 2 = 100 | 100 ≥ 100，除以 10 | 1 | 2 | 5 |
| 3 | 6 | 10 × 6 = 60 | 无（60 < 100） | 1 | 3 | 8 |

四轮的新增数 $1 + 2 + 2 + 3 = 8$，与官方答案一致。逐轮展开就是官方列出的 8 个子数组：

- $right = 0$：`[10]`
- $right = 1$：`[5]`、`[10,5]`
- $right = 2$：`[2]`、`[5,2]`（`[10,5,2]` 乘积恰为 100，被收缩排除）
- $right = 3$：`[6]`、`[2,6]`、`[5,2,6]`

> ⚠️ 第 3 行是最容易写错的一处：乘积**恰好等于** $k$ 也必须收缩，因为题目要求**严格小于**。

## 4. 算法细节

1. **计数公式**：`ans += right - left + 1` 而不是 `+= 1`。右端固定为 $right$ 时，起点 $left, left+1, \dots, right$ 全部合法，一次性加完，避免内层再枚举。
2. **收缩用除法而非重算**：`prod /= nums[left]` 依赖「元素都是正整数、整除无余数」，$O(1)$ 还原出去掉最左元素后的乘积；若用重算，复杂度立刻退化回 $O(n^2)$。
3. **`k <= 1` 必须提前返回**：否则当 $k = 0$ 时 `while (prod >= 0)` 恒成立，`left` 会一路自增直到越过数组右端（访问 `nums[n]`），既越界又死循环；先特判再进窗口，是最省心的写法。
4. **不需要 `left <= right` 守卫**：$k \ge 2$ 时，即使 $nums[right] \ge k$，收缩到空窗口后 `prod = 1 < k` 自然停止，此时 `right - left + 1 = 0`，正好表示「以 $right$ 结尾没有合法子数组」。
5. **乘积用 64 位整数**：收敛后的乘积始终 $< k \cdot 1000 \le 10^9$，`int` 勉强够；但 `ans` 上界是 $\frac{n(n+1)}{2} = 4.5\times 10^8$，用 `long long`（Python 天然大整数）可一次性规避「中间量顺手写成 `int` 后溢出」的隐患。
6. **单指针不回退**：`left` 在整趟循环中只增不减，总自增次数不超过 $n$，因此 `while` 的总执行次数是 $O(n)$，不是 $O(n^2)$——这是复杂度分析的关键，别被嵌套的 `while` 骗了。
7. **空窗口的乘积定义为 1**：`prod` 初值取 $1$，收缩到空时也恰好是 $1$，与「乘法的单位元」一致，无需为 `left > right` 单独开分支。

## 5. 正确性证明

**引理 1（起点集合是后缀）**：固定 $r$，若子数组 $[l, r]$ 的乘积 $< k$，则对任意 $l' \in [l, r]$，$[l', r]$ 的乘积也 $< k$。

**证明**：由于每个 $nums[i] \ge 1$，把区间左侧的因子逐个去掉只会让乘积不增：

$$\prod_{i=l'}^{r} nums[i] \;=\; \prod_{i=l}^{r} nums[i] \Big/ \prod_{i=l}^{l'-1} nums[i] \;\le\; \prod_{i=l}^{r} nums[i] \;<\; k$$

（分母是 $\ge 1$ 的正整数，故除法结果不大于原值。）∎

**引理 2（`left` 是最小合法起点）**：每次 `while` 循环结束后，`prod = nums[left..right]` 的乘积 $< k$，且当 $left > 0$ 时 $nums[left-1..right]$ 的乘积 $\ge k$。

**证明**：循环退出条件是 `prod < k`，此时窗口乘积即 $nums[left..right]$ 的乘积，第一条成立。若 $left > 0$，说明它由上一轮 `prod /= nums[left-1]; left++` 得到，而除法前的乘积 `prod × nums[left-1] = nums[left-1..right]` 的乘积满足条件 `>= k`（否则循环不会进入）。故 $left - 1$ 不是合法起点。∎

**引理 3（`left` 单调不减）**：处理 $right$ 时的最终 $left$，不小于处理 $right-1$ 时的最终 $left$。

**证明**：$right-1$ 轮结束时记为 $L$，此时 $nums[L..right-1] < k$。进入 $right$ 轮，乘积变为 $nums[L..right] = nums[L..right-1] \times nums[right] \ge nums[L..right-1]$，若仍 $< k$ 则 $left$ 保持 $L$；否则收缩使其右移。整个过程 $left$ 只增不减。∎

**引理 4（不重不漏）**：任意合法子数组 $[l, r]$ 在 $right = r$ 这一轮被计入，且只在这一轮被计入。

**证明**：子数组由右端点唯一确定轮次，故只需证 $right = r$ 时 $l \ge left$。由引理 1、引理 2，$[l, r]$ 合法 $\Rightarrow$ 最小合法起点 $left \le l$，于是 $l \in [left, r]$，被 `ans += r - left + 1` 计入。反之 $l < left$ 时由引理 2 的极小性，乘积 $\ge k$，不会被计入。∎

**定理**：算法返回的 `ans` 恰为乘积严格小于 $k$ 的连续子数组个数。

**证明**：由引理 1 与引理 2，每轮计入的恰好是该右端点下全部合法起点，个数为 $r - left + 1$；由引理 3 算法不会漏掉任何起点；由引理 4 每个子数组被唯一一次统计。故 `ans` 等于合法子数组总数。$k \le 1$ 时提前返回 $0$，与「任何乘积 $\ge 1 \ge k$」一致。∎

## 6. 复杂度分析

- **时间**：$O(n)$。外层 `for` 走 $n$ 轮；内层 `while` 中 `left` 单调递增且上界为 $n$，整趟循环的总收缩次数 $\le n$。两者相加为 $2n$ 次基本操作，故为线性。
- **空间**：$O(1)$。只用 `left / right / prod / ans` 四个标量，不复制数组、不开辅助表。

> 💡 对比：暴力 $O(n^2)$、前缀积 + 二分 $O(n \log n)$、滑窗 $O(n)$。本题的最优解正是利用了「正整数 + 乘积单调」这一结构。

## 7. 参考代码

### C++

```cpp
#include <vector>
using namespace std;

class Solution {
public:
    int numSubarrayProductLessThanK(vector<int>& nums, int k) {
        if (k <= 1) return 0;              // 乘积 >= 1，不可能严格小于 k
        long long ans = 0;
        long long prod = 1;                // 空窗口乘积为 1
        int left = 0;
        for (int right = 0; right < (int)nums.size(); ++right) {
            prod *= nums[right];           // 1. 扩张
            while (prod >= k) {            // 2. 收缩到 prod < k
                prod /= nums[left];
                ++left;
            }
            ans += right - left + 1;       // 3. 结算以 right 结尾的窗口
        }
        return (int)ans;
    }
};
```

### Python

```python
class Solution:
    def numSubarrayProductLessThanK(self, nums: list[int], k: int) -> int:
        if k <= 1:
            return 0                      # 乘积 >= 1，不可能严格小于 k
        ans = 0
        prod = 1                          # 空窗口乘积为 1
        left = 0
        for right, x in enumerate(nums):
            prod *= x                     # 1. 扩张
            while prod >= k:              # 2. 收缩到 prod < k
                prod //= nums[left]       # 正整数，整除无余数
                left += 1
            ans += right - left + 1       # 3. 结算以 right 结尾的窗口
        return ans
```

## 8. 边界情况与易错点

1. **$k \le 1$ 整体无解**：$k = 0$ 或 $k = 1$ 时答案必为 $0$。若不特判，$k = 0$ 会让 `while (prod >= 0)` 永远成立，`left` 一路冲出数组导致越界。
2. **「严格小于」不是「小于等于」**：`while (prod >= k)` 中的等号不能省。`[10,5,2]` 乘积恰为 100，必须以 100 为界收缩，否则多算。
3. **元素为 1 时窗口不收缩**：`[1,1,1], k = 2` 每轮 `prod = 1 < 2`，`left` 始终为 0，答案 $\frac{3\times4}{2} = 6$。别误以为「窗口长度必须递减」。
4. **`ans` 用 64 位**：$n = 3\times10^4$、全部为 $1$、$k$ 很大时答案 $\frac{n(n+1)}{2} = 450015000$，虽仍在 `int` 范围内，但 `prod * nums[right]` 等中间量在别的题里常溢出，统一 `long long` 更省心。
5. **单个元素就 $\ge k$**：如 `nums = [1000], k = 1000`，收缩后 `left = 1 > right = 0`，`right - left + 1 = 0`，答案 $0$，恰好正确——不需要额外特判。
6. **不要用浮点对数比较**：改用「取对数 + 前缀和」时，$\log$ 的浮点误差会让恰好 $= k$ 的边界翻转，本题用整数乘法即可，别自找精度麻烦。

**延伸思考**：

1. **前缀积 + 二分**：记 $P[i] = nums[0] \times \cdots \times nums[i-1]$，则 $[l, r]$ 合法等价于 $P[r+1] / P[l] < k$，即 $P[l] > P[r+1] / k$。$P$ 单调递增，对每个 $r$ 二分出最小的合法 $l$，$O(n \log n)$。数值上更稳的写法是对 $\log$ 取前缀和：$S[i] = \sum \ln nums[t]$，则条件化为 $S[l] > S[r+1] - \ln k$，但要注意浮点比较的边界误差。
2. **若把「乘积」换成「和」**：正数前提下同样适用滑窗，只需把 `prod` 的乘、除分别换成 `sum` 的加、减，计数公式 `right - left + 1` 完全不变。
3. **若允许 0 与负数**：乘积失去单调性，滑窗立刻失效；此时需要分治或「负数分段 + 前缀积 + 哈希」，复杂度与代码量都会明显上升。
