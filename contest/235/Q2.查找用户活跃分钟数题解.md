# LeetCode 查找用户活跃分钟数 题解

## 1. 题目概述

- **标题 / 题号**：查找用户活跃分钟数（#1817，medium）
- **链接**：https://leetcode.cn/problems/finding-the-users-active-minutes/
- **来源**：LeetCode 第 235 场周赛 Q2
- **难度**：中等
- **标签**：数组、哈希表、计数

**题意**：给定用户在 LeetCode 上的操作日志 `logs`，其中 `logs[i] = [ID_i, time_i]` 表示 ID 为 `ID_i` 的用户在第 `time_i` 分钟执行了一次操作；**多个用户**可在同一分钟操作，**单个用户**也可在同一分钟执行**多个操作**。某用户的**用户活跃分钟数（UAM）**定义为其执行操作的**唯一分钟数**（同一分钟多次操作只计一次）。再给定整数 `k`，返回长度为 `k`、**下标从 1 开始**的数组 `answer`，其中 `answer[j]` 表示 UAM 恰好等于 $j$ 的用户数。

**约束**：

- $1 \le \text{logs.length} \le 10^4$
- $0 \le ID_i \le 10^9$
- $1 \le time_i \le 10^5$
- $k \in [\text{用户的最大用户活跃分钟数},\ 10^5]$

> 💡 **审题关键**：三处定实现——① UAM 是「**去重后**的分钟数」，且去重粒度是 $(id, time)$ **二元组**而非全局 `time`（两个用户在同一分钟各操作一次，双方各计 1 分钟）；② `answer` **下标从 1 开始计数**，落桶要写 `answer[uam−1]`；③ 约束保证 $k \ge$ 最大 UAM，而入表用户的 UAM 必 $\ge 1$，故 $uam \in [1, k]$ 恒成立，统计时**无需越界特判**。赛时信号：$n \le 10^4$ 极小、无思维量，是纯模拟计数题，比拼的是**手速与零 bug**——五分钟内写完并一次通过就是满分表现。

> 💡 本题在本仓库另有[每日题解 1817](../../solution/1801-1900/1817_查找用户活跃分钟数.md)：以「哈希表 + 集合的概念展开、集合 vs 排序去重的方案对比、面试问答」为主线。本篇按**周赛复盘视角**重写：侧重**赛时最短路径决策**（两语言的写法取舍）、**映射方向的选型依据**（为什么是「用户 → 时间」而不是反向）、**引理—定理完整证明链**与**下标转换踩坑清单**，两篇互为印证。

```text
  两个用户 UAM 都是 2 ⇒ answer[2] = 2（数组的第 2 位），其余为 0
```

```text
  answer[1] = 1，answer[2] = 1，其余为 0
```

## 3. 解题思路

### 3.1 暴力思路：逐用户扫全日志

最直觉的暴力是「枚举用户、逐个扫日志」：先收集出现过的所有用户 ID，对每个用户再完整扫一遍 `logs`，挑出属于它的 `time`，用 `set` 去重后得到 UAM。若日志含 $U$ 个不同用户，总代价 $O(U \cdot n)$；最坏 $U = n$（每条日志一个新用户）时退化 $O(n^2) = 10^8$——C++ 纯扫描勉强能过，Python 大概率超时。

但真正的问题不是「过不过」，而是结构性的：**为每个用户重复扫描整份日志**，「同一用户的记录」从头到尾没有被归拢到一起，全部信息白白流过 $U$ 遍。赛时结论：哪怕暴力能过也不写它——哈希版的代码量并不比暴力长。

### 3.2 核心观察：把「去重」编码进数据结构

![核心概念：用户 → 时间集合 → UAM 分桶计数](images/wc235_q2_uam_concept.svg)

把任务拆成两个独立阶段，每阶段恰好一次遍历：**阶段一按用户归拢分钟，阶段二按 UAM 值分桶计数**。归拢阶段的三个选型决策全部由**约束**直接决定：

1. **键放哈希容器**：$ID \le 10^9$，按下标开数组不可行，必须 `dict` / `unordered_map`；
2. **值用集合**：「同一分钟多次操作只计一次」⇒ 把去重需求直接编码进数据结构，`add` / `insert` 即去重，无需任何 `if` 判断——示例 1 中两条 `[0,5]` 只给用户 0 贡献一个元素 `5`；
3. **映射方向取「用户 → 时间集合」**：统计的主体是用户，方向应由「最终要求统计的主体」决定。若反向存「时间 → 用户集合」，求单个用户的 UAM 要扫描所有时间桶，方向选错直接白给。

阶段二则是一次**分布统计**：遍历表中每个用户，`uam = len(集合)`，落桶 `answer[uam−1] += 1`。

### 3.3 算法流程

![算法流程：先归拢去重、再分桶计数](images/wc235_q2_hash_flow.svg)

1. 初始化 `answer = [0] × k`（语义位 $j$ 对应数组下标 $j-1$）；
2. **阶段一（归拢）**：遍历 `logs`，对每条 `(id, t)` 执行 `userTimes[id].add(t)`——键不存在时容器自动建空集合（C++ `operator[]` 默认构造 / Python `defaultdict`）；
3. **阶段二（分桶）**：遍历 `userTimes` 的每个 `(id, s)`，令 `uam = len(s)`，执行 `answer[uam−1] += 1`；
4. 返回 `answer`。

两个循环都是**零分支**：没有 `if`、没有特判——去重交给集合的语义，越界交给约束 $k \ge$ 最大 UAM。周赛 Q2 档位的题目，「代码里分支越少，一次通过的概率越大」。

### 3.4 示例演算

![示例演算：示例 1 的归拢与分桶全过程](images/wc235_q2_walkthrough.svg)

以示例 1 走查阶段一的建表过程：

| i | logs[i] | 操作 | userTimes 全表状态 |
|---|---------|------|--------------------|
| 0 | `[0,5]` | `userTimes[0].add(5)` | `{0: {5}}` |
| 1 | `[1,2]` | `userTimes[1].add(2)` | `{0: {5}, 1: {2}}` |
| 2 | `[0,2]` | `userTimes[0].add(2)` | `{0: {5,2}, 1: {2}}` |
| 3 | `[0,5]` | `userTimes[0].add(5)`（5 已在，无变化） | `{0: {5,2}, 1: {2}}` |
| 4 | `[1,3]` | `userTimes[1].add(3)` | `{0: {5,2}, 1: {2,3}}` |

注意 $i=3$ 行：用户 0 在第 5 分钟的**第二次**操作，`add(5)` 对已存在的元素不做任何改变——这是把去重交给数据结构的直接红利。**且两条 `[0,5]` 并不相邻**（中间隔着 `[0,2]`），重复可以散落在日志的任意位置，集合语义天然免疫。

**阶段二分布统计**：用户 0 的 UAM $= |{2,5}| = 2$、用户 1 的 UAM $= |{2,3}| = 2$，两次 `answer[2−1] += 1` 都落在 $j=2$ 桶，最终 `answer = [0,2,0,0,0]`，与示例一致。

## 4. 算法细节

1. **容器选型**：Python 用 `defaultdict(set)`（或 `dict` + `setdefault`）；C++ 用 `unordered_map<int, unordered_set<int>>`。不要用红黑树版 `map` / `set`——$O(\log n)$ 无必要，代码也不省。
2. **C++ 的「默认构造」红利**：`userTimes[log[0]].insert(log[1])` 一行完成「找键、无则建、再插入」三件事——`operator[]` 在键缺失时默认构造空 `unordered_set`。Python 的对应物是 `defaultdict(set)` 的 `d[id].add(t)`，两者都是各自语言的最短写法。
3. **下标 1 → 0 转换**：题面「下标从 1 开始计数」意味着语义 `answer[j]` 对应实现 `answer[j-1]`。读题看到这句话就该条件反射地写 `−1`——漏写会整体右移一位且必然在 `answer[k]` 越界。
4. **统计循环无需越界防御**：入表用户至少有一条日志，UAM $\ge 1$；又由约束 $k \ge$ 最大 UAM，故 `uam ∈ [1, k]` 恒成立。加 `if (uam <= k)` 不算错，但属于没吃透约束的冗余分支。
5. **无哈希的排序变体**：把 `logs` 按 `(id, time)` 字典序排序后，同一用户的记录连续、同一分钟的重复相邻——一趟扫描「组内数相邻不相等的 `t`」即得各用户 UAM，$O(n \log n)$。本题 $n \le 10^4$ 不存在卡哈希的场景，列出仅供对照（见 §7 变体代码）。

## 5. 正确性证明

**引理 1**（UAM 的集合刻画）：对任意用户 $u$，设 $D(u) = \{\, t : (u, t) \in \text{logs} \,\}$，则 $\text{UAM}(u) = |D(u)|$。

**证明**：UAM 的定义为 $u$ 执行操作的唯一分钟数，即「存在下标 $i$ 使 $\text{logs}[i] = (u, t)$」的不同 $t$ 的个数。由集合的定义，这恰是 $D(u)$ 的元素个数。∎

**引理 2**（归拢不变量）：遍历完 `logs` 后，哈希表中键 $u$ 对应的集合恰为 $D(u)$。

**证明**：对已处理的日志条数归纳。处理 0 条时表为空，结论平凡。设处理完前 $j$ 条后键 $u$ 的集合为 $S_j$，归纳假设 $S_j$ 等于前 $j$ 条中 $u$ 出现的分钟集合。处理第 $j+1$ 条 $(id, t)$：若 $id \ne u$，键 $u$ 的集合不变，仍等于前 $j+1$ 条中 $u$ 的出现分钟集合；若 $id = u$，唯一操作是 $S_{j+1} = S_j \cup \{t\}$，由集合的吸收律，$S_{j+1}$ 恰为前 $j+1$ 条中 $u$ 的出现分钟集合。归纳完成。∎

**定理**（算法正确性）：算法返回的 `answer` 满足对每个 $j \in [1, k]$：`answer[j-1]` 等于 UAM 恰为 $j$ 的用户数。

**证明**：出现在 `logs` 中的每个用户 $u$ 恰在表中占一个键；由引理 1、2，其 UAM $= |D(u)| = $ 键对应集合的大小，且因 $u$ 至少有一条日志，$|D(u)| \ge 1$。由题目约束 $k \ge$ 最大 UAM，故 $1 \le |D(u)| \le k$，`answer[|D(u)|-1] += 1` 不越界；哈希表遍历使每个键恰被访问一次，即每个出现过的用户恰被计数一次。未出现在 `logs` 中的用户没有键、不产生计数——其 UAM 为 0，本就不在 $[1, k]$ 的统计范围内。故 `answer[j-1]` 恰等于 UAM $= j$ 的用户数。∎

## 6. 复杂度分析

- **时间复杂度**：$O(n + k)$。遍历 $n$ 条日志，每条一次均摊 $O(1)$ 的集合插入；遍历哈希表至多 $n$ 个用户各 $O(1)$；初始化 `answer` 需 $O(k)$。值得留意：$k$ 可达 $10^5$ 而 $n \le 10^4$，**初始化 answer 反而可能是耗时大头**——但总量级 $10^5$ 毫无压力，无需优化。
- **空间复杂度**：$O(n + k)$。哈希表最坏存 $n$ 个键值对（每条日志一个新用户）与至多 $n$ 个分钟值；输出数组 $k$ 个。若不计输出，辅助空间 $O(n)$。

## 7. 参考代码

### C++（哈希表 + 集合，主路线）

```cpp
class Solution {
  public:
    vector<int> findingUsersActiveMinutes(vector<vector<int>>& logs, int k) {
        unordered_map<int, unordered_set<int>> userTimes;
        for (const auto& log : logs) {
            userTimes[log[0]].insert(log[1]);
        }

        vector<int> answer(k, 0);
        for (const auto& [uid, minutes] : userTimes) {
            answer[minutes.size() - 1] += 1;
        }
        return answer;
    }
};
```

### C++（排序 + 分组去重，无哈希变体）

```cpp
class Solution {
  public:
    vector<int> findingUsersActiveMinutes(vector<vector<int>>& logs, int k) {
        sort(logs.begin(), logs.end());          // 按 (id, time) 字典序
        vector<int> answer(k, 0);
        int n = logs.size(), i = 0;
        while (i < n) {
            int j = i, uam = 0;
            while (j < n && logs[j][0] == logs[i][0]) {
                if (j == i || logs[j][1] != logs[j - 1][1]) ++uam;  // 组内相邻去重
                ++j;
            }
            answer[uam - 1] += 1;
            i = j;
        }
        return answer;
    }
};
```

### Python（defaultdict(set)，主路线）

```python
from collections import defaultdict

class Solution:
    def findingUsersActiveMinutes(self, logs: List[List[int]], k: int) -> List[int]:
        user_times = defaultdict(set)
        for uid, t in logs:
            user_times[uid].add(t)

        answer = [0] * k
        for minutes in user_times.values():
            answer[len(minutes) - 1] += 1
        return answer
```

### Python（排序 + groupby，无哈希变体）

```python
from itertools import groupby

class Solution:
    def findingUsersActiveMinutes(self, logs: List[List[int]], k: int) -> List[int]:
        answer = [0] * k
        for uid, grp in groupby(sorted(map(tuple, logs)), key=lambda x: x[0]):
            ts = {t for _, t in grp}
            answer[len(ts) - 1] += 1
        return answer
```

> ⚠️ 赛时首选哈希版（最短、无排序）：本题 $n \le 10^4$ 不存在卡哈希的场景，排序变体仅当输入被构造性针对哈希冲突、或语言无哈希容器时才有意义。`groupby` 只分组**连续**相同的键——变体里必须**先 `sorted`**，漏排序会按原顺序碎片化分组，答案全错。

## 8. 边界情况与易错点

1. **下标转换（本题最高频翻车点）**：题目「下标从 1 开始计数」，UAM 为 $j$ 的用户落在 `answer[j−1]`——UAM = 1 的用户计入 `answer[0]`。误写成 `answer[uam]` 会整体右移一位，且必在 `answer[k]` 越界。
2. **去重粒度是 (id, time) 二元组**：不是全局按 `time` 去重——两个用户在同一分钟各操作一次，双方各计 1 分钟；反之同一用户的重复分钟必须去重——用 `list` 收集后忘了转 `set`，UAM 会偏大（示例 1 的用户 0 会被算成 3）。
3. **ID 高达 $10^9$**：不能开数组按下标索引，必须哈希容器。顺带：若走「把 $(id, t)$ 编码成单整数」的极简写法，$10^9 \times 10^5 = 10^{14}$ 超出 `int` 范围，必须用 64 位整数承接。
4. **k ≥ 最大 UAM 是题目保证**：统计循环无需防御性判断；C++ 里 `minutes.size() - 1` 是无符号运算，但集合非空（至少一条日志才入表），不会下溢。
5. **answer 长度固定为 k**：即使实际最大 UAM 远小于 $k$，尾部也要补 0——初始化 `[0] * k` 天然满足，别按实际用户数或最大 UAM 截断数组。
6. **单条日志 / 单用户**：`logs = [[7,42]]` 时 UAM = 1，计入 `answer[0]`；`k = 1` 时数组仅一位（自拟示例 3 是两者的极端合并）。
7. **重复日志可分散出现**：示例 1 的两条 `[0,5]` 中间隔着 `[0,2]`——「排序 + 相邻去重」变体的前提是先排序把重复挤到相邻；哈希 + 集合版天然免疫位置分布。
8. **Python `groupby` 变体必须先排序**：`groupby` 只合并连续相同键，未排序的日志按原始顺序分组，同一用户会被拆成多段、UAM 被低估。
