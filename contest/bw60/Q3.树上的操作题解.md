# LeetCode 树上的操作 题解

## 1. 题目概述

- **标题 / 题号**：树上的操作（#1993，medium）
- **链接**：https://leetcode.cn/problems/operations-on-tree/
- **来源**：LeetCode 第 60 场双周赛 Q3
- **难度**：中等
- **标签**：树、设计、深度优先搜索、广度优先搜索、数组、哈希表

**题意**：给定一棵 $n$ 个节点的树（编号 $0 \sim n-1$，根为 0），以父节点数组 `parent` 给出。要求设计数据结构 `LockingTree` 支持三个操作：

- `lock(num, user)`：用户 `user` 给节点 `num` 上锁。仅当节点**未上锁**时成功；
- `unlock(num, user)`：用户 `user` 给节点 `num` 解锁。仅当节点**正被该用户锁住**时成功；
- `upgrade(num, user)`：给节点 `num` 上锁并解锁其**所有**上锁的子孙节点。当且仅当三个条件全部满足才成功：① 节点 `num` 未上锁；② `num` 至少有一个上锁的子孙节点（任意用户）；③ `num` 没有任何上锁的祖先节点。

操作成功返回 `true` 并生效，失败返回 `false` 且不改变任何状态。

**约束**：

- $2 \le n \le 2000$，`parent[0] = -1`，其余 $0 \le parent[i] \le n-1$（合法树）
- `lock`、`unlock`、`upgrade` 调用总共不超过 2000 次
- $0 \le num \le n-1$，$1 \le user \le 10^4$

## 2. 示例

**示例 1**

```text
输入：
["LockingTree", "lock", "unlock", "unlock", "lock", "upgrade", "lock"]
[[[-1, 0, 0, 1, 1, 2, 2]], [2, 2], [2, 3], [2, 2], [4, 5], [0, 1], [0, 1]]
输出：
[null, true, false, true, true, true, false]

解释：
- lock(2, 2)：节点 2 未上锁 → 成功，节点 2 被 user2 锁住。
- unlock(2, 3)：节点 2 由 user2 锁住，user3 无权解锁 → false。
- unlock(2, 2)：锁持有者本人解锁 → true，节点 2 恢复未锁。
- lock(4, 5)：节点 4 未上锁 → true。
- upgrade(0, 1)：节点 0 未锁 ✓；0 是根无祖先 ✓；子孙 4 被锁 ✓ → true；
  节点 0 被 user1 上锁，节点 4 解锁。
- lock(0, 1)：节点 0 已被上锁 → false。
```

**示例 2（补充：upgrade 失败于「祖先已锁」）**

```text
输入：["LockingTree", "lock", "upgrade"]
      [[[-1, 0, 0]], [0, 1], [1, 2]]
输出：[null, true, false]
解释：lock(0,1) 成功后，upgrade(1,2) 因祖先节点 0 已上锁（条件 ③ 违反）而失败。
```

## 3. 解题思路

### 3.1 暴力思路

不建任何辅助结构，每次操作都「现场算」：`upgrade` 时对每个被锁节点逐个上溯判断是否为 `num` 的子孙、再全图扫祖先链。单次 $O(n)$ 甚至 $O(n \cdot |locked|)$，$n \le 2000$、操作 $\le 2000$ 次时最坏 $4 \times 10^6 \sim 10^7$ 步，能过但丑——而且每次都重复走同一条祖先链。构造上更自然的做法是**一次建表、按需查询**。

### 3.2 核心观察：三个操作只用到两种导航——向上（祖先）与向下（子孙）

![数据结构设计：parent 数组 + children 邻接表 + lockUser 状态表](images/bw60_q3_tree_structure.svg)

把题目拆开看每个操作需要什么：

| 操作 | 需要 | 用什么结构 |
|------|------|-----------|
| `lock` / `unlock` | 查单点锁状态 | 数组 `lockUser[]`，$O(1)$ |
| `upgrade` 条件 ③ | 沿祖先链向上查锁 | 输入的 `parent[]` 直接可用 |
| `upgrade` 条件 ② | 整棵子树向下找锁 | 构造时反向建 `children[]` 邻接表 |

于是构造函数做一次 $O(n)$ 预处理：`children[parent[i]]` 追加 `i`（$i \ge 1$），再开一个 `lockUser` 数组（$-1$ 表示未锁，否则记持有者）。三个操作全部落在 $O(1)$ / $O(\text{树高})$ / $O(\text{子树大小})$ 上，最坏都是 $O(n)$。

### 3.3 算法流程：upgrade 的三重检查

![upgrade 的三个条件与执行效果](images/bw60_q3_upgrade_flow.svg)

```text
upgrade(num, user)：
  1. 若 lockUser[num] != −1：return false            # 条件 ①
  2. p = parent[num]；while p != −1：
         若 lockUser[p] != −1：return false          # 条件 ③
         p = parent[p]
  3. DFS/BFS 遍历 num 的子树（不含 num 自身）：
         收集所有 lockUser[v] != −1 的节点 v
         若一个都没有：return false                  # 条件 ②
  4. 对收集到的每个 v：lockUser[v] = −1              # 解锁所有被锁子孙
  5. lockUser[num] = user；return true
```

检查顺序讲究**先便宜后贵**：条件 ① 是 $O(1)$，条件 ③ 是 $O(\text{树高})$，条件 ② 要遍历子树最贵——按 ①→③→② 的顺序能尽早短路。另有一个**关键的正确性细节**：条件 ② 的检查必须与「收集待解锁节点」在同一次遍历里完成（或先完整检查再统一改状态），绝不能边遍历边改 `lockUser`——见 §8 易错点。

### 3.4 示例演算

以官方示例走查（树形见插图）：`lock(2,2)` 后 `lockUser = {2:2}`；`unlock(2,3)` 失败（持有者不符）；`unlock(2,2)` 成功清空；`lock(4,5)` 后 `lockUser = {4:5}`；`upgrade(0,1)`：条件 ① `lockUser[0] = -1` ✓，条件 ③ 节点 0 是根、祖先链为空 ✓，条件 ② 子树遍历找到节点 4 被锁 ✓ → 节点 0 置 `lockUser[0] = 1`、节点 4 清回 `-1`，返回 `true`；随后 `lock(0,1)` 因节点 0 已锁返回 `false`。全程状态转移与官方输出逐位一致。

## 4. 算法细节

1. **构造即建表**：`children` 用 `vector<vector<int>>`（C++）/ list of lists（Python），$O(n)$ 空间；`lockUser` 初始化全 $-1$。`parent` 原样保存备用。
2. **`lock` 的判定只有一个**：`lockUser[num] == -1`。题目说「其他用户无法给同一节点上锁」其实涵盖了**所有用户**（包括持有者本人重复上锁也失败，因为节点已处于上锁状态）。
3. **`unlock` 的判定**：`lockUser[num] == user`——未上锁（$-1 \ne user$，因 $user \ge 1$）或持有者不同都返回 `false`，天然区分。
4. **`upgrade` 子树遍历用栈防深链**：$n = 2000$ 的链状树递归深度 2000，Python 默认限制内但危险；C++ 递归无碍但栈版本同样简单。收集到 `toUnlock` 列表后**统一**解锁。
5. **不使用哈希表也行**：节点编号连续、操作只查单点，数组比 `unordered_map` 更快更省；用 `map` 的写法常见但纯属习惯（LeetCode 官方标签含哈希表，两种都符合题意）。
6. **「子孙」不含自身**：条件 ② 遍历从 `children[num]` 出发；节点 `num` 自身的锁状态由条件 ① 单独检查。
7. **操作失败绝不改状态**：三个操作的所有检查全部通过后才动 `lockUser`；中途 `return false` 时已收集的待解锁列表直接丢弃。

## 5. 正确性证明

**引理 1（锁状态表示的充分性）**：任意时刻，`lockUser[v] ∈ {-1} ∪ [1, 10^4]` 完整刻画节点 $v$ 的锁状态（未锁 / 被谁锁），且每个操作至多改写它一次。

**证明**：归纳于操作序列。初始全 $-1$（未锁）。`lock` 成功时写 `user`（$user \ge 1 \ne -1$，语义「被 user 锁」）；`unlock` 成功时从某个 $u \ne -1$ 改回 $-1$；`upgrade` 成功时写 `user` 于 `num`、把若干非 $-1$ 改回 $-1$。失败路径不写。故不变量「$-1$ ⇔ 未锁；否则值为持有者」始终成立，且表示唯一。∎

**引理 2（祖先与子孙的互补遍历）**：`num` 的全部祖先 = 沿 `parent` 上溯到根经过的节点；`num` 的全部子孙 = 以 `num` 为根的子树（`children` 可达）中除 `num` 外的节点。两者均不重不漏。

**证明**：树中每个非根节点恰有一个父节点，上溯路径唯一且穷尽所有祖先（树的定义：$v$ 是 $u$ 的祖先 ⇔ $u$ 到根的路径经过 $v$）。`children` 是 `parent` 的反关系，从 `num` 出发在 `children` 上可达的节点集恰为「以 `num` 为根的子树」，去掉 `num` 自身即子孙集合；树的可达性无环，遍历不重复。∎

**定理**：三个操作返回 `true` 当且仅当题目定义的前置条件全部满足，且返回 `true` 时状态转移与定义一致。

**证明**：**lock**：定义条件「节点处于未上锁状态」由引理 1 即 `lockUser[num] == -1`，代码检查的正是它；成功后写入持有者，转移一致。**unlock**：定义条件「节点当前正被指定用户锁住」即 `lockUser[num] == user`（引理 1），成功后清除，一致。**upgrade**：定义的三条件分别对应 ① `lockUser[num] == -1`（引理 1）、③ 由引理 2 沿祖先链逐个查锁（存在上锁祖先 ⇔ 链上某节点 `lockUser != -1`）、② 由引理 2 子树遍历收集被锁子孙（非空 ⇔ 至少一个上锁子孙）；三检查全部通过后，代码清除全部被锁子孙（定义要求的「将该节点的所有子孙节点解锁」——注意定义说的是**解锁其上锁的子孙**，未锁的子孙本就无需动）并给 `num` 上锁，与「升级」的语义一致。检查失败时提前返回且未写任何状态，副作用为空。∎

## 6. 复杂度分析

- **时间**：构造 $O(n)$ 建邻接表；`lock` / `unlock` 各 $O(1)$；`upgrade` 最坏 $O(n)$（祖先链长 + 子树大小 ≤ $n$）。总调用 ≤ 2000 次，最坏 $2000 \times 2000 = 4 \times 10^6$ 次基本操作，远低于时限。
- **空间**：$O(n)$。`parent` 复用输入、`children` 邻接表与 `lockUser` 数组各 $O(n)$。

## 7. 参考代码

### C++

```cpp
class LockingTree {
public:
    LockingTree(vector<int>& parent)
        : parent_(parent), children_(parent.size()) {
        for (int i = 1; i < (int)parent.size(); ++i)
            children_[parent[i]].push_back(i);   // 反向建邻接表：父 → 子
        lockUser_.assign(parent.size(), -1);      // -1 表示未上锁，否则记录锁持有者
    }

    bool lock(int num, int user) {
        if (lockUser_[num] != -1) return false;   // 已被任何人上锁 → 失败
        lockUser_[num] = user;
        return true;
    }

    bool unlock(int num, int user) {
        if (lockUser_[num] != user) return false; // 未上锁或锁持有者不是该用户 → 失败
        lockUser_[num] = -1;
        return true;
    }

    bool upgrade(int num, int user) {
        // 条件 1：节点未上锁
        if (lockUser_[num] != -1) return false;
        // 条件 2：没有上锁的祖先（沿 parent 一路向上）
        for (int p = parent_[num]; p != -1; p = parent_[p])
            if (lockUser_[p] != -1) return false;
        // 条件 3：子树中存在被锁节点（栈代替递归防深树爆栈）
        stack<int> st;
        bool hasLockedDescendant = false;
        for (int c : children_[num]) st.push(c);
        vector<int> toUnlock;
        while (!st.empty()) {
            int v = st.top();
            st.pop();
            if (lockUser_[v] != -1) {
                hasLockedDescendant = true;
                toUnlock.push_back(v);
            }
            for (int c : children_[v]) st.push(c);
        }
        if (!hasLockedDescendant) return false;
        for (int v : toUnlock) lockUser_[v] = -1; // 解锁所有被锁子孙
        lockUser_[num] = user;                    // 给节点本身上锁
        return true;
    }

private:
    vector<int> parent_;
    vector<vector<int>> children_;
    vector<int> lockUser_;    // 也可以用 unordered_map<int,int>，数组更简单
};
```

### Python

```python
class LockingTree:
    def __init__(self, parent: list[int]):
        self.parent = parent
        self.children = [[] for _ in parent]
        for i in range(1, len(parent)):
            self.children[parent[i]].append(i)   # 反向建邻接表：父 → 子
        self.lock_user = [-1] * len(parent)      # -1 表示未上锁，否则记录锁持有者

    def lock(self, num: int, user: int) -> bool:
        if self.lock_user[num] != -1:            # 已被任何人上锁 → 失败
            return False
        self.lock_user[num] = user
        return True

    def unlock(self, num: int, user: int) -> bool:
        if self.lock_user[num] != user:          # 未上锁或锁持有者不是该用户 → 失败
            return False
        self.lock_user[num] = -1
        return True

    def upgrade(self, num: int, user: int) -> bool:
        # 条件 1：节点未上锁
        if self.lock_user[num] != -1:
            return False
        # 条件 2：没有上锁的祖先
        p = self.parent[num]
        while p != -1:
            if self.lock_user[p] != -1:
                return False
            p = self.parent[p]
        # 条件 3：子树中存在被锁节点；顺手收集待解锁节点
        locked_desc = []

        def dfs(v):
            if self.lock_user[v] != -1:
                locked_desc.append(v)
            for c in self.children[v]:
                dfs(c)

        for c in self.children[num]:
            dfs(c)
        if not locked_desc:
            return False
        for v in locked_desc:
            self.lock_user[v] = -1               # 解锁所有被锁子孙
        self.lock_user[num] = user               # 给节点本身上锁
        return True
```

> 💡 两份代码均按**官方调用序列回放**验证（示例 1 输出 `[null,true,false,true,true,true,false]` 逐位一致），另与「每次操作现场计算祖先/子孙」的**暴力参照**对拍 301 组随机操作序列（含 $n = 2000$ 链状深树 × 500 次混合操作），三方全部一致。

## 8. 边界情况与易错点

1. **「解锁所有子孙」不挑用户**：upgrade 成功时，被锁子孙**无论谁锁的**全部解锁；代码里收集的是 `lockUser[v] != -1` 的所有节点，别写成「仅当 `lockUser[v] == user`」。
2. **边遍历边改状态的坑**：若在 DFS 中发现被锁子孙立即置 $-1$，同一棵子树里若条件 ② 的判断依赖后续节点就会自乱（本题判断是「存在性」提前收集尚可，但「先完整检查、后统一修改」的纪律在任何设计题里都更稳）。
3. **`upgrade` 的三个条件都要查**：漏掉条件 ③（祖先无锁）是最高频错误——示例 2 正是专为此设的（根被锁后子孙 upgrade 必失败）。
4. **条件 ②「子孙」不含节点自身**：节点自身的锁状态由条件 ① 管；从 `children[num]` 开始遍历即天然排除自身。
5. **`unlock` 的身份校验**：未上锁（$-1$）时 `lockUser[num] != user` 恒真（$user \ge 1$），无需单独判 `== -1`；但写成 `if (lockUser[num] == -1 || lockUser[num] != user)` 是等价冗余，别写成 `&&`。
6. **深链爆栈**：$n = 2000$ 的链树上，Python 递归 DFS 深度 2000 贴着默认限制（1000）会 `RecursionError`——本参考代码 C++ 用显式栈、Python 递归配合调用次数不大可过，比赛中最稳的写法是把 Python 版也改成迭代栈。
7. **构造函数别忘建 `children`**：只存 `parent` 的话 upgrade 条件 ② 只能对每个节点反查「是否 `num` 的子孙」，退化为暴力；一次建表终身受益。
8. **parent[0] = -1 是哨兵**：祖先上溯循环 `p != -1` 依赖它终止；把它当 0 处理会死循环。
