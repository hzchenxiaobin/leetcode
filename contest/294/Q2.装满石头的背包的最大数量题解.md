# LeetCode 装满石头的背包的最大数量 题解

## 1. 题目概述

- **标题 / 题号**：装满石头的背包的最大数量（#2279，medium）
- **链接**：https://leetcode.cn/problems/maximum-bags-with-full-capacity-of-rocks/
- **来源**：LeetCode 第 294 场周赛 Q2
- **难度**：中等
- **标签**：贪心、数组、排序

**题意**：`n` 个背包，第 `i` 个容量为 `capacity[i]`、已装 `rocks[i]` 块石头。另有 `additionalRocks` 块**同质**石头，可放入任意背包。放置后返回**恰好装满**（石头数 = 容量）的背包的最大数量。

**约束**：

- $1 \le n \le 5 \times 10^4$
- $1 \le \text{capacity[i]} \le 10^9$
- $0 \le \text{rocks[i]} \le \text{capacity[i]}$（保证缺口非负）
- $1 \le \text{additionalRocks} \le 10^9$

> 💡 本题在本仓库另有[每日题解 2279](../../solution/2201-2300/2279_装满石头的背包的最大数量.md)：以「等收益最小成本」模板 + 交换论证 + 0-1 背包扩展与面试问答展开。本篇按**周赛复盘视角**展开，侧重**5 分钟内识别模板并落笔**的切入路径、**不排序贪心的实锤 WA 反例**、引理-定理化的严格证明（下界 + 可达性 + 单调性）、前缀和溢出与逐个扣减的边界对照，两篇互为印证。

## 2. 示例

**示例 1**

```text
输入：capacity = [2,3,4,5], rocks = [1,2,4,4], additionalRocks = 2
输出：3
解释：缺口 [1,1,0,1]。背包 2 本就满；1 块给背包 0、1 块给背包 1，
      恰好用完 2 块预算，共 3 个满背包。
```

**示例 2**

```text
输入：capacity = [10,2,2], rocks = [2,2,0], additionalRocks = 100
输出：3
解释：缺口 [8,0,2]。花 8 + 2 = 10 即全部装满，预算剩 90 —— 不必用完。
```

**补充反例：不排序「能补就补」是 WA 实锤**

```text
输入：capacity = [3,2,2], rocks = [0,0,0], additionalRocks = 4
输出：2
解释：缺口 [3,2,2]。升序先补两个缺口 2（花 4）→ 2 个满背包；
      原序遍历先花 3 补背包 0 → 剩 1，两个缺口 2 都补不起，只得 1。
```

> ⚠️ 这个反例的欺骗性在于：示例 1、2 的数据**不排序也碰巧全对**（各缺口几乎都不超预算），随原序扫一遍「能补就补」照样 AC 官方样例——只有构造出「大缺口排在前、吃光预算」的数据才暴露错误。周赛里这类「样例过 = 交了再说」的贪心题，排序与否必须靠证明拍板，不能靠样例。

## 3. 解题思路

### 3.1 比赛切入：三步识别「等收益最小成本」模板

Q2 的目标是**识别快、写得快**。本题从题面到代码只需三个观察：

1. **暴力为什么不可行**：枚举石头放置方案是指数级；且 `additionalRocks` 高达 $10^9$，逐块决策本身就没有意义。
2. **石头同质 ⇒ 问题坍缩**：放哪块石头无区别，每个背包只有两种结局——**填满**（花费其缺口）或**不填满**（对答案零贡献）。于是问题变为：预算 `additionalRocks` 内，**选尽量多的背包、各付其缺口**。
3. **等收益 ⇒ 按成本排序**：每装满一个背包收益都是 $+1$，唯一的差异是成本（缺口）——有限预算买最多件东西，先买最便宜的。

第 3 步正是 [455. 分发饼干](https://leetcode.cn/problems/assign-cookies/)、[1833. 雪糕的最大数量](https://leetcode.cn/problems/maximum-ice-cream-bars/) 的同款骨架，比赛时应当形成条件反射。

### 3.2 核心观察：缺口即成本，升序贪心

![核心观察：装满的成本 = 缺口，等收益下先买最便宜的](images/wc294_q2_greedy_concept.svg)

定义第 `i` 个背包的**缺口**：

$$\text{need}[i] = \text{capacity}[i] - \text{rocks}[i]$$

由约束 $\text{rocks[i]} \le \text{capacity[i]}$ 知 $\text{need}[i] \ge 0$，且 $\text{need} = 0$ 表示**已满、免费**。

**贪心策略**：将 `need` **升序排序**，从最小缺口开始逐个用预算填补；一旦当前缺口超过剩余预算，**后面只会更大，直接终止**。

反例图已给出「为什么不能按原序补」的直觉：花 $3$ 补一个大缺口的钱，本可以换来两个 $2$ 缺口的满背包——**等收益下，钱要花在见效最快的地方**。

### 3.3 算法流程

![算法流程：算缺口 → 升序排序 → 贪心扣减，补不起即停](images/wc294_q2_algorithm_flow.svg)

1. **算缺口**：$\text{need}[i] = \text{capacity}[i] - \text{rocks}[i]$，$O(n)$；
2. **排序**：`need` 升序，$O(n \log n)$，**全程瓶颈**；缺口 $0$ 自动沉底，无需单独统计已满数；
3. **贪心扫描**：若剩余预算 $\ge \text{need}[i]$，则扣减、$\text{ans} \mathrel{+}= 1$；否则 `break`（升序保证后续全部补不起）；
4. **返回** `ans`。

### 3.4 示例演算

![示例演算：预算 2 恰好买满 3 个；预算 100 全满还剩 90](images/wc294_q2_example_walkthrough.svg)

**示例 1**：`need = [1,1,0,1]` → 排序 `[0,1,1,1]`，预算 $2$：

| 步 $i$ | 缺口 | 预算变化 | 动作 | 已满数 |
|--------|------|----------|------|--------|
| 0 | 0 | $2 \to 2$ | 白嫖（本就满） | 1 |
| 1 | 1 | $2 \to 1$ | 花 1 买满 | 2 |
| 2 | 1 | $1 \to 0$ | 花 1 买满 | 3 |
| 3 | 1 | $0 < 1\ \text{✗}$ | 补不起 → 停 | **3** |

**示例 2**：`need = [8,0,2]` → 排序 `[0,2,8]`，预算 $100$：三步全满，$\text{ans} = 3$，剩余 $90$ 块不用完。

两例对照：**预算紧张**时「先小后大」才能覆盖最多背包（示例 1 恰好卡在第 4 个差 1）；**预算充裕**时自然全满，`break` 不触发但结果一致。

## 4. 算法细节

1. **原地求缺口**：C++ 里 `capacity` 按引用传入，直接 `capacity[i] -= rocks[i]` 后 `sort(capacity)`，除排序外 $O(1)$ 额外空间；比赛写法从简，工程代码若不可改入参则另建数组（Python 的 `sorted(生成器)` 天然新建）。
2. **扣减的不变式（防溢出关键）**：只在「剩余 $\ge$ 缺口」时扣减，故剩余预算全程 $\in [0,\, 10^9]$，`int` 安全；**不要**先求「总缺口前缀和」——$5 \times 10^4 \times 10^9 = 5 \times 10^{13}$ 溢出 32 位整数。
3. **二分答案变体**：令 $D_k$ 为前 $k$ 小缺口之和（前缀和），则 $\text{ans} = \max\{k : D_k \le \text{additionalRocks}\}$，可排序 + 前缀和 + `bisect` / `upper_bound` 求解；C++ 此写法前缀和**必须 `long long`**。贪心扫描与二分同为 $O(n \log n)$，前者更短，比赛首选。
4. **`break` 而非 `continue`**：升序下单调性保证当前补不起则后续必补不起；若没排序，`break` 是致命错误（见 §8 第 1 条，两种写法都不该存在）。
5. **缺口 $0$ 不特判**：排序天然沉底，花费 $0$、`ans += 1`，与「已满背包直接计数」语义一致，比单独 `count(need == 0)` 更不易错。

## 5. 正确性证明

**引理 1（前 $k$ 小是代价下界）**：将全部缺口升序排列为 $d_1 \le d_2 \le \cdots \le d_n$，记 $D_k = \sum_{j=1}^{k} d_j$。任意大小为 $k$ 的背包集合 $S$ 的装满开销 $\text{cost}(S) = \sum_{i \in S} \text{need}[i] \ge D_k$。

**证明**：$S$ 中 $k$ 个缺口对应排序序列中的 $k$ 个位置 $p_1 < p_2 < \cdots < p_k$。由位置单调性，$p_j \ge j$ 对每个 $j$ 成立（前 $j$ 个位置至多被 $j-1$ 个更早的元素占据），又 $d$ 不减，故 $d_{p_j} \ge d_j$。对 $j$ 求和即 $\text{cost}(S) \ge \sum_{j=1}^{k} d_j = D_k$。∎

**引理 2（前 $k$ 小可达）**：若 $D_k \le \text{additionalRocks}$，则把缺口最小的 $k$ 个背包各补上其缺口是一个合法放置方案，装满数 $\ge k$。

**证明**：总花费恰为 $D_k$，不超过预算；补完后这些背包石头数 = 容量，恰好装满；其余背包不动，放置合法。∎

**引理 3（可行集合是前缀）**：缺口非负 ⇒ $D_k$ 关于 $k$ 单调不减 ⇒ $\{k : D_k \le R\}$ 形如 $\{0, 1, \ldots, \text{ans}\}$ 的前缀区间，其中 $\text{ans} = \max\{k : D_k \le R\}$。升序贪心扫描逐项扣减，恰在 $D_{\text{ans}} \le R < D_{\text{ans}+1}$ 处停止，返回值即该 $\text{ans}$。

**证明**：单调性显然（和式逐项加非负数）。贪心第 $k$ 步后剩余预算为 $R - D_k$，能走完第 $k$ 步当且仅当 $R - D_{k-1} \ge d_k$，即 $D_k \le R$；故扫描完成的步数恰为最大的可行 $k$。∎

**定理**：升序贪心返回的 `ans` 是装满背包数的最大值。

**证明**：设最优值为 $k^*$，即存在集合 $S^*$（$|S^*| = k^*$）可被预算装满，则 $\text{cost}(S^*) \le R$。由引理 1，$D_{k^*} \le \text{cost}(S^*) \le R$，由引理 3 得 $k^* \le \text{ans}$。反之由引理 2，贪心方案合法装满 $\text{ans}$ 个背包，故 $\text{ans} \le k^*$。两向合逼，$\text{ans} = k^*$。∎

> 💡 每日题解中的**交换论证**（把花在大缺口上的预算转给小缺口，答案不降）与引理 1 一体两面：交换论证说「存在只取最小若干缺口的最优解」，引理 1 则直接给出「任何 $k$ 个背包的开销下界」——后者形式化更强，直接支撑二分答案变体的正确性。

## 6. 复杂度分析

- **时间复杂度**：$O(n \log n)$。排序主导；算缺口 $O(n)$、贪心扫描至多 $O(n)$（`break` 常常更早终止）。$n \le 5 \times 10^4$，瓶颈在排序，已是比较排序模型下的常规复杂度，无需再优化。
- **空间复杂度**：$O(n)$ 存缺口数组（Python `sorted` 新建列表）；C++ 原地写法（复用 `capacity`）除排序栈外 $O(1)$ 额外空间。

## 7. 参考代码

### C++（原地缺口 + 排序 + 贪心）

```cpp
class Solution {
public:
    int maximumBags(vector<int>& capacity, vector<int>& rocks, int additionalRocks) {
        const int n = capacity.size();
        for (int i = 0; i < n; ++i) capacity[i] -= rocks[i];   // 原地求缺口
        sort(capacity.begin(), capacity.end());                // 升序
        int ans = 0;
        for (int need : capacity) {
            if (need > additionalRocks) break;                 // 后面更大，必都不够
            additionalRocks -= need;
            ++ans;
        }
        return ans;
    }
};
```

### Python（生成器排序 + 贪心）

```python
class Solution:
    def maximumBags(self, capacity: List[int], rocks: List[int], additionalRocks: int) -> int:
        need = sorted(c - r for c, r in zip(capacity, rocks))
        ans = 0
        for d in need:
            if d > additionalRocks:
                break
            additionalRocks -= d
            ans += 1
        return ans
```

### Python（变体：前缀和 + 二分）

```python
from bisect import bisect_right
from itertools import accumulate

class Solution:
    def maximumBags(self, capacity: List[int], rocks: List[int], additionalRocks: int) -> int:
        pref = [0] + list(accumulate(sorted(c - r for c, r in zip(capacity, rocks))))
        return bisect_right(pref, additionalRocks) - 1
```

> ⚠️ 两个 C++ 细节：① `additionalRocks` 按值传入可直接修改；只在「够付」时扣减，全程 $\in [0, 10^9]$，`int` 无溢出。② 二分变体的前缀和最大 $5 \times 10^{13}$，C++ 必须用 `long long` 存前缀和（Python 任意精度无虞）。

## 8. 边界情况与易错点

1. **不排序直接「能补就补」（头号 WA）**：反例 `capacity=[3,2,2], rocks=[0,0,0], R=4` 得 1，正确 2——先花 3 吃光预算，两个缺口 2 全补不起。官方样例恰好检不出，必须靠「等收益 ⇒ 按成本排序」的证明拍板。
2. **没排序还敢 `break`**：遇到第一个补不起的缺口就停，原序下会把后面能补的小缺口全部漏掉，比第 1 条错得更狠。
3. **溢出**：总缺口可达 $5 \times 10^{13}$，超出 32 位 `int`——逐个扣减写法安全（见 §4 第 2 条），前缀和 / 二分写法 C++ 必须 `long long`。
4. **预算不必用完**：示例 2 剩 90 块。终止条件是「当前缺口补不起」，不是「花光预算」。
5. **缺口非负由约束保证**：$0 \le \text{rocks[i]} \le \text{capacity[i]}$；若题面放宽需 `max(0, ...)` 截断，否则负缺口会污染排序与单调性。
6. **已满背包无需特判**：缺口 0 排序后沉底、花费 0；极端「全部已满」时循环零扣减，直接返回 $n$。
7. **修改入参**：C++ 原地写法复用 `capacity`（按引用传入，比赛安全）；若接口约定不可变，需复制一份。
8. **答案上界是 $n$**：`additionalRocks` 再大（$10^9$）也不能超过背包总数；无需 `min(n, ...)` 之类的多余修正，贪心天然封顶。
