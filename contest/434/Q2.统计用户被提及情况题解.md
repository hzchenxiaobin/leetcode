# LeetCode 统计用户被提及情况 题解

## 1. 题目概述

- **标题 / 题号**：统计用户被提及情况（#3433，medium）
- **链接**：https://leetcode.cn/problems/count-mentions-per-user/
- **来源**：LeetCode 第 434 场周赛 Q2
- **难度**：中等
- **标签**：数组、排序、模拟、事件扫描

**题意**：`numberOfUsers` 个用户初始全部在线。给定 `events`，每条事件是两类之一：

- **消息事件** `["MESSAGE", "timestamp", "mentions_string"]`：`mentions_string` 是三种形式之一——
  - `id<number>` 列表：空格分隔、**可重复**，直接提及这些用户（**允许提及离线用户**）；
  - `ALL`：提及所有用户（含离线）；
  - `HERE`：提及所有**在线**用户。
- **离线事件** `["OFFLINE", "timestamp", "id"]`：用户 `id` 在 `timestamp` 时刻离线 60 个单位时间，到 `timestamp + 60` 自动上线。

返回 `mentions[i]`：用户 `i` 在所有 MESSAGE 事件中被提及的总次数（同一条消息内重复提及**分别计数**）。

**关键规则**：**状态变更（离线 / 重新上线）先于同一时刻的 MESSAGE 事件处理**——即 `OFFLINE(t, u)` 对 `t` 时刻的 HERE 生效（`u` 已离线），而恰在 `t` 时刻重新上线的用户对 `t` 时刻的 HERE 算在线。

**约束**：

- `1 <= numberOfUsers <= 100`
- `1 <= events.length <= 100`
- `1 <= int(events[i][1]) <= 10^5`
- 单条 MESSAGE 中 id 提及数 1~100；`0 <= <number> <= numberOfUsers - 1`
- OFFLINE 事件发生时，该用户保证处于在线状态（⇒ 同一用户的离线区间互不重叠）
- **约束未保证 `events` 按时间戳升序给出**，需自行排序

## 2. 示例

**示例 1**

```text
输入：numberOfUsers = 2, events = [["MESSAGE","10","id1 id0"],["OFFLINE","11","0"],["MESSAGE","71","HERE"]]
输出：[2,2]
解释：t=10 提及 id1 和 id0，mentions = [1,1]；
      t=11 id0 离线（到 71 上线）；
      t=71 id0 恰好重新上线，"HERE" 提及两人，mentions = [2,2]。
```

**示例 2**

```text
输入：numberOfUsers = 2, events = [["MESSAGE","10","id1 id0"],["OFFLINE","11","0"],["MESSAGE","12","ALL"]]
输出：[2,2]
解释："ALL" 包括离线用户，t=12 时 id0（离线中）和 id1 都被提及。
```

**示例 3**

```text
输入：numberOfUsers = 2, events = [["OFFLINE","10","0"],["MESSAGE","12","HERE"]]
输出：[0,1]
解释：id0 离线区间 [10, 70)，t=12 仍离线，"HERE" 只提及 id1。
```

## 3. 解题思路

### 3.1 朴素思路：按输入顺序模拟（错误）或逐消息重算

最直观的写法是按输入顺序逐条模拟，但有个隐藏陷阱：**约束里没有保证 `events` 按时间戳有序**，晚发生的事件可能先出现在数组里，直接按输入顺序维护在线状态会错。

意识到要排序后，还有一版"逐消息重算"的暴力：对每条 `MESSAGE(t)`，扫描全部 OFFLINE 事件，逐用户判断 `t` 是否落入某个离线区间 `[s, s+60)`。单条消息判定 $O(F \cdot U)$（$F$ 为 OFFLINE 条数），总计 $O(M \cdot F \cdot U) \le 10^6$，本题规模下也能过，但每次全量重算很浪费——**在线状态是随时间单调演化的量，天然适合增量维护**。

### 3.2 核心观察：离线是左闭右开区间，一个数 offlineUntil[u] 足矣

三个观察把模拟降到最简：

1. **离线是区间，且同一用户的区间互不重叠**。`OFFLINE(s, u)` 让 $u$ 在 $[s, s+60)$ 内离线；由于题面保证 OFFLINE 发生时 $u$ 必在线，同一用户相邻两次离线满足 $s_{j+1} \ge s_j + 60$。因此**不需要区间数组，每个用户只需记一个数**——最近一次离线的上线时刻 $\text{offlineUntil}[u]$。
2. **在线判定是一行比较**：时刻 $t$ 用户 $u$ 在线当且仅当 $\text{offlineUntil}[u] \le t$。等号方向由"状态变更先于同刻消息"决定：**恰在 $t$ 重新上线算在线，恰在 $t$ 离线算离线**（区间左闭右开的含义）。
3. **ALL 与 id 提及与在线状态无关**：`ALL` 无条件全体 +1；`id<number>` 列表无条件逐个 +1（可提及离线用户、可重复）。只有 `HERE` 需要在线判定。

![离线区间与上线时刻判定](images/user_mentions_offline_timeline.svg)

### 3.3 算法流程

![排序加单遍扫描流程](images/user_mentions_algorithm_flow.svg)

1. **排序**：以 `(int(时间戳), 类型是否 MESSAGE)` 为键升序——第二关键字保证**同刻 OFFLINE 先于 MESSAGE**。
2. **初始化**：`mentions[u] = 0`，`offlineUntil[u] = 0`（时间戳 $\ge 1 > 0$，等价于初始在线）。
3. **单遍扫描**：
   - `OFFLINE (t, id)`：`offlineUntil[id] = t + 60`（区间不重叠，直接覆盖即可）；
   - `MESSAGE (t, s)`：`"ALL"` → 全体 +1；`"HERE"` → 对每个满足 `offlineUntil[u] <= t` 的用户 +1；否则按空格切分，每个 token `"id<k>"` 给 `mentions[k]` + 1。
4. 返回 `mentions`。

### 3.4 示例演算

以示例 1（`numberOfUsers = 2`）走查，排序后事件依次为 `t=10` MESSAGE、`t=11` OFFLINE、`t=71` MESSAGE：

| 时刻 | 事件 | 动作与判定 | mentions |
|------|------|-----------|----------|
| 10 | MESSAGE "id1 id0" | id 形式不做在线过滤：id1 +1、id0 +1 | [1, 1] |
| 11 | OFFLINE id0 | `offlineUntil[0] = 11 + 60 = 71`，计数不变 | [1, 1] |
| 71 | MESSAGE "HERE" | id0：71 ≤ 71 已重新上线 → +1；id1 在线 → +1 | **[2, 2]** |

![示例1逐步演算](images/user_mentions_example_walkthrough.svg)

> 💡 若把这条 HERE 提前到 `t=70`，则 `offlineUntil[0]=71 > 70`，id0 不被提及，答案变成 [1, 2]——**边界等号方向正是本题最阴的坑**。

## 4. 算法细节

1. **排序键的第二关键字**：把 `events[i][0] == "MESSAGE"` 作为 bool 参与比较，OFFLINE（false）排在同刻 MESSAGE（true）之前，恰好实现"同刻状态变更先行"。
2. **`offlineUntil` 初始化为 0 的合法性**：时间戳 $\ge 1$，初始 $\text{offlineUntil}[u] = 0 \le t$ 恒成立，即"从第 0 时刻起就在线"，无需额外的在线标志数组。
3. **覆盖写而非取 max**：处理 `OFFLINE(t, u)` 时直接赋值。由离线区间的不重叠性，赋值时用户必在线，即旧值 $\le t$，新值 $t + 60$ 严格更大，覆盖与取 max 等价。
4. **`mentions_string` 三分支**：先整串判等 `"ALL"` / `"HERE"`；剩余情况必为 id 列表，`split()` 后 `int(tok[2:])` 剥掉 `"id"` 前缀。逐 token 累加天然支持重复提及分别计数。
5. **时间戳是字符串**：参与排序与运算前必须转整数——字典序下 `"9" > "10"`，直接按字符串比较必错。

## 5. 正确性证明

**引理 1（离线区间语义）**：设用户 $u$ 的全部 OFFLINE 时刻为 $s_1 < s_2 < \cdots$，则 $u$ 在时刻 $t$ 离线，当且仅当存在某个 $s_j$ 使 $s_j \le t < s_j + 60$。

**证明**：`OFFLINE(s_j, u)` 使 $u$ 自 $s_j$ 起离线，至 $s_j + 60$ 自动上线。由"状态变更先于同刻消息"的规则，$s_j$ 时刻的 HERE 视 $u$ 为离线、$s_j + 60$ 时刻的 HERE 视 $u$ 为在线，故离线恰为左闭右开区间 $[s_j, s_j+60)$。又因 OFFLINE 发生时 $u$ 必在线，有 $s_{j+1} \ge s_j + 60$，诸区间两两不交（可首尾相接）。因此 $t$ 时刻 $u$ 离线 ⟺ $t$ 落入某个 $[s_j, s_j+60)$。∎

**引理 2（单变量判定）**：按排序后的顺序处理事件、维护 $\text{offlineUntil}[u]$（初始 0）时，`MESSAGE(t)` 处 $u$ 在线 ⟺ $\text{offlineUntil}[u] \le t$。

**证明**：处理 `MESSAGE(t)` 时，排序保证所有 $s \le t$ 的 OFFLINE 均已处理（同刻 OFFLINE 优先），故 $\text{offlineUntil}[u] = \max\{s_j : s_j \le t\} + 60$；而 $s > t$ 的 OFFLINE 尚未处理，其区间起点大于 $t$，不影响 $t$ 时刻状态。由引理 1，$u$ 离线 ⟺ 存在 $s_j \le t$ 使 $t < s_j + 60$ ⟺ $\max\{s_j\} + 60 > t$ ⟺ $\text{offlineUntil}[u] > t$。取反即得。∎

**定理**：排序 + 单遍扫描统计出的 `mentions` 与题面定义一致。

**证明**：三部分分别对应：(1) `ALL` 与 `id<number>` 提及不依赖在线状态，按定义全体或逐 token +1（重复 id 分别计数），与题面一致；(2) `HERE` 提及在线用户，由引理 2，判定 $\text{offlineUntil}[u] \le t$ 与"在线"语义一致；(3) OFFLINE 的覆盖写由引理 1 的区间不交性保证正确。∎

## 6. 复杂度分析

- **时间复杂度**：$O(E \log E + \sum_{\text{MESSAGE}} (U + L))$，其中 $L$ 为该消息的 token 数。最坏每条 MESSAGE 都是 HERE/ALL，总计 $O(E \log E + E \cdot U)$；代入 $E, U \le 100$ 约 $2 \times 10^4$ 次基本操作，轻松通过。
- **空间复杂度**：$O(U + E)$——`mentions` 与 `offlineUntil` 数组 $O(U)$；C++ 对下标数组排序额外 $O(E)$。

## 7. 参考代码

### C++

```cpp
class Solution {
  public:
    vector<int> countMentions(int numberOfUsers, vector<vector<string>>& events) {
        int n = events.size();
        vector<int> order(n);
        iota(order.begin(), order.end(), 0);
        auto key = [&](int i) {
            // 时间戳升序；同刻 OFFLINE 先于 MESSAGE（状态变更先行）
            return make_pair(stoi(events[i][1]), events[i][0] == "MESSAGE");
        };
        sort(order.begin(), order.end(), [&](int a, int b) { return key(a) < key(b); });

        vector<int> mentions(numberOfUsers, 0);
        vector<int> offlineUntil(numberOfUsers, 0);  // ≤ t 即在线；0 = 初始在线

        for (int i : order) {
            int t = stoi(events[i][1]);
            if (events[i][0] == "OFFLINE") {
                offlineUntil[stoi(events[i][2])] = t + 60;  // 区间不重叠，直接覆盖
            } else {
                const string& s = events[i][2];
                if (s == "ALL") {
                    for (int u = 0; u < numberOfUsers; u++) mentions[u]++;
                } else if (s == "HERE") {
                    for (int u = 0; u < numberOfUsers; u++)
                        if (offlineUntil[u] <= t) mentions[u]++;  // 边界取 ≤
                } else {
                    stringstream ss(s);
                    string tok;
                    while (ss >> tok) mentions[stoi(tok.substr(2))]++;  // 重复分别计
                }
            }
        }
        return mentions;
    }
};
```

### Python

```python
class Solution:
    def countMentions(self, numberOfUsers: int, events: List[List[str]]) -> List[int]:
        mentions = [0] * numberOfUsers
        offline_until = [0] * numberOfUsers  # ≤ t 即在线；0 = 初始在线

        # 时间戳升序；同刻 OFFLINE 先于 MESSAGE（状态变更先行）
        order = sorted(range(len(events)),
                       key=lambda i: (int(events[i][1]), events[i][0] == "MESSAGE"))

        for i in order:
            t = int(events[i][1])
            if events[i][0] == "OFFLINE":
                offline_until[int(events[i][2])] = t + 60  # 区间不重叠，直接覆盖
            else:
                s = events[i][2]
                if s == "ALL":
                    for u in range(numberOfUsers):
                        mentions[u] += 1
                elif s == "HERE":
                    for u in range(numberOfUsers):
                        if offline_until[u] <= t:  # 边界取 ≤
                            mentions[u] += 1
                else:
                    for tok in s.split():  # 重复 id 分别计
                        mentions[int(tok[2:])] += 1
        return mentions
```

## 8. 边界情况与易错点

1. **`events` 乱序是最大的坑**：约束未保证按时间戳升序，必须先按 `(时间戳, OFFLINE 优先)` 排序，否则在线状态会错乱。
2. **同刻优先级**：OFFLINE 与 MESSAGE 同刻时状态变更先行——排序第二关键字 `events[i][0] == "MESSAGE"` 让 OFFLINE 排前。
3. **边界等号**：判定在线用 `offlineUntil[u] <= t`。写成 `<` 会在"恰在重新上线时刻发 HERE"处出错（示例 1 的 `t=71` 正是这个边界）；对应地，恰在离线时刻发 HERE 不提及（同刻离线先行）。
4. **id 可重复**：`"id0 id0"` 给 id0 计 2 次，逐 token 累加天然正确，**不要去重**。
5. **id 可提及离线用户**：解析 id 列表时不要做任何在线过滤；只有 `HERE` 需要在线判定。
6. **OFFLINE 直接覆盖写**：题面保证 OFFLINE 时用户在线 ⇒ 离线区间不重叠，`offlineUntil[u] = t + 60` 无需取 max。
7. **时间戳是字符串**：先转整数再比较 / 运算，字典序比较 `"9" > "10"` 必错。

**延伸思考**：

- 若 $U, E$ 放大到 $10^5$：ALL/HERE 的"全体 +1"改为全局基数 `base++`；离线用户放入按 `offlineUntil` 的小根堆，`HERE(t)` 前先弹出所有 $\le t$ 的（恢复在线），再给仍在堆中的离线用户记欠账 `debt[u]++`，最终 $\text{mentions}[u] = \text{base} - \text{debt}[u] + \text{extra}[u]$（`extra` 为 id 提及），均摊 $O((E+U)\log E)$。
- 若离线时长不固定（每条 OFFLINE 自带时长 $d$）：把 60 换成 $d$，其余完全不变。
- 若允许 `mentions_string` 混合形式（如 `"HERE id3"`）：逐 token 独立判定即可，算法骨架不变。
