# LeetCode HTML 实体解析器 题解

## 1. 题目概述

- **标题 / 题号**：HTML 实体解析器（#1410，medium）
- **链接**：https://leetcode.cn/problems/html-entity-parser/
- **来源**：LeetCode 第 184 场周赛 Q3
- **难度**：中等
- **标签**：哈希表、字符串、模拟

**题意**：给定字符串 `text`，实现一个 HTML 实体解析器——把其中的**字符实体**替换为对应的字符本身，返回解析结果。需识别的实体共 6 种：

| 字符实体 | 替换为 | 含义 | 长度 |
|----------|--------|------|------|
| `&quot;` | `"` | 双引号 | 6 |
| `&apos;` | `'` | 单引号 | 6 |
| `&amp;` | `&` | 与符号 | 5 |
| `&gt;` | `>` | 大于号 | 4 |
| `&lt;` | `<` | 小于号 | 4 |
| `&frasl;` | `/` | 斜线号 | 7 |

隐含语义（由示例 1 可证）：**只对原文中的实体做恰好一次替换，替换产物不再参与后续匹配**，§5 给出形式化。

**约束**：

- $1 \le \text{text.length} \le 10^5$
- 字符串可能包含 256 个 ASCII 字符中的任意字符

## 2. 示例

**示例 1**

```text
输入：text = "&amp; is an HTML entity but &ambassador; is not."
输出："& is an HTML entity but &ambassador; is not."
解释：&amp; 替换为 &；&ambassador; 不是 6 种实体之一，原样保留。
```

**示例 2**

```text
输入：text = "and I quote: &quot;...&quot;"
输出："and I quote: \"...\""
```

**示例 3**

```text
输入：text = "x &gt; y &amp;&amp; x &lt; y is always false"
输出："x > y && x < y is always false"
解释：三处实体各自独立替换，连续两个 &amp; 输出两个 &。
```

**补充用例（陷阱自检）**

```text
输入：text = "&amp;gt;"
输出："&gt;"
解释：&amp; 命中，产物 & 直接写入结果；随后的 gt; 是普通文本，原样输出。
若输出 ">"，说明替换产物被二次扫描——见 §3.1 的顺序陷阱。
```

## 3. 解题思路

### 3.1 暴力思路：链式 str.replace——能过，但踩着一个顺序陷阱

最直观的做法是对 6 种实体逐一调用全局替换：

```python
class Solution:
    def entityParser(self, text: str) -> str:
        return (text.replace("&quot;", '"').replace("&apos;", "'")
                    .replace("&gt;", ">").replace("&lt;", "<")
                    .replace("&frasl;", "/").replace("&amp;", "&"))
```

6 趟 × 每趟 $O(n)$，共 $O(6n)$，本题 $n \le 10^5$ 稳过。**但这版代码的正确性悬在一根头发丝上**：`&amp;` 必须放在**最后**。若把它挪到前面：

```text
text = "&amp;quot;"
第 1 趟 replace("&amp;", "&")  →  "&quot;"     ← 新生了一个 & ！
第 2 趟 replace("&quot;", "\"") →  "\""          ← 被误替换
而正确答案是 "&quot;"（& 来自 &amp;，quot; 是普通文本）
```

> ⚠️ 根源：链式 replace 的每一趟都会**重扫上一趟的产物**。`&amp;` 的产物 `&` 恰好是所有实体的**起始符**，新生的 `&` 与后续文本拼成伪实体，被后续趟次误消费。`&amp;` 垫底只是"此后再无趟次"的特解——实体表一旦扩展（如产物含 `&` 的自定义实体），链式替换立刻失效。赛时若不想论证顺序，直接写 §3.2 的单趟扫描最稳。

### 3.2 核心观察：单趟扫描——替换产物永不回扫

![核心观察：链式replace的顺序陷阱与单趟扫描的产物不回扫](images/wc184_q3_trap_concept.svg)

三个环环相扣的观察：

1. **`&` 是唯一的实体起点**。6 种实体全部以 `&` 开头，扫描时只有遇到 `&` 才需要做实体判定，其余字符一律走 $O(1)$ 快路径直接输出。
2. **产物不回扫**。`&amp;` → `&` 会产生新的 `&`，这是链式 replace 翻车的根源。单趟扫描让指针 $i$ **只进不退**：命中实体后输出映射字符、$i$ 一步跳过整个实体；替换产物只追加进结果串 `res`，**从不回到扫描窗口**——从结构上杜绝二次替换，正确性不依赖任何替换顺序。
3. **实体短且有界，判定可 O(1) 定音**。6 种实体长度 $4 \sim 7$、互不为前缀、内部（除末位）不含 `;`。于是位置 $i$ 至多一个实体匹配，且判定只需看窗口 $[i, i+7)$ 内的**首个** `;`——取出 `text[i..s]` 查一次哈希表即可（§5 引理 1、2 严格化）。

| 方案 | `&amp;quot;` 的处理 | 结果 | 正确？ |
|------|---------------------|------|--------|
| 链式 replace（`&amp;` 先） | `&quot;` → `"` | `"` | ✗ |
| 单趟扫描 | 匹配 `&amp;` → 输出 `&`、跳到 `quot;` 原样输出 | `&quot;` | ✓ |

### 3.3 算法流程：遇 `&` 开窗找 `;`，查表定去留

![算法流程：单趟扫描加窗口找分号加哈希查表](images/wc184_q3_scan_flow.svg)

1. **初始化**：哈希表 `ents = {实体 → 字符}` 共 6 条；`res = []`，`i = 0`。
2. **循环**直到 `i == n`：
   - 若 `text[i] != '&'`：`res.append(text[i])`，`i += 1`（快路径）；
   - 若 `text[i] == '&'`：在 $[i+1,\ i+7)$ 内找**首个** `;`，记下标 `semi`；
     - **找到**且 `text[i..semi]` 在 `ents` 中：`res.append(ents[ent])`，`i = semi + 1`（**跳过整个实体**）；
     - 否则：`res.append('&')`，`i += 1`（`&` 按普通字符处理）。
3. 返回 `''.join(res)`。

> 💡 **为何窗口限 $i+7$？** 最长实体 `&frasl;` 长 7，合法实体的 `;` 最远在 $i+6$。限窗一举两得：① 每个 `&` 至多比较 7 个字符，保证 $O(n)$；② 天然把 `;` 更远的伪实体（如 `&ambassador;` 的 `;` 在 $i+11$）挡在门外——由引理 2，窗口内判否与"无实体匹配"等价，不是近似而是精确。

### 3.4 示例演算

以示例 1 为例，重点看两种关键情形：**命中实体跳整段**与**伪实体判否只 +1**。

![示例演算：amp命中跳五格与ambassador伪实体窗口内无分号判否](images/wc184_q3_walkthrough.svg)

| 步骤 | $i$ | 输入片段 | 判定 | 输出 | $i$ 跳到 |
|------|-----|----------|------|------|----------|
| 1 | 0 | `&amp;` | 窗口内首个 `;` 在 $i+4$，`&amp;` 在表中 | `&` | 5 |
| 2 | 5–27 | `" is an HTML entity but "` | 无 `&`，快路径 | 原样 | 28 |
| 3 | 28 | `&` | 窗口 $[29, 35)$ 内无 `;`（`;` 在 $i+11$） | `&` | 29 |
| 4 | 29–47 | `ambassador; is not.` | 无 `&` | 原样 | 结束 |

拼接输出 `"& is an HTML entity but &ambassador; is not."` ✓。注意步骤 1 与步骤 3 的对比：同样是 `&` 开头，命中时 $i$ 一次跳 5 格、整段消费；判否时 $i$ 只 +1，`&ambassador;` 十二个字符全部原样保留。

## 4. 算法细节

1. **实体表建哈希**：`unordered_map<string, char>` / `dict`，键为实体全文，单次查询 $O(1)$（键长 $\le 7$）。等价写法是 `vector<pair<string, char>>` 逐一 `compare`——每次至多 $6 \times 7$ 次字符比较，同为常数，任选。
2. **从 $i+1$ 起找 `;`**：`text[i]` 是 `&` 本身；6 种实体除末位外均不含 `;`，故窗口内**首个** `;` 就是唯一候选终点——首个不命中即整段判否，不需要尝试更远的 `;`（引理 2）。
3. **命中后 `i = semi + 1`**：一步跨过整个实体。这是"跳过整段、产物不回扫"的代码形态；漏写成 `i += 1` 会把实体的剩余字符（如 `amp;`）再扫一遍，虽不致错但白做功，且窗口判定会重复失败。
4. **C++ 越界防护**：窗口右端取 `min(i + 7, n)`，`substr(i, semi - i + 1)` 只在 `semi` 命中界内后执行。
5. **结果容器**：Python 用 `list` + `join`——字符串不可变，`res += c` 每次整体复制是 $O(n^2)$；C++ 的 `string::operator+=` 均摊 $O(1)$，可 `reserve(n)` 进一步减少扩容。
6. **快路径优先**：先判 `text[i] == '&'` 再开窗，普通字符零额外开销；全文无 `&` 时算法退化为一次线性拷贝（`Stay home!` 型纯文本即此情形）。

## 5. 正确性证明

**规范语义**：从左到右扫描原文。位置 $i$ 处若有实体匹配（由引理 1 知至多一个），则输出其对应字符、扫描跳到实体之后；否则输出单字符 $\text{text}[i]$、$i$ 前进 1。解析结果为所有输出字符的拼接。**替换产物只追加进结果串，永不回到扫描窗口**——这是"每个实体恰好替换一次"的形式化，补充用例 `&amp;gt;` → `&gt;` 印证。

**引理 1（唯一性与不重叠性）**：任意两个实体命中段要么相同、要么不相交；从而每个位置至多一个实体匹配。

**证明**：逐字检验 6 种实体：除首字符外均不含 `&`。设命中段 $[i, i+L_1)$ 与 $[j, j+L_2)$ 相交且 $i \le j < i + L_1$，即较晚的起点 `&` 落在较早段**内部**——而段内唯一的 `&` 是较早实体的首字符，故 $j = i$。于是两个实体在**同一位置**匹配，较短者必为较长者的前缀；但 6 种实体的第二字符 `q, a, a, g, l, f` 中仅 `&apos;`/`&amp;` 同为 `a` 且第三字符 `p ≠ m`，其余两两互异，任何两个实体在前 3 个字符内必现分歧，无前缀关系，矛盾。∎

**引理 2（窗口判定）**：设 $\text{text}[i] = \&$，则 $i$ 处有实体匹配 $\iff$ $[i+1,\ i+7)$ 内存在 `;`，且记 $s$ 为其中**首个** `;` 时，$\text{text}[i..s]$ 在实体表中。

**证明**：(⇒) 实体长 $4 \sim 7$，其终止 `;` 位于 $i+3 \sim i+6 \subseteq [i+1, i+7)$；实体除末位外不含 `;`，故该 `;` 即区间内首个 `;`，且整个实体恰为 $\text{text}[i..s]$。(⇐) 若 $\text{text}[i..s]$ 在表中，则它本身就是在 $i$ 处匹配的实体。∎

**定理（单趟扫描正确性）**：算法输出等于规范语义的解析结果。

**证明**：对扫描位置 $i$ 强归纳。算法每步恰三选一，且均与规范一致：

- 非 `&`：输出单字符，$i{+}{=}1$；
- `&` 且引理 2 条件成立：由引理 1 匹配唯一，输出映射字符、$i \leftarrow s+1$——原文区间 $[i, s]$ 恰被消费一次；
- `&` 但条件不成立：由引理 2 的逆否，$i$ 处无任何实体匹配，输出 `&`、$i{+}{=}1$。

三种情况消费的原文区间两两不相交（引理 1）且并集为 $[0, n)$——每个位置被消费恰一次。又算法只读原文、只追加 `res`，产物不进入任何后续判定，二次替换无从发生。归纳得输出与规范逐字符相同。∎

**推论（链式 replace 的正确顺序）**：先替换 5 种产物不含 `&` 的实体、最后替换 `&amp;`，结果与单趟扫描一致。

**证明**：将原文划分为互不重叠的命中段与未命中段（引理 1 保证划分良定义）。`&amp;` 的命中段与其他实体的命中段不相交（引理 1），故前 5 趟不触碰它们；5 种替换产物 `" ' > < /` 都不是 `&amp;` 的组成字符，跨段拼出新 `&amp;` 不可能——中间串中的 `&amp;` 恰是原文未命中段里的那些。最后一趟将其全部替换为 `&`，此后再无趟次，新生的 `&` 不会被消费。∎

> 💡 推论解释了 §3.1 那行"头发丝代码"为何能过，也划定了它的边界：一旦实体表扩展出产物含 `&` 的条目，"垫底"技巧失效，单趟扫描是唯一普适解。

## 6. 复杂度分析

- **时间复杂度**：$O(n)$。指针 $i$ 单调前进，每个字符至多被消费一次；每次遇到 `&` 至多在窗口内比较 7 个字符 + 一次 $O(1)$ 哈希查询，合计 $O(7n) = O(n)$。链式 replace 为 $O(6n)$，同为线性但常数约 6 倍且依赖顺序。
- **空间复杂度**：$O(n)$，即结果串 `res`。哈希表仅 $6$ 条、键长 $\le 7$，为 $O(1)$。
- **下界对照**：输出长度可达 $n$（无实体时原样拷贝），任何算法都需 $\Omega(n)$，故单趟扫描已是最优。

## 7. 参考代码

### C++

```cpp
class Solution {
public:
    string entityParser(string text) {
        unordered_map<string, char> ents = {
            {"&quot;", '"'}, {"&apos;", '\''}, {"&amp;", '&'},
            {"&gt;", '>'},   {"&lt;", '<'},    {"&frasl;", '/'}
        };
        int n = text.size();
        string res;
        res.reserve(n);
        for (int i = 0; i < n; ) {
            if (text[i] == '&') {
                int lim = min(i + 7, n);
                int semi = -1;
                for (int j = i + 1; j < lim; ++j)
                    if (text[j] == ';') { semi = j; break; }
                if (semi != -1) {
                    auto it = ents.find(text.substr(i, semi - i + 1));
                    if (it != ents.end()) {
                        res += it->second;
                        i = semi + 1;
                        continue;
                    }
                }
            }
            res += text[i++];
        }
        return res;
    }
};
```

### Python

```python
class Solution:
    def entityParser(self, text: str) -> str:
        ents = {
            "&quot;": '"', "&apos;": "'", "&amp;": "&",
            "&gt;": ">", "&lt;": "<", "&frasl;": "/",
        }
        res = []
        i, n = 0, len(text)
        while i < n:
            if text[i] == '&':
                semi = text.find(';', i, i + 7)
                if semi != -1:
                    ent = text[i:semi + 1]
                    if ent in ents:
                        res.append(ents[ent])
                        i = semi + 1
                        continue
            res.append(text[i])
            i += 1
        return ''.join(res)
```

> 💡 赛时策略：Python 直接交 §3.1 的链式 replace（`&amp;` 垫底）最省时；C++ 无现成链式 replace 一行流，写本节单趟版反而更短。两版对拍 `&amp;gt;`、`&ambassador;` 两类用例即可互验。

## 8. 边界情况与易错点

1. **顺序陷阱（最常见 WA 点）**：链式 replace 把 `&amp;` 放前面，`&amp;quot;` → `&quot;` → `"` ✗。要么 `&amp;` 垫底（推论），要么直接单趟扫描。
2. **窗口必须限界**：`text.find(';', i)` 不带上界（Python/C++ 同理）在 `&&&…&;`（$10^5$ 个 `&` 加末尾一个 `;`）上，每个 `&` 都扫到串尾，退化为 $O(n^2)$ 超时。务必写 `find(';', i, i + 7)` / `min(i + 7, n)`。
3. **产物不回扫自检**：`&amp;gt;` 的正确输出是 `&gt;` 而非 `>`，`&amp;amp;` 的正确输出是 `&amp;`——调试时先跑这两个用例。
4. **伪实体原样保留**：`&ambassador;`（`;` 在窗外）、`&gt`（无 `;`）、`&x;`（不在表中）——判否后 `&` 按普通字符输出、$i$ 只 +1，后续字符自然原样，**无需任何特判**。
5. **首个 `;` 即唯一候选**：不要在窗口内收集多个 `;` 逐一尝试——实体内部无 `;`，首个不命中即整段判否（引理 2）。
6. **Python 拼接**：`res += c` 是 $O(n^2)$，必须 `list` + `join`；C++ `string +=` 均摊 $O(1)$，无此问题。
7. **C++ 转义**：`'\''` 与 `'"'` 书写易错；`substr` 前确认 `semi` 在 `min(i+7, n)` 界内，防越界。
8. **退化输入**：全文无 `&`（如 `Stay home! Practice on Leetcode :)`）走快路径线性拷贝；单字符输入、$n = 1$ 同样无需特判。
