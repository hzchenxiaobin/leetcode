# LeetCode 设计地铁系统 题解

## 1. 题目概述

- **标题 / 题号**：设计地铁系统（#1396，medium）
- **链接**：https://leetcode.cn/problems/design-underground-system/
- **来源**：LeetCode 第 182 场周赛 Q3
- **难度**：中等
- **标签**：设计、哈希表、字符串

**题意**：实现 `UndergroundSystem` 类，跟踪乘客在不同车站之间的出行时间，并随时查询任意两站之间的**平均**行程用时：

- `checkIn(id, stationName, t)`：卡号 `id` 的乘客在时刻 `t` 从 `stationName` 进站；
- `checkOut(id, stationName, t)`：卡号 `id` 的乘客在时刻 `t` 从 `stationName` 出站；
- `getAverageTime(startStation, endStation)`：返回**截至目前**所有从 `startStation` **直接**到 `endStation` 的行程的平均用时。

统计按**方向**进行——A→B 与 B→A 是两组互不相干的行程。调用序列保证逻辑自洽：出站必有对应进站、乘客在途时不会二次进站、查询的站对至少已有一条行程。

**约束**：

- $1 \le \text{id}, t \le 10^6$
- $1 \le \text{stationName.length} \le 10$，站名仅含大小写字母与数字
- `checkIn` / `checkOut` / `getAverageTime` 总调用次数 $\le 2 \times 10^4$
- 与标准答案误差在 $10^{-5}$ 以内视为正确

> 💡 从约束读档位：调用总量只有 $2 \times 10^4$，但「先攒 $10^4$ 条行程、再查询 $10^4$ 次」的最坏组合会把逐条遍历的暴力推到 $10^8$ 次操作——C++ 卡边缘、Python 必超时。站名长度 $\le 10$ 则暗示**站对键怎么拼都便宜**：两个站名拼起来至多 21 个字符，哈希开销近似常数。两条约束合起来正好圈出正解形态：**两张哈希表 + 增量聚合，三个方法全 $O(1)$**。

## 3. 解题思路

### 3.1 暴力思路：行程明细逐条存，查询时现算均值

用一个列表存下每条已完成行程 `(start, end, dt)`：`checkOut` 时 `append`，`getAverageTime` 时遍历全表，筛出起终站匹配的行程求和取均值。正确性没有问题，但 `getAverageTime` 单次 $O(T)$（$T$ 为历史行程总数），最坏 $10^4$ 次查询 × $10^4$ 条行程 ≈ $10^8$ 次操作，在超时边缘徘徊；更糟的是同一段 `(Leyton, Waterloo)` 的部分和被每次查询**重算一遍**。症结在**存储粒度太细**：查询要的是聚合量（均值），存的却是明细（每条行程）。

> ⚠️ 设计题的通用破局点：先看清「查询依赖多少信息」，再决定「写入时维护多少信息」。均值 $\bar{T} = \frac{\text{总时长}}{\text{行程数}}$ 只依赖**两个标量**——把它们在写入时顺手维护好，查询就退化成一次读表一次除法。这就是**聚合前置**。

### 3.2 核心观察：均值只吃两个标量——聚合前置，双表分工

![核心观察：双哈希表分离在途与累计，出站时折叠成增量](images/metro1396_two_tables_concept.svg)

一条行程的「一生」分两段：**进站后、出站前**只有起点和进站时刻（信息不完整，行程尚未成立）；**出站那一刻**行程闭合，可立刻算出用时并折算成站对统计量的增量。两段数据的生命周期截然不同，天然该分两张表：

| 表 | 键 → 值 | 生命周期 | 职责 |
|----|---------|----------|------|
| `checkIns` | `id → (起点站, 进站时刻)` | **临时**——出站即删 | 拼合一条行程的两个半边 |
| `travelTimes` | `(起点, 终点) → (总时长, 行程数)` | **永久**——持续累加 | 供均值查询的两个标量 |

- `checkIn`：往 `checkIns` 写一条，$O(1)$；
- `checkOut`：从 `checkIns` 取出起点与 $t_{\text{in}}$，算 $dt = t - t_{\text{in}}$，对 `travelTimes[(起点, 终点)]` 执行 `(总时长 \mathrel{+}= dt,\ 行程数 \mathrel{+}= 1)`，再删掉在途记录——四步全是哈希操作，$O(1)$；
- `getAverageTime`：读 `travelTimes[(s, e)]` 的两个标量，一次除法，$O(1)$。

> ⚠️ **键是有序站对**：`(A, B)` 与 `(B, A)` 是两个不同的键——题面明说两个方向的平均时间可能不同（自拟示例 3）。用无向对或排序后的站对做键，会把两组统计错误地混在一起，这是本题最容易踩的语义坑。

> 💡 为什么敢在出站时立刻累加、不留明细？因为均值是 $\sum_i d_i / n$ 的函数，$\big(\sum_i d_i,\ n\big)$ 这对合计值是**充分统计量**——此后无论再发生多少次查询与新行程，明细本身再无任何用途。存明细等于花 $O(T)$ 空间买一份用不上的信息。

### 3.3 算法流程：三个方法各 O(1)，出站是四步流水线

![算法流程：checkIn 一写、checkOut 四步流水线、getAverageTime 一读一除](images/metro1396_checkout_flow.svg)

```text
checkIn(id, stationName, t):
    checkIns[id] = (stationName, t)                  # 一次哈希写入

checkOut(id, stationName, t):
    (start, tIn) ← checkIns[id]                      # ① 查在途（先读）
    key ← (start, stationName)                       # ② 组有序站对键
    travelTimes[key].total += t − tIn                # ③ 增量累加（缺省 (0,0)）
    travelTimes[key].count += 1
    delete checkIns[id]                              # ④ 删在途（后删）

getAverageTime(startStation, endStation):
    (total, cnt) ← travelTimes[(startStation, endStation)]
    return total / cnt                               # 一次除法
```

四步中唯一**不能换位**的是「①读」与「④删」：必须先取值后删除，否则在途信息丢失（C++ 里若先把引用绑定到 `checkIns[id]` 再 `erase`，还会产生悬垂引用）。②③④之间的相对顺序自由。

### 3.4 示例演算

![示例演算：两张表随示例 1 操作序列逐步演化](images/metro1396_walkthrough.svg)

对示例 1 逐步追踪两张表（L = Leyton，W = Waterloo，P = Paradise，C = Cambridge）：

| # | 操作 | checkIns（在途） | travelTimes（累计） | 返回 |
|---|------|------------------|---------------------|------|
| 1 | `checkIn` 45 / 32 / 27 号 | {45:(L,3), 32:(P,8), 27:(L,10)} | 空 | — |
| 2 | `checkOut(45,W,15)`，dt = 12 | 删 45 | (L,W) = (12, 1) | — |
| 3 | `checkOut(27,W,20)`，dt = 10 | 删 27 | (L,W) = (22, 2) | — |
| 4 | `checkOut(32,C,22)`，dt = 14 | 删 32，表空 | (P,C) = (14, 1) | — |
| 5 | `getAvg(P, C)` | — | 读 (14, 1) | **14.0** |
| 6 | `getAvg(L, W)` | — | 读 (22, 2)，22/2 | **11.0** |
| 7 | `checkIn(10,L,24)`；`getAvg(L, W)` | +10:(L,24) | 不变（10 号在途，行程未闭合） | **11.0** |
| 8 | `checkOut(10,W,38)`，dt = 14 | 删 10 | (L,W) = (36, 3) | — |
| 9 | `getAvg(L, W)` | — | 读 (36, 3)，36/3 | **12.0** |

三个关键瞬间：**第 4 步**之后在途表清空——历史行程全部折叠进累计表的两个条目里，明细一条不留；**第 7 步**查询发生在 10 号乘客在途时——在途信息不进累计表，均值仍是 11.0，正确体现「行程闭合才入账」；**第 9 步** (L,W) 已累到 (36, 3)，`36/3 = 12` 与示例输出一致。

## 4. 算法细节

1. **站对键的表示**：C++ 的 `unordered_map` 不认 `pair<string, string>`（须手写 `std::hash` 特化，冗长易错），最省事的是 `start + "," + end` 拼字符串——站名仅含字母数字，逗号**必然不出现在站名内**，拼接无歧义；站名 $\le 10$，键长 $\le 21$。Python 直接用元组 `(start, end)` 作键，天然可哈希。
2. **值类型**：累计表的时长用 `long long`——上界 $2 \times 10^4 \times 10^6 = 2 \times 10^{10}$，超出 32 位 `int`（$\approx 2.1 \times 10^9$）近十倍；次数用 `int` 足够（$\le 2 \times 10^4$）。
3. **缺省语义**：C++ `travelTimes[key]` 在键不存在时默认构造 `(0, 0)`，`operator[]` + 原地 `+=` 一气呵成；Python 用 `setdefault((s, e), [0, 0])` 或 `dict.get` 显式兜底，直接下标取不存在的键会 `KeyError`。
4. **读取与删除的顺序**：`checkOut` 里先从 `checkIns[id]` **取值**（拷贝），再 `erase` / `pop`。C++ 里若写 `auto &[s, t] = checkIns[id];` 绑引用后 `erase(id)` 再使用引用，是悬垂引用（未定义行为）——structured bindings 写成值拷贝 `auto [s, t] = ...` 才安全；Python 的 `pop` 一步完成读取 + 删除，最干净。
5. **精度策略**：整数累加、查询时一次除法——整个流程只在最后一步发生一次浮点舍入，误差远小于 $10^{-5}$。不要用「增量均值」$mean \mathrel{+}= (dt - mean) / cnt$：每步浮点舍入会累积，且白白把整数域换成浮点域。
6. **同卡号复用**：乘客出站后可携带同一 `id` 再次进站（自拟示例 4 的 7 号乘客）——`checkIns[id]` 直接覆盖写入即可；在途期间二次 `checkIn` 被题面排除，无需防御逻辑。

## 5. 正确性证明

对任意时刻 $t$（即已执行的操作前缀），设 $S_t(a, b)$ 为截至 $t$ 已**闭合**的 $a \to b$ 行程用时构成的多重集，$\mathcal{P}_t$ 为截至 $t$ 在途（已进站未出站）的乘客集合。对操作序列长度归纳，证明两张表各自维护的不变式。

**引理 1（在途表不变式）**：任意时刻，`checkIns` 的键集恰为 $\mathcal{P}_t$，且 `checkIns[id] = (s, \tau)` 当且仅当乘客 id 在时刻 $\tau$ 从站 $s$ 进站且尚未出站。

**证明**：归纳于已执行的操作数。初始两表皆空，命题成立。设某时刻命题成立：

- 执行 `checkIn(id, s, τ)`：题面保证 id 当前不在途（「一次只能从一个站进入」），故 $\mathcal{P}_{t+1} = \mathcal{P}_t \cup \{\text{id}\}$；程序执行 `checkIns[id] = (s, τ)`，恰新增该键且不影响其余条目。
- 执行 `checkOut(id, e, τ')`：题面保证 id 在途，由归纳假设 `checkIns[id] = (s, τ)` 且 $\tau < \tau'$；程序删除键 id，与 $\mathcal{P}_{t+1} = \mathcal{P}_t \setminus \{\text{id}\}$ 一致。
- `getAverageTime` 不改任何表。

归纳传递完成。∎

**引理 2（累计表不变式）**：任意时刻，对每个已出现过行程的站对 $(a, b)$：

$$\text{travelTimes}[(a,b)] = \Big( \sum_{d \in S_t(a,b)} d,\ \big| S_t(a,b) \big| \Big)$$

**证明**：归纳于已执行的操作数。初始 $S_0(a,b)$ 为空、表无该键，命题成立。唯一改变 $S$ 的操作是 `checkOut(id, b, τ')`：由引理 1，此刻 `checkIns[id] = (a, τ)`，即该行程为 $a \to b$、用时 $d = \tau' - \tau$，故 $S_{t+1}(a,b) = S_t(a,b) \uplus \{d\}$（多重集添一元素）；程序恰对该键执行 `total += d; cnt += 1`。`checkIn` 与 `getAverageTime` 不触碰 `travelTimes`，归纳传递完成。∎

**定理**：每次 `getAverageTime(a, b)` 返回 $\displaystyle \frac{\sum_{d \in S_t(a,b)} d}{\big| S_t(a,b) \big|}$，即题目所求的平均用时；且分母 $\ge 1$，无除零风险。

**证明**：题面保证调用前 $a \to b$ 至少有一条已闭合行程，故 $|S_t(a,b)| \ge 1$。由引理 2，表中 `(total, cnt)` 即 $\big(\sum_{d} d,\ |S_t(a,b)|\big)$，返回 `total / cnt` 即所求。∎

> 💡 **方向有序性落在哪**：$S_t(a,b)$ 与 $S_t(b,a)$ 是不同的多重集，对应 `travelTimes` 中两个不同的键——统计天然按方向分开，「A→B 与 B→A 可能不同」的题设被**键的结构**直接吸收，无需任何额外处理。

## 6. 复杂度分析

- **时间复杂度**：三个方法均为**均摊 $O(1)$**。`checkIn` 一次哈希写；`checkOut` 两次哈希读写 + 一次删除 + 一次键拼接（站名 $\le 10$，常数级）；`getAverageTime` 一次哈希读 + 一次除法。哈希表扩容偶发 $O(n)$ 重哈希，摊到每次插入仍为 $O(1)$。总代价 $O(Q)$，$Q \le 2 \times 10^4$。
- **空间复杂度**：$O(P + S)$。$P$ 为**当前在途**乘客数（出站即删，`checkIns` 不随历史行程数增长）；$S$ 为已出现行程的**不同站对数**，上界为车站数 $C$ 的平方 $C^2$，实际只存出现过的对。两张表都与总行程数 $T$ 无关——这正是「聚合前置」相对暴力存明细（$O(T)$ 空间）的核心优势。
- **横向对比**：暴力法 `getAverageTime` 单次 $O(T)$，最坏总代价 $O(Q \cdot T) \approx 10^8$ 次操作；本解三方法全 $O(1)$，总量级仅 $10^4$。

## 7. 参考代码

### C++

```cpp
class UndergroundSystem {
    unordered_map<int, pair<string, int>> checkIns;            // 在途：id → (起点, 进站时刻)
    unordered_map<string, pair<long long, int>> travelTimes;   // 累计：站对 → (总时长, 行程数)

  public:
    void checkIn(int id, string stationName, int t) {
        checkIns[id] = {std::move(stationName), t};
    }

    void checkOut(int id, string stationName, int t) {
        auto [start, tIn] = checkIns[id];                              // ① 拷贝读出在途信息
        checkIns.erase(id);                                            // ② 删除（必须在读取之后）
        auto &[total, cnt] = travelTimes[start + "," + stationName];   // ③ 缺省 (0, 0)
        total += t - tIn;                                              //    累加时长
        ++cnt;                                                         //    累加次数
    }

    double getAverageTime(string startStation, string endStation) {
        const auto &[total, cnt] = travelTimes[startStation + "," + endStation];
        return static_cast<double>(total) / cnt;                       // 整数累加，一次除法
    }
};
```

### Python

```python
class UndergroundSystem:
    def __init__(self):
        self.check_ins = {}   # 在途：id -> (起点, 进站时刻)
        self.travel = {}      # 累计：(起点, 终点) -> [总时长, 行程数]

    def checkIn(self, id: int, stationName: str, t: int) -> None:
        self.check_ins[id] = (stationName, t)

    def checkOut(self, id: int, stationName: str, t: int) -> None:
        start, t_in = self.check_ins.pop(id)                    # 读取 + 删除一步完成
        rec = self.travel.setdefault((start, stationName), [0, 0])
        rec[0] += t - t_in
        rec[1] += 1

    def getAverageTime(self, startStation: str, endStation: str) -> float:
        total, cnt = self.travel[(startStation, endStation)]
        return total / cnt
```

> 💡 两版的键与兜底策略不同：C++ 拼字符串（避开 `pair` 哈希特化），`operator[]` 自带 `(0,0)` 缺省；Python 用元组键 + `setdefault` 显式兜底。共同点是 `total` 走整数域（C++ `long long`，Python 任意精度），全程只在 `getAverageTime` 里发生唯一一次除法。

## 8. 边界情况与易错点

1. **总时长溢出**：$2 \times 10^4$ 条行程 × 单程上界 $10^6$ = $2 \times 10^{10}$，32 位 `int` 必爆——C++ 必须用 `long long`（Python 无此虑）。这是本题最经典的错误来源。
2. **站对是有序的**：`(A, B)` 与 `(B, A)` 必须分开统计。把键写成 `min + "," + max` 或无向集合，自拟示例 3 那种两方向时长不同的数据立刻出错。
3. **整数除法**：C++ 里两个整数相除是整除——必须 `static_cast<double>(total) / cnt`，直接写 `total / cnt` 会返回截断的整数，精度全失。
4. **先读后删**：`checkOut` 中对 `checkIns[id]` 的读取必须先于删除。C++ 里 `auto &ref = checkIns[id]; checkIns.erase(id);` 之后继续用 `ref` 是悬垂引用（未定义行为）；写 `auto [start, tIn] = checkIns[id]`（值拷贝）再删才安全。
5. **不要增量维护均值**：`mean += (dt - mean) / cnt` 每步一次浮点舍入，误差逐步累积；整数和 + 查询时一次除法，全程只有一次舍入，稳过 $10^{-5}$ 容差。
6. **同一卡号复用**：出站后同一 `id` 可再次 `checkIn`——在途表直接覆盖写入，不需要清理逻辑；在途期间二次进站被题面排除。若本地对拍脏数据想防御，`checkIn` 前加一句 `checkIns.count(id)` 检查即可。
7. **查询站对无行程**：题面保证 `getAverageTime` 的站对至少有一条行程，无除零风险；但若手滑把方向拼反（如 `(end, start)`），Python 的 `dict[...]` 会直接 `KeyError`——这是方向写错时最快的报错信号。
8. **初始化**：C++ 成员哈希表默认构造即空，无需显式初始化；Python 必须写 `__init__` 建两张表。LeetCode 会为每个测试用例重新构造对象，状态不会串场。
