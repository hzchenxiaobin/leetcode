# LeetCode 处理含限制条件的好友请求 题解

## 1. 题目概述

- **标题 / 题号**：处理含限制条件的好友请求（#2076，hard）
- **链接**：https://leetcode.cn/problems/process-restricted-friend-requests/
- **来源**：LeetCode 第 267 场周赛 Q4
- **难度**：困难
- **标签**：并查集、图、连通性、在线算法

**题意**：网络上有 $n$ 个用户（编号 $0$ 到 $n-1$），初始时没有任何好友。给定限制列表 `restrictions`，其中 `restrictions[i] = [xi, yi]` 表示用户 $x_i$ 与 $y_i$ **不能成为好友**——不管是**直接**好友，还是经由其他用户**间接**相连的好友。再给定好友请求列表 `requests`，`requests[j] = [uj, vj]` 按顺序逐条处理：若 $u_j$ 与 $v_j$ **可以**成为好友（即成为好友后不违反任何限制），请求**成功**，二人成为**直接好友**并对后续请求持续生效；否则**失败**。返回布尔数组，标记每条请求是否成功。

**约束**：

- $2 \le n \le 1000$
- $0 \le \text{restrictions.length} \le 1000$，且 $x_i \ne y_i$
- $1 \le \text{requests.length} \le 1000$，且 $u_j \ne v_j$
- $0 \le x_i, y_i, u_j, v_j < n$

> 💡 **审题关键**：① 「不能成为好友，不管是直接还是间接」翻译成图语言：$x_i$ 与 $y_i$ **在任何时刻都不能处于同一个连通分量**；② 好友关系**只增不减**——成功的请求永久生效，分量只会合并、不会分裂，因此限制只需在**每条请求发生的当下**检查一次；③ 题目特别注明「已是直接好友仍成功」，暗示判定基准是**连通性**而非「直接边」——已间接好友的请求同样是空操作，必成功。

## 2. 示例

**示例 1（限制经由中间人间接生效）**

```text
输入：n = 3, restrictions = [[0,1]], requests = [[0,2],[2,1]]
输出：[true,false]
解释：请求 0：合并 {0}、{2} 不触碰限制 [0,1] → 成功。
      请求 1：2 已与 0 同分量，再连 1—2 会让 0、1 经 1—2—0
              间接连通 → 违反限制 → 拒绝。
```

**示例 2（请求相同、顺序不同，结果不同）**

```text
输入：n = 3, restrictions = [[0,1]], requests = [[1,2],[0,2]]
输出：[true,false]
解释：请求 0：合并 {1}、{2} → 成功。
      请求 1：0 与 2（已与 1 同分量）合并会让 0、1 经 0—2—1
              间接连通 → 拒绝。
      与示例 1 对比：两条请求内容完全一样，只是交换顺序，输出
      仍是 [true,false]，但被拒的是另一条——这是**在线**问题，
      成功的合并会改写后续判定，必须按序模拟。
```

**示例 3（本文走查用例）**

```text
输入：n = 5, restrictions = [[0,1],[1,2],[2,3]], requests = [[0,4],[1,2],[3,1],[3,4]]
输出：[true,false,true,false]
解释：请求 0：接受 → {0,4}。
      请求 1：[1,2] 本身就是限制 → 拒绝。
      请求 2：接受 → {1,3}（限制 [0,1] 的 0 端在 {0,4}，
              不在待合并的 {3}、{1} 任何一侧，不跨界）。
      请求 3：拒绝——合并 {1,3} 与 {0,4} 后，0 与 1 将经
              0—4—3—1 间接连通，违反限制 [0,1]。
```

## 3. 解题思路

### 3.1 暴力思路：每次请求后全图重查

把已接受的好友请求建成邻接表。处理请求 $(u,v)$ 时先加上边，再对**每条限制** $(x,y)$ 做一次 BFS/DFS 判断 $x$、$y$ 是否连通；发现违反则回滚该边并判为失败，否则保留。

- **复杂度**：每条请求要做 $K$ 次可达性查询（$K$ 为限制数），每次 $O(n+m)$，总计 $O\big(R \cdot K \cdot (n+m)\big)$。本题 $n, R, K \le 1000$ 时约 $10^9$ 量级，**超时**，且「加边—检查—回滚」的实现相当繁琐。
- **根因**：可达性被重复计算了太多遍。而一次成功合并对连通性的影响是**局部的、整块的**——完全值得增量维护，而不是每次从零 BFS。

另一个「半暴力」做法：用哈希集合直接维护每个朋友圈（连通分量为集合），请求时枚举限制查两端归属，成功时 $O(n)$ 合并两个集合。总量 $O\big(R(K+n)\big) \approx 2\times10^6$，本题规模能过；但合并开销大、实现琐碎，数据范围一旦放大立即失效。

### 3.2 核心观察：限制的语义是「两个分量不得合并」

![核心观察：一次合并波及 A×B](images/wc267_q4_merge_concept.svg)

**观察一（间接好友 = 同一连通分量）**：把用户看成节点、成功的好友请求看成无向边，则「直接或间接好友」恰是图的连通关系——$x$ 与 $y$ 是好友 ⟺ 二者同分量，即 $\text{find}(x) = \text{find}(y)$。

**观察二（合并的连锁效应）**：设请求 $(u,v)$ 中 $u$ 在分量 $A$、$v$ 在分量 $B$（$A \ne B$）。边 $(u,v)$ 一旦加入，**任意** $a \in A$ 与 $b \in B$ 都成为间接好友（路径 $a \cdots u\text{—}v \cdots b$），而 $A$、$B$ 内部以及它们与其余用户的连通关系**不变**。一次合并的波及面是整个 $A \times B$，与 $u,v$ 具体是谁无关。

**观察三（判据）**：结合观察二，请求 $(u,v)$ 能成功 ⟺ **没有任何限制 $(x,y)$ 恰好横跨 $A$、$B$ 两侧**——即不存在限制满足 $x \in A \wedge y \in B$ 或 $x \in B \wedge y \in A$。特殊地，若 $u,v$ 已同属一个分量，合并是空操作，必然成功（对应题目「已是好友仍成功」的说明）。

于是「每条限制 $O(n+m)$ 的可达性查询」被压缩成「$O(\alpha)$ 的根比较」——这正是并查集的主场：分量 = 并查集的等价类，若 $\text{find}(x) = \text{find}(u)$ 且 $\text{find}(y) = \text{find}(v)$（或对称），限制 $(x,y)$ 恰好横跨待合并的两侧，请求必须拒绝。

> 💡 **「只增不减」为什么重要**：好友边永不删除，分量只会合并、不会分裂，所以每条请求只需在当下做一次判定，不存在「先拒绝、后来又能接受」的反悔。若题目允许删除好友，并查集就不再适用，需要可撤销并查集（离线）或动态连通性结构（在线）。

### 3.3 算法流程

![单条请求的判定流程](images/wc267_q4_decide_flow.svg)

对每条请求 $(u, v)$ 依次执行：

| 步骤 | 操作 | 说明 |
|------|------|------|
| ① | $r_u = \text{find}(u)$，$r_v = \text{find}(v)$ | 各自所在分量的根 |
| ② | $r_u = r_v$？ | 同分量 ⇒ 已是好友，直接记 `true`，进入下一条 |
| ③ | 扫描每条限制 $(x,y)$：$a=\text{find}(x)$，$b=\text{find}(y)$ | 限制两端当前所在侧 |
| ④ | $a,b$ 恰跨 $r_u,r_v$ 两侧？ | $(a{=}r_u \wedge b{=}r_v) \vee (a{=}r_v \wedge b{=}r_u)$ |
| ⑤ | 有跨界限制 → `false`；否则 `true` 并 `union(r_u, r_v)` | 拒绝则状态不变 |

### 3.4 示例演算

![示例 3 逐步走查](images/wc267_q4_walkthrough.svg)

以示例 3 走查（限制 $(0,1),(1,2),(2,3)$）：

| 请求 | 待合并两侧 | 跨界限制？ | 结果 | 处理后分量 |
|------|-----------|-----------|------|-----------|
| $(0,4)$ | $\{0\},\{4\}$ | 无（三条限制都不横跨） | `true` | $\{0,4\},\{1\},\{2\},\{3\}$ |
| $(1,2)$ | $\{1\},\{2\}$ | 限制 $(1,2)$ 本身横跨 | `false` | 不变 |
| $(3,1)$ | $\{3\},\{1\}$ | 无（$0$ 在 $\{0,4\}$，不在两侧） | `true` | $\{0,4\},\{1,3\},\{2\}$ |
| $(3,4)$ | $\{1,3\},\{0,4\}$ | 限制 $(0,1)$：$0 \in \{0,4\}$、$1 \in \{1,3\}$ | `false` | 不变 |

最终 `result = [true, false, true, false]`。注意最后一行：请求写的是 $(3,4)$，限制写的是 $(0,1)$，表面上毫无交集——但 $3$ 已与 $1$ 同分量、$4$ 已与 $0$ 同分量，合并 $(3,4)$ 等价于打通 $\{0,4\}$ 与 $\{1,3\}$，于是 $0$、$1$ 经 $0—4—3—1$ 间接连通。这正是观察二「连锁效应」的具象，也是本题最容易看漏的拒绝场景。

## 4. 算法细节

1. **限制只需在请求时刻检查一次**：好友只增不减 ⇒ 分量只合不分。第 5 节引理 3 证明：只要每次合并前确认无跨界限制，全程不会有任何限制对落入同分量。
2. **比较的是根，不是编号**：四元判定全部用 `find` 的结果。示例 1 的请求 $(2,1)$ 里，与 $0$ 同分量的 $2$ 必须先 `find` 回根再比——直接拿 $x,y$ 与 $u,v$ 的**编号**比是最高频错误。
3. **同分量短路必须显式写出**：若漏掉步骤②直接进入扫描，四元比较在 $r_u = r_v$ 时恰好恒为假、结果碰巧仍是 `true`；但后续 `sz[ru] += sz[rv]` 会把同一分量的大小**翻倍**，按大小合并的元数据从此失真——「结果对、状态坏」极难排查。
4. **判定的集合写法**：由引理 3 的不变式，限制两端永远异侧（$a \ne b$），故四元比较可简写为 $\{a,b\} = \{r_u,r_v\}$。竞赛中更短，但显式写法不依赖不变式、更稳。
5. **并查集实现**：路径压缩 + 按大小合并即可；$n \le 1000$ 的规模下即便只写路径压缩也绰绰有余。
6. **每条请求都扫全部限制**：$R \times K \le 10^6$ 次根比较，毫无压力。数据范围放大到 $10^5$ 时的优化见「相关题目与扩展」。

## 5. 正确性证明

记某时刻已接受请求构成无向图 $F$，并查集维护 $F$ 的连通分量。

**引理 1（分量对应）**：任意时刻，用户 $p,q$ 是好友（直接或间接）⟺ $p,q$ 在 $F$ 中连通 ⟺ $\text{find}(p) = \text{find}(q)$。

**证明**：对已处理请求数 $t$ 归纳。$t=0$ 时无边，人人孤立，命题成立。设 $t$ 时成立，第 $t{+}1$ 条请求 $(u,v)$：被拒绝则 $F$ 不变；被接受则 $F \gets F \cup \{(u,v)\}$，且算法恰在 $r_u \ne r_v$ 时执行 `union`——并查集等价类与图连通分量同步变化。两种情形下归纳均保持。∎

**引理 2（合并的封闭性）**：设 $A \ne B$ 为两个分量，$u \in A$、$v \in B$。加入边 $(u,v)$ 后，新增的好友对恰为 $A \times B$，其余任何点对的连通关系不变。

**证明**：$A$、$B$ 是连通分量，故 $F$ 中**没有任何边**跨越 $A$ 与其补集（否则该补集端点应属于 $A$），$B$ 同理。于是 $F \cup \{(u,v)\}$ 中从 $A \cup B$ 之外的点出发的任何路径都不可能进入 $A \cup B$（唯一新边 $(u,v)$ 两端都在 $A \cup B$ 内），外部点对的连通性不变。$A \cup B$ 内部：任取 $a \in A, b \in B$，$a$ 与 $u$ 在 $A$ 内连通、$v$ 与 $b$ 在 $B$ 内连通，拼接新边得 $a$ 到 $b$ 的路径；而 $A$ 内（或 $B$ 内）任意两点在 $F$ 中本已连通。故新增连通对恰为 $A \times B$。∎

**引理 3（不变式与判据等价）**：记不变式 $\mathcal{I}$：「每条限制 $(x,y)$ 的两端处于不同分量」。只要算法仅在「无跨界限制」时合并，$\mathcal{I}$ 全程保持；且请求 $(u,v)$（$r_u \ne r_v$）可以成功（即 $F \cup \{(u,v)\}$ 不违反任何限制）⟺ 没有限制横跨 $A \times B$。

**证明**：$\mathcal{I}$ 初始成立（无边，而限制两端点不同）。归纳保持：若请求被接受，扫描已确认无限制横跨 $A,B$，由引理 2 新增好友对恰为 $A \times B$ 且不含限制对；若被拒绝或同分量短路，$F$ 不变。
判据：（⇒）若限制 $(x,y)$ 横跨（不妨 $x \in A, y \in B$），接受后 $x,y$ 同分量成为间接好友，违反限制，必须拒绝。（⇐）若无横跨限制，由引理 2，接受后新增好友对仅 $A \times B$，其中无限制对；其余限制对本就异侧（$\mathcal{I}$）且不受本次影响。故接受合法。∎

**定理（主定理）**：算法输出的布尔数组与题目定义的真实处理结果一致。

**证明**：题目对每条请求的结果是**被唯一决定**的：若 $r_u = r_v$，$u,v$ 已是好友（引理 1），成功且图不变；否则由引理 3，成功 ⟺ 无跨界限制，成功时图恰好增加边 $(u,v)$、失败时不变。对请求序号归纳：算法每一步的判定与状态更新均与真实过程一致，故输出一致。∎

## 6. 复杂度分析

- **时间复杂度**：$O\big((R \cdot K + K)\,\alpha(n)\big) \approx O(R K \alpha(n))$。每条请求至多扫描 $K$ 条限制，每条限制 2 次 `find`，单次 `find` 为路径压缩下的均摊近常数；$R, K \le 1000$ ⇒ 至多约 $2 \times 10^6$ 次根查找，毫秒级。
- **空间复杂度**：$O(n)$。并查集的 `fa` 与 `sz` 数组；限制与请求为只读输入，不计入。

## 7. 参考代码

### C++

```cpp
class Solution {
    vector<int> fa, sz;

    int find(int x) {
        while (fa[x] != x) {
            fa[x] = fa[fa[x]];       // 路径压缩（隔代跳跃）
            x = fa[x];
        }
        return x;
    }

public:
    vector<bool> friendRequests(int n, vector<vector<int>>& restrictions,
                                vector<vector<int>>& requests) {
        fa.resize(n);
        iota(fa.begin(), fa.end(), 0);
        sz.assign(n, 1);

        vector<bool> res;
        res.reserve(requests.size());
        for (auto& q : requests) {
            int ru = find(q[0]), rv = find(q[1]);
            if (ru == rv) {                  // 已是好友（直接或间接）→ 必成功
                res.push_back(true);
                continue;
            }
            bool ok = true;
            for (auto& r : restrictions) {   // 是否有限制恰跨 ru、rv 两侧
                int a = find(r[0]), b = find(r[1]);
                if ((a == ru && b == rv) || (a == rv && b == ru)) {
                    ok = false;              // 合并会让 a、b 成为间接好友
                    break;
                }
            }
            res.push_back(ok);
            if (ok) {                        // 按大小合并
                if (sz[ru] < sz[rv]) swap(ru, rv);
                fa[rv] = ru;
                sz[ru] += sz[rv];
            }
        }
        return res;
    }
};
```

### Python

```python
class Solution:
    def friendRequests(self, n: int, restrictions: List[List[int]],
                       requests: List[List[int]]) -> List[bool]:
        fa = list(range(n))
        sz = [1] * n

        def find(x: int) -> int:
            while fa[x] != x:
                fa[x] = fa[fa[x]]        # 路径压缩（隔代跳跃）
                x = fa[x]
            return x

        res = []
        for u, v in requests:
            ru, rv = find(u), find(v)
            if ru == rv:                 # 已是好友（直接或间接）→ 必成功
                res.append(True)
                continue
            ok = True
            for x, y in restrictions:    # 是否有限制恰跨 ru、rv 两侧
                a, b = find(x), find(y)
                if (a == ru and b == rv) or (a == rv and b == ru):
                    ok = False           # 合并会让 a、b 成为间接好友
                    break
            res.append(ok)
            if ok:                       # 按大小合并
                if sz[ru] < sz[rv]:
                    ru, rv = rv, ru
                fa[rv] = ru
                sz[ru] += sz[rv]
        return res
```

## 8. 边界情况与易错点

1. **拿原始编号而非根做比较**：示例 1 的请求 $(2,1)$ 中，与 $0$ 同分量的 $2$ 若不先 `find`，会误判「限制 [0,1] 与请求无关」而错误接受。四次比较必须全部针对根。
2. **漏掉同分量短路**：除了白扫一遍限制，还会让 `sz` 翻倍污染按大小合并的元数据（见 §4 第 3 点），隐蔽且难查。
3. **「已是间接好友」也要返回 `true`**：题目只明说了直接好友，但同分量（间接好友）时连「成为好友」这个动作都是空操作，同样成功。
4. **限制与请求重合**：示例 3 的请求 $(1,2)$ 与限制 $[1,2]$ 完全相同，判定流程自然拒绝，无需特判；限制列表中重复给出的限制对亦幂等。
5. **限制列表为空**：内层扫描空转，所有请求成功——代码天然兼容，不要为此加分支。
6. **顺序敏感**：示例 1 与示例 2 说明同样的请求换个顺序、被拒的就是另一条。必须在线处理，不能离线排序或倒推。
7. **误用「逐对 BFS 判连通」**：见 §3.1，$O\big(RK(n+m)\big)$ 在极限数据下超时；并查集把单次判定降到 $O(\alpha)$。
8. **返回类型**：注意接口返回布尔数组（C++ `vector<bool>`、Python `List[bool]`），与题面逐一对应。

**延伸思考**：① 若 $n, R, K$ 放大到 $10^5$，逐请求扫全部限制的 $O(RK)$ 不再可接受——可为**每个分量根维护「禁止合并的根集合」**：初始把限制 $(x,y)$ 互相记入对方集合；请求 $(u,v)$ 只需查询 $\text{find}(v) \in \text{bad}[\text{find}(u)]$；合并时把小集合并入大集合，并把别处指向旧根的记录改指新根。每条限制最多迁移 $O(\log n)$ 次（小并大，所属集合每次至少翻倍），总量 $O\big((R + K\log n)\,\alpha(n)\big)$。② 若好友关系允许**删除**，连通性不再单调，在线并查集失效——需离线按操作序分治（可撤销并查集）或动态图连通性结构。③ 若限制弱化为「不能成为**直接**好友」（允许间接相连），判定退化为查重：请求成功 ⟺ $(u,v)$ 不在限制集合中，一个哈希集合即可。
