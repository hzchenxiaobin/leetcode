# LeetCode 宝石与石头 题解

## 1. 题目概述

- **标题 / 题号**：宝石与石头（#771，easy）
- **链接**：https://leetcode.cn/problems/jewels-and-stones/
- **来源**：LeetCode 第 69 场周赛 Q1
- **难度**：简单
- **标签**：哈希表，字符串

**题意**：`jewels` 给出的是**宝石的类型清单**（每个字符一种类型，**互不相同**），`stones` 给出的是你**手里所有石头**（每个字符一块石头，同类型可重复）。问：`stones` 中有多少块石头的类型出现在 `jewels` 里。字母**区分大小写**，`'a'` 与 `'A'` 是两种不同的石头。

一句话抽象：把 `jewels` 预处理成一个**类型集合**，然后对 `stones` 的每个字符做一次**成员查询**，统计命中的次数。

**约束**：

- $1 \le \lvert \text{jewels} \rvert,\ \lvert \text{stones} \rvert \le 50$
- `jewels` 与 `stones` 仅由英文字母组成
- `jewels` 中所有字符**互不相同**

> 💡 三条约束其实已经把答案写在脸上：字母表只有 $52$ 个字符，`jewels` 至多 $50$ 类，`stones` 至多 $50$ 块。于是**暴力也能过**，真正的分水岭在于「你沉淀的是哪种模板」——嵌套比较、哈希集合、还是用**一个 64 位整数当集合**。

## 2. 示例

**示例 1**

```text
输入：jewels = "aA", stones = "aAAbbbb"
输出：3
解释：stones 依次为 a, A, A, b, b, b, b
      a 是宝石（jewels 含 'a'）→ 计数 1
      A 是宝石（jewels 含 'A'）→ 计数 2
      A 是宝石              → 计数 3
      b 不是宝石（jewels 只有 'a' 和 'A'）→ 计数保持 3
```

**示例 2**

```text
输入：jewels = "z", stones = "ZZ"
输出：0
解释：'Z' 与 'z' 是两种类型，大小写敏感；jewels 只有小写 'z'，
      所以两块大写 Z 都不是宝石，答案为 0。
```

**补充边界**（非官方示例，用于校准大小写）

```text
输入：jewels = "a", stones = "AAAa"
输出：1
解释：三个大写 A 全部不算，只有末尾的小写 a 命中。
```

## 3. 解题思路

### 3.1 暴力思路

「照题意翻译」：对 `stones` 里每块石头，回头扫一遍 `jewels`，逐字符比较，相同就计入答案。

```text
for s in stones:
    for j in jewels:
        if s == j: ans += 1; break
```

复杂度 $O(\lvert \text{jewels} \rvert \cdot \lvert \text{stones} \rvert)$，本题上界 $50 \times 50 = 2500$ 次比较——**完全能过**，这也是官方 hint「For each stone, check if it is a jewel.」的字面意思。

它的问题不在速度，而在**模板不可扩展**：一旦 `jewels` 与 `stones` 都涨到 $10^5$ 规模（比如「逐个判断每个模式串是否是字典里的词」），嵌套比较立刻从 $2500$ 涨到 $10^{10}$。而本题真正的信息是「`jewels` 是**查询字典**、`stones` 是**查询序列**」，字典可以**预处理一次、反复使用**——这才是值得沉淀的那一步。

### 3.2 核心观察：把「类型清单」压成一张 64 位类型表

![宝石类型集合 → 一个 64 位整数的类型表](images/wc69_q1_type_mask_model.svg)

**观察一（问题结构）**：本题是 $\lvert \text{stones} \rvert$ 次**独立的成员查询**，每次查询只问「字符 $s$ 在不在 `jewels` 里」。嵌套比较之所以慢，是因为每次查询都重新扫了一遍字典。

**观察二（值域极小）**：`jewels` 只含英文字母，字母表一共 $26 + 26 = 52$ 个字符。集合里可能的元素**不超过 52 种**，一个 $64$ 位整数的位宽就装得下——于是「集合」不必是哈希表，可以是**一个整数**。

**观察三（位号必须分段）**：要让大小写天然不撞位，给两类字母分配互不重叠的位段：

$$\mathrm{bit}(c)=\begin{cases} c-\text{'a'}, & c \text{ 是小写字母（落在第 } 0 \sim 25 \text{ 位）}\\ c-\text{'A'}+26, & c \text{ 是大写字母（落在第 } 26 \sim 51 \text{ 位）}\end{cases}$$

有了位号，建表与查询都变成**一条位运算**：

$$\text{mask}=\bigvee_{c\,\in\,\text{jewels}} 2^{\mathrm{bit}(c)},\qquad \text{hit}(s)=\left\lfloor \frac{\text{mask}}{2^{\mathrm{bit}(s)}}\right\rfloor \bmod 2$$

也就是代码里的 `mask |= 1 << bit(c)` 与 `(mask >> bit(s)) & 1`。掩码的第 $k$ 位为 $1$，就代表「类型 $k$ 是宝石」。

> 💡 与哈希集合相比，掩码法省掉了哈希值计算、桶数组、内存分配和 cache miss；与 `bool[128]` 数组相比，它更进一步——整张表就是一个**寄存器里的数**。

### 3.3 算法流程 / 状态转移

![算法流程：一次建表，逐块查位](images/wc69_q1_algorithm_flow.svg)

1. `mask = 0`：类型表清空，52 个位全为 $0$；
2. 遍历 `jewels` 的每个字符 $c$：`mask |= 1 << bit(c)`，把「$c$ 是宝石」这件事**记进第 $\mathrm{bit}(c)$ 位**；
3. 遍历 `stones` 的每个字符 $s$：取 $\text{hit}(s)$，为 $1$ 时 `ans += 1`，为 $0$ 时直接跳过；
4. 返回 `ans`。

三种实现的横向对比（同一份题意，成本差别极大）：

| 实现 | 每次查询 | 总时间 | 空间 | 评价 |
|------|----------|--------|------|------|
| 双重循环 | $O(\lvert J \rvert)$ | $O(\lvert J \rvert \cdot \lvert S \rvert) \le 2500$ | $O(1)$ | 能过，但模板不可扩展 |
| 哈希集合 | 均摊 $O(1)$ | $O(\lvert J \rvert + \lvert S \rvert)$ | $O(\lvert J \rvert)$ | 通用，写法最长 |
| **52 位掩码** | **$O(1)$ 单条指令** | $O(\lvert J \rvert + \lvert S \rvert)$ | **$O(1)$ 一个整数** | 值域可枚举时的最优解 |

### 3.4 示例演算

![示例 1 的逐块石头走查表](images/wc69_q1_walkthrough.svg)

对示例 1，`jewels = "aA"` 让 $\text{mask} = 2^{0} + 2^{26} = 67108865$，其余 $50$ 位全为 $0$：

| 步 | 石头 $s$ | $\mathrm{bit}(s)$ | 第 $\mathrm{bit}(s)$ 位 | 判定 | `ans` |
|----|----------|-------------------|--------------------------|------|-------|
| 1 | `'a'` | 0 | 1 | ✓ 宝石 | 1 |
| 2 | `'A'` | 26 | 1 | ✓ 宝石 | 2 |
| 3 | `'A'` | 26 | 1 | ✓ 宝石 | 3 |
| 4 | `'b'` | 1 | **0** | ✗ 跳过 | 3 |
| 5 | `'b'` | 1 | 0 | ✗ 跳过 | 3 |
| 6 | `'b'` | 1 | 0 | ✗ 跳过 | 3 |
| 7 | `'b'` | 1 | 0 | ✗ 跳过 | 3 |

第 $4$ 步是第一个「未命中」：`'b'` 落在第 $1$ 位，而掩码第 $1$ 位是 $0$，于是直接跳过；后面三个 `'b'` 完全相同。最终 `ans = 3`，与官方输出一致。

示例 2 更干脆：`'z'` 在小写段里是第 $25$ 位，`'Z'` 在大写段里是第 $51$ 位，两个位都没被置过，两次查询全部落空，答案 $0$。这正是「两段位号互不重叠」的价值——若把大小写混到同一段，`"z"` 就会把 `"Z"` 误判成宝石。

## 4. 算法细节

1. **位号必须是「双段映射」**：小写用 $c-\text{'a'}$、大写用 $c-\text{'A'}+26$。若偷懒写成 `c - 'a' & 31` 或 `c % 32`，`'a'` 与 `'A'` 会被压到同一位（`'a'` $=97$、`'A'` $=65$，模 $32$ 后同为 $1$），直接破坏大小写敏感。
2. **C++ 必须用 `1ULL` 而不是 `1`**：大写段的位号最大到 $51$，`int` 只有 $32$ 位，`1 << 51` 是**未定义行为**（典型表现是位移量被模 $32$，静默变成 `1 << 19`）。写 `1ULL << bit(c)`、掩码类型用 `unsigned long long`，一次避开。
3. **取位别漏掉 `& 1`**：`(mask >> k) & 1` 才是第 $k$ 位。若写成 `mask >> k == 1`，当更高的位上还有置位时（`aA` 的 `mask` 在高位就有 $1$），`mask >> 0` 等于 $67108865 \ne 1$，本该命中却会被判成「不是宝石」——这是本题最隐蔽的 WA。
4. **`jewels` 字符唯一，让 OR 天然去重**：就算题面不保证唯一，`mask |= x` 也是**幂等**的——重复置同一位置结果不变，所以这份代码对「`jewels` 有重复」的变体同样正确，属于免费得到的鲁棒性。
5. **给非字母留一个兜底位**：`bit()` 对既非小写也非大写的字符返回 $52$。第 $52$ 位在本题永远不会被置 $1$，于是这类字符的查询恒为「不是宝石」；这样即使题面放宽字符集，程序也不会越界位移（C++ 中移位量 $\ge$ 位宽仍是 UB）。
6. **不要给 `stones` 排序或去重**：题目问的是**块数**，不是种类数。`jewels = "aA"`、`stones = "aAA"` 时答案是 $3$，若先 `set(stones)` 去重就只剩 $2$ 块不同的石头，答案被改写。
7. **命中后不要 `break`**：外层循环必须走满 $\lvert \text{stones} \rvert$ 轮。只有「是否存在」类问题才允许提前返回。
8. **Python 不需要关心位宽**：`int` 是任意精度，`1 << 51` 自然正确；但若把同样的位号公式搬到 `int32`、`int64` 的静态语言里，位宽检查一次都不能省。
9. **字符集一变，方案就得变**：掩码法的前提是「取值可枚举，且种类数不超过机器字长」——本题恰好只有 $52$ 种。若题目扩到全部 ASCII（$128$ 种），就要用 `unsigned __int128` 或两个 `uint64_t`；若扩到 Unicode，就该退回 `unordered_set` / `bool[65536]`。

## 5. 正确性证明

**引理 1（位号映射是单射）**：对任意两个英文字母 $c_1 \ne c_2$，有 $\mathrm{bit}(c_1) \ne \mathrm{bit}(c_2)$，且 $\mathrm{bit}(c) \in [0, 51]$。

**证明**：小写字母的 $c - \text{'a'}$ 取值落在 $[0,25]$，大写字母的 $c - \text{'A'} + 26$ 取值落在 $[26,51]$，两段不交，故 $\mathrm{bit}(c) \in [0,51]$。若 $c_1, c_2$ 同为小写或同为大写，$c_1 \ne c_2$ 时二者减同一常数后仍不相等；若一者小写一者大写，它们的位号分别落在不交的 $[0,25]$ 与 $[26,51]$，也不可能相等。∎

**引理 2（建表正确）**：第 2 步结束后，对任意英文字母 $c$，$\text{mask}$ 的第 $\mathrm{bit}(c)$ 位为 $1$ 当且仅当 $c \in \text{jewels}$。

**证明**：

- ($\Leftarrow$) 若 $c \in \text{jewels}$，则循环中必有 $c$ 这一轮执行 `mask |= 1 << bit(c)`，把第 $\mathrm{bit}(c)$ 位置为 $1$；后续的 OR 只会把位从 $0$ 变 $1$、不会把 $1$ 变 $0$，故结束时该位为 $1$。
- ($\Rightarrow$) 若结束时第 $\mathrm{bit}(c)$ 位为 $1$，则必是某次 `mask |= 1 << bit(x)` 置上的，此时 $\mathrm{bit}(x) = \mathrm{bit}(c)$；由引理 1 的单射性得 $x = c$，而 $x$ 取自 `jewels`，故 $c \in \text{jewels}$。∎

**引理 3（单次查询正确）**：对任意英文字母 $s$，$\text{hit}(s) = 1$ 当且仅当 $s \in \text{jewels}$。

**证明**：$\text{hit}(s) = \lfloor \text{mask} / 2^{\mathrm{bit}(s)} \rfloor \bmod 2$ 取出的正是 $\text{mask}$ 的第 $\mathrm{bit}(s)$ 位，其值只能是 $0$ 或 $1$。由引理 2，该位为 $1 \iff s \in \text{jewels}$，故 $\text{hit}(s) = 1 \iff s \in \text{jewels}$。∎

**定理**：算法返回的值等于 `stones` 中「类型属于 `jewels`」的石头块数。

**证明**：循环变量 $s$ 遍历 `stones` 的每一块石头，恰好一次、不重不漏。由引理 3，`ans` 恰在 $s \in \text{jewels}$ 时加 $1$，否则不变。故结束时 `ans` 等于满足条件的石头块数，即所求。∎

## 6. 复杂度分析

- **时间**：$O(\lvert \text{jewels} \rvert + \lvert \text{stones} \rvert)$。建表扫一遍 `jewels`（至多 $50$ 个字符），每次是一次 `bit()` 计算加一次 OR；查表扫一遍 `stones`（至多 $50$ 个字符），每次是一次移位加一次按位与。总计至多约 $100$ 次基本运算，且每次都只碰一个机器字，无哈希、无分支预测失败。
- **空间**：$O(1)$。整个「类型表」就是一个 $64$ 位整数（`unsigned long long` / Python `int`），与输入规模无关；递归栈、临时容器均为零。
- **对比**：暴力法时间 $O(\lvert J \rvert \cdot \lvert S \rvert)$（最坏 $2500$ 次比较），哈希集合法空间 $O(\lvert J \rvert)$ 且每次查询有哈希开销。在本题数据范围内三者都能过，但只有掩码法同时做到「线性时间 + 常数空间 + 无分配」。
- **常数层面**：$\lvert J \rvert, \lvert S \rvert \le 50$ 时总工作量约 $10^2$ 次整数运算，单次调用在微秒以内——这也是它适合当**热路径模板**的原因：没有容器构造，就没有初始化成本。

## 7. 参考代码

### C++

```cpp
#include <string>
using namespace std;

class Solution {
public:
    int numJewelsInStones(string jewels, string stones) {
        unsigned long long mask = 0;                 // 52 位有效，其余保持 0
        for (char c : jewels)
            mask |= 1ULL << bit(c);                  // 建表：把「c 是宝石」记进第 bit(c) 位

        int ans = 0;
        for (char c : stones)
            if ((mask >> bit(c)) & 1ULL) ++ans;      // 查表：一次移位 + 一次按位与
        return ans;
    }

private:
    // 小写 a..z -> 0..25，大写 A..Z -> 26..51；其它字符落到第 52 位（本题永不置位）
    static int bit(char c) {
        if (c >= 'a' && c <= 'z') return c - 'a';
        if (c >= 'A' && c <= 'Z') return c - 'A' + 26;
        return 52;
    }
};
```

### Python

```python
class Solution:
    def numJewelsInStones(self, jewels: str, stones: str) -> int:
        def bit(ch: str) -> int:
            if 'a' <= ch <= 'z':
                return ord(ch) - ord('a')            # 0..25
            if 'A' <= ch <= 'Z':
                return ord(ch) - ord('A') + 26       # 26..51
            return 52                                # 兜底位，永不置位

        mask = 0
        for ch in jewels:
            mask |= 1 << bit(ch)                     # 只在宝石类型上置位

        ans = 0
        for ch in stones:
            if (mask >> bit(ch)) & 1:                # 取第 bit(ch) 位
                ans += 1
        return ans
```

## 8. 边界情况与易错点

1. **大小写敏感**：`'a'` 与 `'A'` 是两种石头。示例 2（`"z"` 对 `"ZZ"`）专门考这一点；若把字符统一 `lower()` 后再比，答案会从 $0$ 变成 $2$。
2. **答案可以是 $0$**：`stones` 里一块宝石都没有时要返回 $0$，别写成返回 $-1$ 或提前 `return` 一个未初始化变量。
3. **C++ 的位移溢出**：`1 << 51` 在 `int`（$32$ 位）上是 UB，且常表现为「位移量模 $32$」。务必用 `1ULL` 且掩码声明为 `unsigned long long`；大写段恰好是这个坑的触发点。
4. **`jewels` 长度为 $1$**：最短输入下映射仍要走两段判断，`'z'`（第 $25$ 位）与 `'Z'`（第 $51$ 位）都不能越界。
5. **`stones` 的重复块数要各自计数**：统计的是**块数**不是**种类数**，不要先 `set(stones)` 去重；示例 1 中有两个 `A`，它贡献 $2$ 而非 $1$。
6. **别把 `jewels` 里的字符也算进去**：答案只统计 `stones`，`jewels` 只用来建表。把 `jewels` 拼进 `stones` 再统计是典型的手滑。
7. **非字母字符（防御性）**：题面保证只有英文字母，但把 `bit()` 的兜底写成 $52$ 而不是返回 $-1$，可以避免「移位量为负」这种更难查的 UB；这类兜底在面试手写时也是加分项。
8. **`jewels` 字符唯一但对拍时别依赖**：随机测试里若用 `random.choice` 生成长度 $>52$ 的 `jewels`，必然出现重复，会与「唯一」约束不符；生成数据时要 `random.sample`。
9. **`ans` 用 `int` 足够**：上界是 $50$，不会有溢出问题；但若把题型改成「`stones` 长 $10^9$」，就要考虑 `long long`。
