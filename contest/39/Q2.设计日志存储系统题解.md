# LeetCode 设计日志存储系统 题解

## 1. 题目概述

- **标题 / 题号**：设计日志存储系统（#635，medium）
- **链接**：https://leetcode.cn/problems/design-log-storage-system/
- **来源**：LeetCode 第 39 场周赛 Q2
- **难度**：中等
- **标签**：设计、哈希表、字符串、有序集合

**题意**：维护一个日志库。每条日志是 `(id, timestamp)`，`timestamp` 形如 `2017:01:01:23:59:59`——**年:月:日:时:分:秒**六段，全部是**定宽补零**的十进制数。需要支持两个接口：

- `put(id, timestamp)`：写入一条日志；
- `retrieve(start, end, granularity)`：返回时间落在 $[start, end]$ 内的日志 `id` 列表，**比较精度**由 `granularity` 决定（`Year` / `Month` / `Day` / `Hour` / `Minute` / `Second`）。精度为 `Day` 时，`start` 那一天整天都算在内，`end` 那一天也是如此。

**约束**：

- `put` 与 `retrieve` 的总调用次数不超过 300 次
- 年份范围 $[2000, 2017]$（固定 4 位），小时范围 $[00, 23]$
- 每条日志 `id` 唯一；时间戳各段两位补零、年份四位，故所有时间戳**等长且定宽**
- `retrieve` 的返回顺序**不做要求**

> 💡 读题关键：`granularity` 不是"四舍五入"，而是**把时间轴切成一格一格的单位**——查询问的是"日志所属单位的序号，是否落在 `start` 与 `end` 所属单位的序号之间"。抓住这一点，题目立刻从"日期加减"退化成"字符串前缀比较"。

## 2. 示例

**示例 1（官方示例，两次查询）**

```text
操作：
put(1, "2017:01:01:23:59:59")
put(2, "2017:01:01:22:59:59")
put(3, "2016:01:01:00:00:00")

retrieve("2016:01:01:01:01:01", "2017:01:01:23:00:00", "Year")  // 返回 [1,2,3]
retrieve("2016:01:01:01:01:01", "2017:01:01:23:00:00", "Hour")  // 返回 [1,2]

解释：精度为 Year 时只比到年份——2016、2017 都在区间内，三条全中；
      精度为 Hour 时比到"时"——日志 3 的 2016:01:01:00 早于 start 的
      2016:01:01:01，被排除在外。
```

**示例 2（补充：同一批日志换 Day 精度）**

```text
retrieve("2016:01:01:01:01:01", "2017:01:01:23:00:00", "Day")  // 返回 [1,2,3]

解释：截断到"日" ⇒ lo = 2016:01:01，hi = 2017:01:01；
      日志 3 的前缀 2016:01:01 恰好等于 lo——等于边界必须算命中。
```

**示例 3（补充：换 Second 精度，精度越细区间越窄）**

```text
retrieve("2016:01:01:01:01:01", "2017:01:01:23:00:00", "Second")  // 返回 [2]

解释：整串比较 ⇒ 日志 1 的 ...23:59:59 超过 hi 的 ...23:00:00，日志 3 不足 lo，
      只剩日志 2 的 2017:01:01:22:59:59。
```

## 3. 解题思路

### 3.1 暴力思路

最直白的写法：每条日志原样存进一个数组；`retrieve` 时**把区间两端补全到秒级**——`start` 缺的段填最小值（月、日填 `01`，时、分、秒填 `00`），`end` 缺的段填最大值（月 `12`、日 `31`、时 `23`、分秒 `59`）——然后遍历全部日志，用整串比较判断是否落在 $[start', end']$ 内。

这个写法是对的，复杂度 $O(m)$（$m$ 为日志条数）、总操作数 $\le 300$ 也完全跑得动。但它的**代码负担全在边界上**：需要 12 个常量（两端各 6 段）、要区分"哪些段该补"、`Day` 精度下 $end$ 侧填 `31` 还会让人怀疑 2 月是否要填 `28`。这些顾虑没有一个是题目真正考的东西，而且每加一个粒度就要多想一遍。

瓶颈不在遍历，而在**"补全"这个动作本身**：既然时间戳是定宽字符串，为什么还要把它拆开再拼回去？

### 3.2 核心观察：截断到 k 段，而不是补全到秒

![截断到 k 段：定宽字符串的前缀比较](images/wc39_q2_prefix_truncate_concept.svg)

把 `granularity` 从细到粗排成 6 个层级，第 $k$ 级对应时间戳的前 $k$ 段。定义**截断算子** $\pi_k(t)$ 为时间戳 $t$ 的前 $k$ 段组成的字符串，则

$$\ell_k = 4 + 3(k-1),\qquad k = 1,\dots,6$$

即 $\ell = 4, 7, 10, 13, 16, 19$——年占 4 位，其后每段 2 位数字外加 1 个冒号。

两条几乎免费的性质撑起整个解法：

1. **字典序即时间序**：所有时间戳都是 19 字符的等长串，且分隔符位置固定，所以字符串比较的结果与"时间先后"完全一致。
2. **截断单调**：$s \le t \implies \pi_k(s) \le \pi_k(t)$，并且 $\pi_k(t)$ 相同的日志落在同一个 $k$ 级时间单位里。

于是"$t$ 的单位落在 $start$ 与 $end$ 的单位之间"这句话，可以原样翻译成一次字符串比较：

$$\pi_k(start) \;\le\; \pi_k(t) \;\le\; \pi_k(end)$$

**不需要补全**：区间两端截断到同一精度，日志也截断到同一精度，三者在同一把尺子上比较，`Day` 精度是否要按月份天数区分之类的问题一次性消失。

> 💡 一句话：**补全要为 6 段各想一遍 min/max，截断只要一个前缀长度 $\ell$。**

### 3.3 算法流程

![流程：lower_bound 定位 + 前缀单调性提前终止](images/wc39_q2_retrieve_flow.svg)

**存储**：用**有序容器** `map<string, vector<int>>`，键是完整时间戳，值是该时间戳下的全部 `id`（同一秒允许多条日志）。

**`put(id, timestamp)`**：`store[timestamp].push_back(id)`，有序性由容器自动维护，$O(\log m)$。

**`retrieve(start, end, granularity)`**：

1. 查表得到 $\ell$，截出 `lo = start.substr(0, ℓ)`、`hi = end.substr(0, ℓ)`；
2. `it = store.lower_bound(lo)`——第一个"键 $\ge$ `lo`"的位置。由于 `lo` 只是前缀，这恰好等价于"第一个前缀 $\ge$ `lo` 的键"，所有前缀更小的日志被整段跳过；
3. 从 `it` 起顺序扫描，把 `it->second` 里的 `id` 全部加入答案，直到 `it == end` 或 `it->first.substr(0, ℓ) > hi` 就停；
4. 返回答案（顺序任意）。

第 3 步的**提前终止**是"截断单调"的直接红利：前缀沿有序键单调不减，一旦超过 `hi`，后面的只会更大。

### 3.4 示例演算

![示例演算：同一批日志在 Year 与 Hour 下的前缀与命中](images/wc39_q2_walkthrough.svg)

三条日志的 $\pi_1$ 与 $\pi_4$：

| id | 时间戳 | $\pi_1$（Year） | $\pi_4$（Hour） |
|----|--------|-----------------|-----------------|
| 1 | `2017:01:01:23:59:59` | `2017` | `2017:01:01:23` |
| 2 | `2017:01:01:22:59:59` | `2017` | `2017:01:01:22` |
| 3 | `2016:01:01:00:00:00` | `2016` | `2016:01:01:00` |

**Year 查询**：$\ell = 4$，`lo = 2016`、`hi = 2017`。三条日志的前缀分别是 `2017`、`2017`、`2016`，全部落在闭区间内，返回 $[1,2,3]$。注意日志 3 的前缀**恰好等于下界** `lo`，这靠的是比较用 $\le$ 而不是 $<$。

**Hour 查询**：$\ell = 13$，`lo = 2016:01:01:01`、`hi = 2017:01:01:23`。日志 1 的前缀**恰好等于上界** `hi`（`23` 时），命中；日志 2 的 `22` 时小于 `23`，命中；日志 3 的 `00` 时小于 `01`，出局。返回 $[1,2]$。

同一个区间、同一批数据，只是把 $\ell$ 从 4 改成 13，结果就从三条变两条——**精度只影响一次截断，不影响任何比较逻辑**。

## 4. 算法细节

1. **粒度 → 前缀长度用查表**：`{"Year":4,"Month":7,"Day":10,"Hour":13,"Minute":16,"Second":19}`。用表（`map` / `dict`）而不是一串 `if-else`，既省代码也避免漏写分支；$\ell = 4 + 3(k-1)$ 只是这六个数背后的规律，实现时直接写死更清楚。
2. **截断 vs 补全**：补全派要给 $start$ 填 `01/00`、给 $end$ 填 `12/31/23/59/59`，还得想"$end$ 是闰年 2 月"这类题面根本没问的事；截断派只要一句 `substr(0, ℓ)`。两者本质等价（见 §5 引理 3 的推论），但代码量与出错面差一个数量级。
3. **必须用有序容器**：`map` / `TreeMap`，Python 用"有序键表 + `bisect`"。**不能用 `unordered_map`**——它无法按区间遍历，退化成全表扫描就丢掉了有序结构的意义。若用 `set<pair<string,int>>`，键是（时间戳, id），区间遍历同样成立。
4. **同一秒可以有多条日志**：键是时间戳而非 `id`，所以值必须是列表（`vector<int>`）。写成 `map<string,int>` 会把同一秒的后一条日志覆盖掉前一条。
5. **`lower_bound` 的语义要看清**：`lo` 是长度 $\ell$ 的**前缀**，比任何完整时间戳都短；字典序下"前缀 < 以它为前缀的串"，所以 `lower_bound(lo)` 返回的位置恰好是"第一个前缀 $\ge$ `lo`"的键，前缀更小的条目一个都不看。
6. **终止条件写前缀，不要写完整串**：循环条件必须是 `it->first.substr(0, ℓ) <= hi`。若图省事写成 `it->first <= end`，就是在拿 19 字符串和 13 字符的 `hi` 比，`hi` 对应单位内的日志会被整批漏掉——这是本题最典型的 bug。
7. **只在首次见到时间戳时插入键表**：Python 版用 `insort` 维护有序键表，重复时间戳再插一次会让键表出现重复项，区间遍历重复输出 `id`。
8. **不要解析成整数秒**：解析要处理月长、闰年、年份只有 4 位等细节；字符串比较一次最多 19 个字符，既快又没有任何进位坑。

## 5. 正确性证明

**引理 1（字典序 = 时间序）**：对任意两条合法时间戳 $s, t$，$s < t$ 当且仅当 $s$ 表示的日期时间严格早于 $t$。

**证明**：两串等长 19、分隔符位置固定，逐字符比较。设第一个不同字符在下标 $p$：$p$ 必落在某一字段内部——若它落在分隔符上或跨字段边界，则前面所有字段连同分隔符都相同，矛盾。于是两串在该字段上的数字串不同，而等宽补零的十进制串的字典序与数值序一致，故该字段数值更小；更高层字段全同，正是"时间更早"。∎

**引理 2（截断单调与单位归属）**：对 $1 \le k \le 6$ 与任意时间戳 $s \le t$，有 $\pi_k(s) \le \pi_k(t)$；且 $\pi_k(s) = \pi_k(t)$ 当且仅当二者落在同一个 $k$ 级时间单位内。

**证明**：若前 $k$ 段完全相同，则 $\pi_k(s) = \pi_k(t)$，且按定义二者共享同一 $k$ 级单位。否则它们在某个 $\le k$ 的字段上首次出现不同，由引理 1 的论证该差异方向与 $s, t$ 的先后一致，故 $\pi_k(s) < \pi_k(t)$，同时二者单位不同。∎

**引理 3（区间定位正确）**：设 $\ell = \ell_k$，`lo`、`hi` 为两端前缀。则 (i) `lower_bound(lo)` 之前的键满足 $\pi_k < lo$；(ii) 首个 $\pi_k > hi$ 的键之后，所有键的 $\pi_k$ 也 $> hi$。

**证明**：(i) 取键 $u < lo$。若 $\pi_k(u) = lo$，则 $u$ 以 `lo` 开头且 $|u| = 19 > \ell$，字典序上 $u > lo$，矛盾；故 $\pi_k(u) \ne lo$，再由引理 2 的单调性得 $\pi_k(u) \le lo$，即 $\pi_k(u) < lo$。(ii) 由引理 2，$\pi_k$ 沿有序键单调不减，一旦某个键的前缀超过 `hi`，其后继只会更大。∎

**定理**：`retrieve` 返回的 `id` 集合恰为所有满足"日志的 $k$ 级单位落在 $start$ 与 $end$ 的 $k$ 级单位之间"的日志。

**证明**：由引理 2，该语义条件等价于 $\pi_k(start) \le \pi_k(t) \le \pi_k(end)$，即算法中的比较条件。由引理 3，扫描起点之前没有任何满足条件的键，终止点之后也没有，中间被访问的每个键都恰好被判定一次：满足条件时把该桶内全部 `id` 输出（不漏），不满足时跳过（不多）。`put` 只做追加、不改写其他桶，故答案与调用历史一致。∎

**推论**：把两端"补全到秒"再整串比较的经典写法与本文的截断写法给出相同结果——因为对任意时间戳 $t$，$t \ge \text{expand}_{\min}(start)$ 当且仅当 $\pi_k(t) \ge \pi_k(start)$，两个方向都可由引理 2 的单调性得到。

## 6. 复杂度分析

- **时间**：`put` 为 $O(\log m)$（`map` 插入）或 $O(m)$（Python `insort` 的列表搬移，$m \le 300$ 可忽略）。`retrieve` 为 $O(\log m + h + L)$：一次二分 $O(\log m)$，$h$ 为命中桶数、$L$ 为输出长度，每次桶内拼接是 $O(1)$ 摊还（`insert` 区间插入）或 $O(|bucket|)$。最坏 $O(m + L)$，即全表命中。总操作数 $Q \le 300$、$m \le 300$，即便每次查询都全表命中，字符比较也只有 $300 \times 300 \times 19 \approx 1.7 \times 10^6$ 次，远在时限之内。
- **空间**：$O(\sum_i L_i)$ 存日志本身（每条一个 19 字节字符串 + 一个 `int`），$O(m)$ 存索引，返回值 $O(L)$。没有额外的时间维度表、也没有按粒度冗余建索引。

## 7. 参考代码

### C++

```cpp
#include <map>
#include <string>
#include <vector>
using namespace std;

class LogSystem {
    map<string, vector<int>> store;   // 完整时间戳 -> 该秒下的全部 id（键有序）
    map<string, int> plen = {{"Year", 4},   {"Month", 7},  {"Day", 10},
                             {"Hour", 13},  {"Minute", 16}, {"Second", 19}};

  public:
    LogSystem() {}

    void put(int id, string timestamp) {
        store[timestamp].push_back(id);           // 同一秒可有多条日志，不能覆盖
    }

    vector<int> retrieve(string start, string end, string granularity) {
        int k = plen[granularity];               // 比较到第 k 段
        string lo = start.substr(0, k), hi = end.substr(0, k);   // 两端截到同一精度
        vector<int> res;
        for (auto it = store.lower_bound(lo);    // 跳过前缀 < lo 的全部键
             it != store.end() && it->first.substr(0, k) <= hi; ++it)
            res.insert(res.end(), it->second.begin(), it->second.end());
        return res;                              // 顺序不做要求
    }
};
```

### Python

```python
from bisect import bisect_left, insort


class LogSystem:
    UNITS = {"Year": 4, "Month": 7, "Day": 10,
             "Hour": 13, "Minute": 16, "Second": 19}

    def __init__(self):
        self.ids = {}     # 时间戳 -> id 列表
        self.keys = []    # 有序的不同时间戳，配合 bisect 当作有序集合

    def put(self, id: int, timestamp: str) -> None:
        if timestamp not in self.ids:            # 只在首次见到该秒时维护键表
            self.ids[timestamp] = []
            insort(self.keys, timestamp)
        self.ids[timestamp].append(id)

    def retrieve(self, start: str, end: str, granularity: str) -> list:
        k = self.UNITS[granularity]              # 前缀长度
        lo, hi = start[:k], end[:k]              # 两端截到同一精度
        res = []
        i = bisect_left(self.keys, lo)           # 第一个键 >= lo
        while i < len(self.keys) and self.keys[i][:k] <= hi:
            res.extend(self.ids[self.keys[i]])   # 命中的桶整桶输出
            i += 1
        return res
```

## 8. 边界情况与易错点

1. **闭区间**：两端都要用 $\le$。示例 2 中日志 3 的前缀等于 `lo`，示例 1 的 Hour 查询中日志 1 的前缀等于 `hi`，写错一个方向就少一条。
2. **同一秒多条日志**：值必须是列表。`map<string,int>` 或 `dict[ts]=id` 会让后写的覆盖先写的，表现为"随机少 id"。
3. **`start` 与 `end` 落在同一单位**：`lo == hi`，此时仍应返回该单位内的全部日志（例如同一秒钟的区间），不是空集。
4. **`granularity = "Second"`**：$\ell = 19$ 正好等于整串长度，退化成整串比较。别把表写成 18 或 20——少一位会把"秒"并进"分钟"里比较；多一位会被 `substr` 静默截到末尾，等于没截断，报错都没有。
5. **粒度名大小写敏感**：题面是首字母大写 `Year`、`Month`……C++ 里写成全小写，`plen[granularity]` 会静默插入并返回 0，`substr(0, 0)` 得到空串，空串是一切字符串的前缀，结果是"全部命中"；Python 里 `self.UNITS[...]` 则直接 `KeyError`。两种表现不同，但都说明查表前该确认拼写。
6. **`start > end`（题面未保证）**：`lower_bound(lo)` 之后的第一个键前缀必然大于 `hi`，循环立即结束返回空——只要条件写成 `while` 而非 `do-while` 就安全。
7. **不要用 `unordered_map`**：没有顺序就无法二分、无法提前终止，等于放弃"有序集合"这个标签的考点。
8. **重复插入时间戳**：Python 版 `insort` 只在 `timestamp not in self.ids` 时执行；漏了判断会让同一个 `id` 被输出两次。

**延伸思考**：若时间戳精确到毫秒、日志量 $10^6$、查询 $10^5$，字符串比较的常数会成为瓶颈——此时可按 $12/32/24/60/60$ 的进制把时间戳打包成一个 64 位整数键，截断变成整数除法 $\lfloor key / base^{6-k} \rfloor$，比较变成整数比较，仍然保持"截断单调"。若还要求"按粒度聚合统计条数"（例如"每年有多少条日志"），可以为 6 个粒度各建一棵有序树做冗余索引，把一次查询的代价从 $O(\log m + h)$ 压到 $O(\log m + \text{聚合节点数})$；若要支持删除与更新，桶内的 `id` 集合要换成有序结构，才能保证输出顺序稳定。所有这些扩展都只改**存储层**，§3.2 那条"截断 + 字典序"的判定骨架一行都不用动。
