# LeetCode 预算内的最多机器人数目 题解

## 1. 题目概述

- **标题 / 题号**：预算内的最多机器人数目（#2398，hard）
- **链接**：https://leetcode.cn/problems/maximum-number-of-robots-within-budget/
- **来源**：LeetCode 第 86 场双周赛 Q4
- **难度**：困难
- **标签**：队列、数组、二分查找、前缀和、滑动窗口、单调队列、堆（优先队列）

**题意**：$n$ 个机器人，`chargeTimes[i]` 为充电时间，`runningCosts[i]` 为运行成本。运行**连续** $k$ 个机器人（区间 $[l, l+k-1]$）的总开销为

$$\max_{i \in [l,\,l+k-1]} \text{chargeTimes}[i] + k \cdot \sum_{i \in [l,\,l+k-1]} \text{runningCosts}[i]$$

给定 `budget`，求开销 $\le$ budget 时最多能运行的**连续**机器人数目（$k = 0$ 表示一个都跑不动，返回 0）。

**约束**：

- $\text{chargeTimes.length} = \text{runningCosts.length} = n \le 5 \times 10^4$
- $1 \le \text{chargeTimes}[i], \text{runningCosts}[i] \le 10^5$
- $1 \le \text{budget} \le 10^{15}$

## 2. 示例

**示例 1**

```text
输入：chargeTimes = [3,6,1,3,4], runningCosts = [2,1,3,4,5], budget = 25
输出：3
解释：取前 3 个：max(3,6,1) + 3 × (2+1+3) = 6 + 18 = 24 ≤ 25；4 个必超。
```

**示例 2**

```text
输入：chargeTimes = [11,12,19], runningCosts = [10,8,7], budget = 19
输出：0
解释：单跑任意一个都超预算（11+10=21 最小），返回 0。
```

**边界补充**

```text
输入：chargeTimes = [1], runningCosts = [1], budget = 2    输出：1   # 恰好等号成立
输入：chargeTimes = [1], runningCosts = [1], budget = 1    输出：0   # 差一点
输入：chargeTimes = [5,5,5,5], runningCosts = [1,1,1,1], budget = 21
输出：4    # 5 + 4×4 = 21 恰好；budget = 17 时答案 3（5 + 3×3 = 14）
```

## 3. 解题思路

### 3.1 暴力思路

枚举全部 $O(n^2)$ 个区间，对每个区间现算 max 与 sum：$O(n^3)$；前缀和把 sum 降到 $O(1)$ 后仍剩 $O(n^2)$ 个区间 × $O(n)$ 求 max，或 $O(n^2)$ 个区间 × $O(1)$（若用 ST 表）。$n = 5\times10^4$ 时 $O(n^2) = 2.5 \times 10^9$，不可行。突破口在于"**连续**"二字——这是滑动窗口的地形；障碍在于窗口内 **max 不满足单调性**（左端右移后 max 变化无常），这正是单调队列登场的信号。

### 3.2 核心观察：枚举右端点，单调队列维护窗口 max，左端整体右移

![单调队列模型：dq 存下标、对应 charge 递减，队头即窗口 max](images/bw86_q4_monotonic_queue.svg)

三个组件咬合：

1. **固定右端点 $r$，窗口 $[l, r]$ 的开销关于 $l$ 单调**：$l$ 增大（窗口变短）时，max 不增、$k \cdot \text{sum}$ 严格减小（$\text{runningCosts} > 0$），故开销随 $l$ 增大而**不增**。于是对每个 $r$ 存在最小的 $l^*(r)$ 使 $[l^*, r]$ 可行，且 $l^*(r)$ 关于 $r$ **单调不减**——双指针合法（左端永不回退）。
2. **窗口 max 用单调队列**：`dq` 存下标、对应 `chargeTimes` 值**递减**。新元素 $r$ 入队前，从队尾弹出所有值 $\le \text{chargeTimes}[r]$ 的下标（它们永远不可能再当 max——被更新、更靠右的 $r$ 压住）；队头即当前窗口最大值的下标。左端 $l$ 右移时若队头下标 $< l$ 则弹出队头。每个下标至多进出队各一次，总计 $O(n)$。
3. **窗口 sum 用增量维护**：`sum` 随右端扩展加、随左端收缩减。

> ⚠️ 与"和 ≤ 目标"型滑窗的区别：那里窗口内和天然单调，双指针即可；本题的 max 项**不随窗口收缩而单调变化**（收缩可能让 max 不变、变小），但**整个开销函数**对固定 $r$ 仍随 $l$ 单调不增（max 与 $k\cdot$sum 都不增），单调性在"总开销"层面保住了——这是双指针仍然合法的根本原因，也是本题最容易想岔的一步。

### 3.3 算法流程

![算法流程：右端扩展、入队、超预算收缩、记录窗长](images/bw86_q4_algorithm_flow.svg)

```text
dq = 空双端队列（存下标，chargeTimes 递减）
sum = 0, left = 0, best = 0
for right = 0 .. n-1:
    入队：while dq 非空且 chargeTimes[dq.back()] <= chargeTimes[right]: 弹尾
         dq.push_back(right)
    sum += runningCosts[right]
    收缩：while left <= right 且 chargeTimes[dq.front()] + (right-left+1)*sum > budget:
             若 dq.front() == left: 弹头
             sum -= runningCosts[left]; left += 1
    记录：若 left <= right: best = max(best, right - left + 1)
返回 best
```

收缩循环的条件里，`chargeTimes[dq.front()]` 与 `(right-left+1)*sum` 都随 `left` 增大而不增（队头弹出只会让 max 变小或不变、长度与 sum 严格减小），故循环必然终止且每步都在逼近可行。

### 3.4 示例演算

![示例演算：示例 1 的双指针推进与单调队列状态](images/bw86_q4_example_walkthrough.svg)

示例 1（`charge = [3,6,1,3,4]`，`run = [2,1,3,4,5]`，`budget = 25`）逐右端点演算：

| $r$ | 入队后 dq（值） | sum | 收缩后 $[l,r]$ | 开销 | best |
|---|---|---|---|---|---|
| 0 | 3 | 2 | $[0,0]$：$3 + 1\times2 = 5$ | 5 ✓ | 1 |
| 1 | 3→6（3 被弹） | 3 | $[0,1]$：$6 + 2\times3 = 12$ | 12 ✓ | 2 |
| 2 | 6,1 | 6 | $[0,2]$：$6 + 3\times6 = 24$ | 24 ✓ | 3 |
| 3 | 6,1,3 | 10 | 先试 $[0,3]$：$6+4\times10 = 46 > 25$ → 收缩；$[1,3]$：$6+3\times8=30>25$ → 收缩；$[2,3]$：$3+2\times7 = 17$ ✓ | 17 ✓ | 3 |
| 4 | 6,1,3,4 | 15 | $[2,4]$：$4+3\times12 = 40 > 25$；$[3,4]$：$4+2\times9=22$ ✓ | 22 ✓ | 3 |

注意 $r = 1$ 时 3 被 6 弹出（更老更小，永无出头之日）；$r = 3$ 收缩时队头 6（下标 1）在 $l$ 越过 1 前一直是 max。最终 `best = 3`，与官方一致。

## 4. 算法细节

1. **为什么"枚举右端 + 收缩左端"而不"二分长度"**：二分长度 $k$ 后需检验"是否存在长度 $k$ 的可行区间"，检验本身要滑窗 + 单调队列 $O(n)$，总 $O(n \log n)$——正确但多一个 $\log$。关键在于可行性关于长度**单调**（长度 $k$ 可行 ⇒ 长度 $k-1$ 必可行？不！两端各缩一格的 max 与 sum 都不增，故**任何**子区间都可行——对，是单调的），因此双指针 $O(n)$ 成立且更优。
2. **弹尾用 `<=` 还是 `<`**：`chargeTimes[dq.back()] <= chargeTimes[right]` 时弹出——相等时留谁都当 max 一样，弹出更老的减少队头过期维护；用 `<` 也正确（队里多存一个相等值），仅常数差异。
3. **收缩循环里先判队头过期再算开销**：`dq.front()` 的下标可能已 $< l$（还在队里但出了窗口），必须**先弹过期队头**再取 max。本实现把过期弹头放在"队头 == left 即将越界"时同步进行——因为收缩是逐格推进的，队头下标 $\ge l$ 恒成立（归纳：每次 `left += 1` 前检查 `dq.front() == left`），所以取 `dq.front()` 前无需额外清理。
4. **`left <= right` 的保护**：极端预算下窗口可能收缩到空（每个单机器人开销都超预算），收缩条件带 `left <= right` 防止越界；此时本轮不更新 `best`（长度 0）。
5. **溢出**：$(right - left + 1) \times sum \le 5\times10^4 \times (5\times10^4 \times 10^5) = 2.5\times10^{14}$，加 max 后仍在 `long long`（$\approx 9.2 \times 10^{18}$）内；但 **`int` 必炸**——`(right-left+1) * sum` 若 `sum` 是 `int` 已先溢出，Python 无虞、C++ 必须 `long long`。
6. **为什么不需要 `best` 在收缩后兜底为 0**：`best` 初值 0，收缩到空窗时跳过更新即可；别把"窗口空"误记为 $-1$ 长度。

## 5. 正确性证明

**引理 1（子区间单调性）**：设区间 $I' \subseteq I$，则 $\text{cost}(I') \le \text{cost}(I)$。

**证明**：$\text{cost} = \max \text{charge} + k \cdot \sum \text{run}$。子区间的 max 不大于全集的 max（取值集合是子集）；$k' \le k$ 且 $\sum' \le \sum$，且 $\text{runningCosts}[i] \ge 1 > 0$ 保证项项为正，故 $k' \sum' \le k \sum$。两项相加即得。∎

**引理 2（左端点单调）**：对每个右端点 $r$，定义 $L(r) = \min\{l : \text{cost}([l, r]) \le \text{budget}\}$（若不存在则 $L(r) = r + 1$ 表示空窗起点）。则 $L(r)$ 关于 $r$ 单调不减。

**证明**：设 $r_1 < r_2$，往证 $L(r_1) \le L(r_2)$。若 $L(r_2) = r_2 + 1$（空窗）则由 $L(r_1) \le r_1 + 1 \le r_2 + 1$ 立得。否则取 $l = L(r_2)$，则 $[l, r_2]$ 可行。由引理 1，其子区间 $[l, r_1]$（非空，因 $l \le r_2$ 且若 $l > r_1$ 则 $L(r_1) \le r_1 + 1 \le l$ 直接成立）可行，故 $L(r_1) \le l = L(r_2)$。∎

**引理 3（单调队列维护窗口 max）**：算法不变式——任意时刻，`dq` 中下标递增、对应 `chargeTimes` 值严格递减，且**当前窗口 $[l, r]$ 内的所有"可能成为未来窗口 max"的候选下标**恰好在 `dq` 中，队头是窗口 max。

**证明**：归纳于操作序列。入队弹尾：被弹出的下标 $t$ 满足 $\text{charge}[t] \le \text{charge}[r]$ 且 $t < r$——对任意未来包含 $t$ 的窗口（必含 $r$，因窗口右端只增），$t$ 的值不大于更靠右的 $r$，永不可能当 max，删除无损。收缩弹头：队头下标 $< l$ 时它已离开窗口，而队列下标递增保证越界者必在队头，弹出后新队头是仍在窗内的最大候选。窗口 max 恰为队头：窗内任何不在 `dq` 的下标都被某更靠右、值不小于它的在队下标支配，故最大值总在队中且在队头（值递减）。∎

**定理**：算法返回可行区间的最大长度。

**证明**：最优解设为区间 $I^* = [l^*, r^*]$，长度 $T^*$。算法枚举每个右端点 $r$，收缩后的窗口 $[l_r, r]$ 是"以 $r$ 为右端点的最长可行区间"（收缩循环在首次满足 $\text{cost} \le \text{budget}$ 时停止；由引理 1 可行性随 $l$ 增大单调恢复，循环得到的恰是最小可行 $l$）。于是 $best = \max_r (r - l_r + 1) \ge r^* - l^* + 1 = T^*$。反过来，每个被记录的窗口都经过开销判定（收缩条件保证记录时 $\text{cost}([l_r, r]) \le \text{budget}$，引理 3 保证 max 取值正确，sum 增量维护显然正确），故 $best \le T^*$。两个方向夹逼得 $best = T^*$。

还需确认双指针**不会漏解**：由引理 2，$l_r$ 单调不减，算法的 `left` 指针从不清退（只前进），且归纳可证处理完 $r$ 后 `left` $= L(r)$（收缩循环恰好推进到首个可行位置或空窗），因此对每个 $r$ 记录的都是"右端点为 $r$ 的最长可行区间"，无遗漏。∎

> ⚠️ 引理 1 的正数条件不可省：若允许 $\text{runningCosts} = 0$ 且 charge 全 0，则任意区间开销恒 0，结论退化但仍成立；但若 runningCosts 可为**负**，$k \cdot \sum$ 不再随收缩单调下降，引理 1、2 双双失效，双指针不再合法（须回到枚举/DP）。本题约束 $> 0$ 是滑窗的基石。

## 6. 复杂度分析

- **时间**：$O(n)$。右端点 $n$ 轮；每个下标至多入队一次、出队一次（队尾支配或队头过期），收缩的 `left` 总推进量 $\le n$，`sum` 的加减与之一一对应。相比二分长度的 $O(n \log n)$ 与暴力的 $O(n^2)/O(n^3)$。
- **空间**：$O(n)$。单调队列最坏存全部下标（charge 严格递减时），加上常数个标量。

## 7. 参考代码

### C++

```cpp
class Solution {
public:
    int maximumRobots(vector<int>& chargeTimes, vector<int>& runningCosts, long long budget) {
        int n = chargeTimes.size();
        deque<int> dq;                       // 下标，chargeTimes 递减
        long long sum = 0;
        int left = 0, best = 0;
        for (int right = 0; right < n; ++right) {
            while (!dq.empty() && chargeTimes[dq.back()] <= chargeTimes[right])
                dq.pop_back();               // 更老更小的永无出头之日
            dq.push_back(right);
            sum += runningCosts[right];
            while (left <= right &&
                   (long long)chargeTimes[dq.front()] +
                       (long long)(right - left + 1) * sum > budget) {
                if (dq.front() == left) dq.pop_front();   // 队头随左端出窗
                sum -= runningCosts[left];
                ++left;
            }
            if (left <= right) best = max(best, right - left + 1);
        }
        return best;
    }
};
```

### Python

```python
class Solution:
    def maximumRobots(self, chargeTimes: list[int], runningCosts: list[int], budget: int) -> int:
        from collections import deque
        n = len(chargeTimes)
        dq = deque()                          # 下标，chargeTimes 递减
        sum_ = 0
        left = 0
        best = 0
        for right in range(n):
            while dq and chargeTimes[dq[-1]] <= chargeTimes[right]:
                dq.pop()                      # 更老更小的永无出头之日
            dq.append(right)
            sum_ += runningCosts[right]
            while left <= right and chargeTimes[dq[0]] + (right - left + 1) * sum_ > budget:
                if dq[0] == left:
                    dq.popleft()              # 队头随左端出窗
                sum_ -= runningCosts[left]
                left += 1
            if left <= right:
                best = max(best, right - left + 1)
        return best
```

> 💡 两份代码均通过官方 2 个示例与 4 个手算边界（等号成立/差一点、全队恰跑、部分跑），并与"枚举全部区间"暴力对拍：C++ 1.8 万组（含 $10^{15}$ 大预算与 1 的极小预算）、Python 1 千组随机，`mismatch = 0`；另通过 $n = 5\times10^4$ 满规模性能校验（budget $10^{15}$ → 50000、budget $10^9$ → 154，跨语言一致）。

## 8. 边界情况与易错点

1. **答案为 0**：单跑任意机器人都超预算（示例 2），收缩循环会把每个右端点推到空窗（`left = right + 1`），`best` 保持 0——确认收缩条件带 `left <= right` 保护、记录前判 `left <= right`。
2. **溢出是第一杀手**：`(right-left+1) * sum` 最大 $5\times10^4 \times 5\times10^9 = 2.5\times10^{14}$。C++ 中若 `sum` 声明为 `int`，乘法先在 `int` 域溢出再转 `long long` 也晚了——`(long long)(right-left+1) * sum` 与 `long long sum` 二选一必须落实（本文两者都用了）。
3. **弹尾的比较符**：`<=`（相等也弹）与 `<`（相等保留）都正确；但写成 `>=` 方向反了，队列变递增，队头成了窗口**最小** charge，答案系统性偏小。
4. **队头过期弹出时机**：本文在 `left` 推进且 `dq.front() == left` 时同步弹头——依赖"收缩逐格推进"这一事实。若你把收缩写成大步跳（如直接二分 $l$），就必须改为"取 max 前清理所有 $< l$ 的队头"，否则用到过期 max。
5. **等号的方向**：开销恰等于 budget 是**可行**（题面"不超过"）；收缩条件是 `> budget`（严格大于才收缩），写成 `>=` 会把等号可行的窗口错杀。
6. **别把 max 换成"堆 + 懒删除"还沾沾自喜**：`multiset`/延迟堆也能 $O(n \log n)$ 维护窗口 max，正确但慢一个量级且代码更长；单调队列是本题的"官方姿势"。
7. **`numSelect` 式的"恰好 k"幻觉**：本题问"最多能跑几个"，不是"恰好 k 个的开销"——若误读成后者会去二分 $k$ 再判"恰好"，绕远路还容易把"至多"与"恰好"的判定写混。
