# LeetCode 制作 m 束花所需的最少天数 题解

## 1. 题目概述

- **标题 / 题号**：制作 m 束花所需的最少天数（#1482，medium）
- **链接**：https://leetcode.cn/problems/minimum-number-of-days-to-make-m-bouquets/
- **来源**：LeetCode 第 193 场周赛 Q3
- **难度**：中等
- **标签**：数组、二分查找

**题意**：花园里有 $n$ 朵花，第 $i$ 朵要到第 `bloomDay[i]` 天才盛开，盛开后一直可用。现在要做 $m$ 束花，**每束必须用 $k$ 朵在花园中下标相邻的花**，且每朵花最多只能进一束。求**最少**要等多少天才能做齐 $m$ 束；永远做不齐则返回 `-1`。

注意「相邻」是**下标相邻**，不是「开花的先后相邻」：两朵都盛开的花如果中间隔着一朵没开的，它们就不能被算进同一束。

**约束**：

- $n = \text{bloomDay.length}$，$1 \le n \le 10^5$
- $1 \le \text{bloomDay}[i] \le 10^9$
- $1 \le m \le 10^6$，$1 \le k \le n$
- $m \cdot k$ 最大可达 $10^{11}$，**远超 32 位整数**，判无解时要用 64 位

## 2. 示例

**示例 1**

```text
输入：bloomDay = [1,10,3,10,2], m = 3, k = 1
输出：3
解释：k = 1，每朵盛开的花各成一束，只需凑够 3 朵。
      1 天后 [x,_,_,_,_] → 1 束；2 天后 [x,_,_,_,x] → 2 束；
      3 天后 [x,_,x,_,x] → 3 束，故答案为 3。
```

**示例 2**

```text
输入：bloomDay = [1,10,3,10,2], m = 3, k = 2
输出：-1
解释：需要 3 × 2 = 6 朵花，而花园里只有 5 朵，永远做不齐。
```

**示例 3**

```text
输入：bloomDay = [7,7,7,7,12,7,7], m = 2, k = 3
输出：12
解释：7 天后 [x,x,x,x,_,x,x]，第一段连续 4 朵只能做 ⌊4/3⌋ = 1 束，
      第二段连续 2 朵凑不满 3 朵，只能作废，共 1 束 < 2；
      12 天后 [x,x,x,x,x,x,x]，连续 7 朵可做 ⌊7/3⌋ = 2 束，故答案为 12。
```

## 3. 解题思路

### 3.1 暴力思路

最直白的翻译是「按天模拟」：从第 $1$ 天枚举到第 $\max(\text{bloomDay})$ 天，每天扫一遍数组统计能做的束数，第一个够 $m$ 束的天数就是答案。

单次判定是 $O(n)$，但天数要枚举到 $10^9$，总复杂度

$$O\bigl(n \cdot \max(\text{bloomDay})\bigr) \le 10^5 \times 10^9 = 10^{14}$$

完全不可行。即便只枚举 `bloomDay` 中出现的不同天数（去重后最多 $n$ 个），仍有 $O(n^2)$ 级别的判定开销，$10^{10}$ 同样超时。

问题出在「一天一天试」这个维度上：答案的候选值域太大，而**判定本身很便宜**。

### 3.2 核心观察：可行性关于天数单调不减

![可做束数随天数单调不减，二分最小可行天数](images/wc193_q3_feasibility_monotone.svg)

关键性质只有一条：

**若第 $x$ 天能做够 $m$ 束，则任意第 $y > x$ 天也一定能做够 $m$ 束。**

理由很直观：把第 $x$ 天的那 $m$ 束原封不动保留下来，到了第 $y$ 天，原来盛开的花不会凋谢，只是**多了**一些新开的花，所以同样的做法依然成立。

于是「能否做够 $m$ 束」这个布尔判定关于天数是**单调**的：前面一段全是 false，后面一段全是 true，中间只有一个分界点。这正好是**二分答案**的标准结构——在值域 $[\min(\text{bloomDay}), \max(\text{bloomDay})]$ 上二分，找那个最小的可行天数。

还有一个顺带的结论：答案一定**等于某个 `bloomDay` 值**。因为在两个相邻的花开日之间，花园的状态（哪些花已开）完全不变，判定结果自然也不变。这条结论让「按天枚举」可以去重压缩，但真正的加速来自二分。

### 3.3 算法流程：check(day) + 二分下界

![check(day) 顺序扫描：run 计数、凑满 k 即成一束](images/wc193_q3_scan_flow.svg)

**第一步：写判定函数 `check(day)`。** 全部操作就是一次顺序扫描，维护两个计数器：

- `run`：**当前**这段连续盛开的花已经有多长；
- `bouquets`：已经做成的束数。

遇到 $x \le \text{day}$ 的花，`run += 1`；一旦 `run == k`，立刻 `bouquets += 1` 并把 `run` 归零（这 $k$ 朵被消耗掉）。遇到没开的花，说明连续段断开，`run = 0`。

`run` 反复「涨到 $k$ 就清零」，最终等价于对每个长度为 $L$ 的连续段累加 $\lfloor L/k \rfloor$——段内多出来的 $L \bmod k$ 朵因为不邻接下一段，只能作废。只要 `bouquets >= m` 就提前返回 true；扫完仍不足则返回 false。

**第二步：在值域上二分下界。**

1. 若 $m \cdot k > n$，总花数都不够，直接返回 `-1`；
2. 令 $lo = \min(\text{bloomDay})$，$hi = \max(\text{bloomDay})$，先判 `check(hi)`：连全开都做不齐，返回 `-1`；
3. 当 $lo < hi$：取 $mid = lo + \lfloor (hi - lo)/2 \rfloor$，若 `check(mid)` 为真则 $hi = mid$（mid 可能就是答案，不能丢），否则 $lo = mid + 1$；
4. $lo = hi$ 时收敛，`lo` 就是最小的可行天数。

### 3.4 示例演算

![示例 3 的逐天状态与二分轨迹](images/wc193_q3_walkthrough.svg)

以示例 3 为例，`bloomDay = [7,7,7,7,12,7,7]`，$m = 2$，$k = 3$，初值 $lo = 7$、$hi = 12$。

| 探测天数 | 盛开情况 | 连续段长度 | 束数 | 判定 | 区间更新 |
|----------|----------|------------|------|------|----------|
| 7 | `x x x x _ x x` | 4, 2 | $\lfloor 4/3 \rfloor + \lfloor 2/3 \rfloor = 1$ | 不足 | —— |
| 9（mid） | `x x x x _ x x` | 4, 2 | 1 | 不足 | $lo = 10$ |
| 11（mid） | `x x x x _ x x` | 4, 2 | 1 | 不足 | $lo = 12$ |
| 12 | `x x x x x x x` | 7 | $\lfloor 7/3 \rfloor = 2$ | 足够 | 收敛，返回 12 |

第 7 天那一行是二分之外的手工验算；二分中 $mid$ 依次取 $9, 11$，都落在「下标 4 还没开」的同一状态里，结果自然相同，$lo$ 被一路推到 12 与 $hi$ 重合。右侧 2 朵盛开的花之所以作废，是因为中间隔着 1 朵未开的花，它们与左边 4 朵不在同一连续段，凑不满 $k = 3$，贡献为 0。

## 4. 算法细节

1. **先判总量**：`m * k > n` 直接返回 `-1`。C++ 里 `m * k` 必须写成 `(long long)m * k`，$10^6 \times 10^5 = 10^{11}$ 会把 `int` 撑爆，得到一个错误的负数或小正数。
2. **二分区间取 $[\min, \max]$ 而不是 $[1, 10^9]$**：答案必落在花的开花日范围内，值域小时轮数随之减少（例如全部花同一天开，$lo = hi$，一轮都不必跑）；两者复杂度同阶，但取真实值域更干净。
3. **下界二分模板**：`while (lo < hi)`，`mid = lo + (hi - lo) / 2` 向下取整，可行就 `hi = mid`（保留 mid），不可行就 `lo = mid + 1`。这里**必须**用向下取整的 mid，否则 `lo = mid` 那种写法会在 `hi = lo + 1` 时死循环。
4. **`run` 的语义是「段内计数」而不是「全局计数」**：遇到未盛开的花必须清零。写成全局累加会把被隔开的花算进同一束，示例 3 的第 7 天就会错判成 2 束。
5. **凑满即消耗**：`run == k` 之后必须 `run = 0`，而不是让 `run` 一路涨到段末。若不清零，长度 $7$、$k = 3$ 的段在整段内只会触发一次 `run == k`，被错算成 1 束（正确答案是 $\lfloor 7/3 \rfloor = 2$ 束）。清零正是「从左端每 $k$ 朵切一块」的贪心。
6. **提前返回**：`bouquets >= m` 时立刻 `return true`，因为后面还有没有花已经不影响结论。这在答案较早的用例上是常数级加速，最坏仍是 $O(n)$。
7. **不要排序、不要前缀和**：判定只需要「哪些花已开」，一次线性扫描即得；排序反而引入 $O(n \log n)$。若把二分改为在**去重排序后的开花日**上做，轮数从 $\log(10^9) \approx 30$ 降到 $\log n \approx 17$，但排序开销抵消收益，直接对整数二分更简洁。
8. **`check(hi)` 的预判可以省掉**：也可以不预判，二分收敛后对 `lo` 再做一次 `check`，失败则返回 `-1`。两种写法等价，选一种即可，**不要两边都漏**。
9. **值域与类型**：$\text{bloomDay}[i] \le 10^9 < 2^{31} - 1$，天数用 `int` 足够；`lo + hi` 同样不溢出，但写成 `lo + (hi - lo) / 2` 是更稳的模板习惯。

## 5. 正确性证明

**引理 1（单调性）**：对任意 $x \le y$，若第 $x$ 天能做够 $m$ 束，则第 $y$ 天也能做够 $m$ 束。

**证明**：第 $x$ 天的 $m$ 束花共占用 $m \cdot k$ 朵下标互不重叠、彼此按段相邻的花，且这些花在第 $x$ 天都已盛开，即对其中每朵花 $i$ 都有 $\text{bloomDay}[i] \le x \le y$。因此到第 $y$ 天这些花依然盛开，同样的 $m$ 束花可以直接沿用。∎

**引理 2（单段贡献）**：固定某一天，设花已经盛开的位置被切成若干极大连续段，长度为 $L_1, L_2, \dots, L_t$，则这一天**最多**能做 $\sum_{j} \lfloor L_j / k \rfloor$ 束，且这个上界**可以达到**。

**证明**：

- **上界**：每一束由 $k$ 朵下标相邻的花组成，这 $k$ 朵必然落在同一个连续段内（段与段之间隔着未盛开的花，下标不连续）。不同束的花互不重叠，故第 $j$ 段最多容纳 $\lfloor L_j / k \rfloor$ 束；各段求和即得上界。
- **可达**：在第 $j$ 段内，从最左端开始每 $k$ 朵切一组，共切出 $\lfloor L_j / k \rfloor$ 组，每组内部下标相邻、组间不重叠，全部合法。∎

**引理 3（check 的正确性）**：`check(day)` 返回 true，当且仅当第 `day` 天能做够 $m$ 束。

**证明**：

- 扫描过程中 `run` 记录的是**当前连续段**已遍历部分的长度，`bouquets` 每凑满 $k$ 就加一并把 `run` 清零；对长度为 $L_j$ 的段，累加次数恰为 $\lfloor L_j / k \rfloor$，遇到未盛开的花 `run` 归零保证计数不跨段。因此扫描结束时 `bouquets` 恰为 $\sum_j \lfloor L_j / k \rfloor$，即引理 2 的上界。
- 若返回 true，则已凑出至少 $m$ 束合法花束，故第 `day` 天可行；若扫描结束返回 false，则总数 $\sum_j \lfloor L_j / k \rfloor < m$，由引理 2 的上界可知确实做不出 $m$ 束。∎

**引理 4（二分不变量）**：循环过程中始终有「$lo$ 左侧（不含）的天数均不可行」，且 $hi$ 是一个**已知可行**的天数（进入循环前由 `check(hi)` 保证）。

**证明**：初始时 $hi$ 已被 `check(hi)` 验证可行，$lo$ 左侧为空，成立。每轮取 $mid$：若 `check(mid)` 为真，由引理 1，$\ge mid$ 全部可行，令 $hi = mid$ 仍然可行；若为假，则 $\le mid$ 全部不可行（引理 1 的逆否命题），令 $lo = mid + 1$ 不越过可行边界。两种情况下不变量保持。∎

**定理**：算法返回的是最小的可行天数；若 $\max(\text{bloomDay})$ 天仍不可行则返回 `-1`。

**证明**：若 `check(hi)` 在初始 $hi = \max(\text{bloomDay})$ 处失败，由引理 1 的逆否命题，所有更小的天数也不可行，返回 `-1` 正确。否则由引理 4，循环终止时 $lo = hi$：左侧天数全部不可行，而 $hi$ 可行，故 $lo$ 恰为最小可行天数。又由引理 3，`check` 与「能否做够 $m$ 束」等价，所以该天数就是题面要求的最少等待天数。∎

## 6. 复杂度分析

- **时间**：$O(n \log V)$，其中 $V = \max(\text{bloomDay}) - \min(\text{bloomDay}) \le 10^9$，即二分至多 $\lceil \log_2 10^9 \rceil = 30$ 轮。每轮 `check` 顺序扫描一次数组，$O(n)$，且能在凑够 $m$ 束时提前退出。总量约 $3 \times 10^6$ 次比较，非常宽裕。此外求 `min/max` 一次 $O(n)$，可忽略。
- **空间**：$O(1)$ 额外空间，只用了 `lo / hi / mid / run / bouquets` 几个标量，没有复制数组、没有辅助哈希表。
- **对比**：暴力按天模拟是 $O(n \cdot V)$，最坏约 $10^{14}$；本算法把「逐个天数试」换成「对数次探测」，值域越大优势越明显。

## 7. 参考代码

### C++

```cpp
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    int minDays(vector<int>& bloomDay, int m, int k) {
        int n = (int)bloomDay.size();
        if ((long long)m * k > n) return -1;      // m*k 可达 1e11，必须开 long long

        // 第 day 天能否做够 m 束：一次线性扫描
        auto can = [&](int day) -> bool {
            int bouquets = 0, run = 0;
            for (int x : bloomDay) {
                if (x <= day) {
                    if (++run == k) {             // 凑满一束
                        run = 0;                  // 这 k 朵被消耗
                        if (++bouquets >= m) return true;
                    }
                } else {
                    run = 0;                      // 段断开，计数清零
                }
            }
            return false;
        };

        int lo = *min_element(bloomDay.begin(), bloomDay.end());
        int hi = *max_element(bloomDay.begin(), bloomDay.end());
        if (!can(hi)) return -1;                  // 全开了也做不齐
        while (lo < hi) {                         // 二分最小的可行天数
            int mid = lo + (hi - lo) / 2;
            if (can(mid)) hi = mid;
            else lo = mid + 1;
        }
        return lo;
    }
};
```

### Python

```python
class Solution:
    def minDays(self, bloomDay: list[int], m: int, k: int) -> int:
        n = len(bloomDay)
        if m * k > n:                 # 总数都不够，无解
            return -1

        def can(day: int) -> bool:
            bouquets = 0
            run = 0                   # 当前连续盛开段的长度
            for x in bloomDay:
                if x <= day:
                    run += 1
                    if run == k:      # 凑满一束
                        run = 0       # 这 k 朵被消耗
                        bouquets += 1
                        if bouquets >= m:
                            return True
                else:
                    run = 0           # 段断开，计数清零
            return False

        lo, hi = min(bloomDay), max(bloomDay)
        if not can(hi):               # 全开仍不够
            return -1
        while lo < hi:                # 二分下界
            mid = (lo + hi) // 2
            if can(mid):
                hi = mid
            else:
                lo = mid + 1
        return lo
```

## 8. 边界情况与易错点

1. **总数不足**：`m * k > n` 必须提前返回 `-1`（示例 2），否则二分会一路失败后在末尾返回一个不存在的天数。C++ 中 `m * k` 要用 `long long`，`int` 溢出后可能算出「够用」从而进入错误分支。
2. **`k == 1`**：每朵盛开的花各自成一束，答案就是第 $m$ 小的 `bloomDay`（示例 1 输出 3）。此时 `run` 每次加一就等于 `k`，逻辑无需特判，但如果把「凑满即清零」写成「`run > k` 才清零」，就会全部错判。
3. **`m == 1` 且 `k == n`**：必须 $n$ 朵全部盛开，答案恰为 $\max(\text{bloomDay})$。这也说明「答案可以等于 `hi`」，因此 `check(hi)` 的预判不是多余的防御，而是必要的分支。
4. **所有 `bloomDay` 相同**：`lo == hi`，循环一次都不执行，直接返回该值——前提是已经通过 `check(hi)`；漏掉预判时这里会返回一个未经检验的值。
5. **`n == 1`**：只可能是 $m = k = 1$，答案 `bloomDay[0]`。`min_element` 与循环边界都不会越界，但仍要保证 `m*k > n` 的判断在前。
6. **`run` 忘记清零**：这是本题最高频的 WA。`[7,7,7,7,12,7,7]`、$k=3$ 时若跨段续算，第 7 天会被算成 $\lfloor 7/3 \rfloor = 2$ 束，答案错答成 7。
7. **二分死循环或漏解**：`mid` 向下取整 + `hi = mid / lo = mid + 1` 是配套写法；若把可行分支写成 `lo = mid`，在 `hi = lo + 1` 时 `mid` 恒等于 `lo`，会死循环。
8. **返回 `-1` 的遗漏**：二分本身只会在 $[\min, \max]$ 内收敛，它**不会**自己发现「无解」，必须有 `check(hi)` 或循环后补判，否则会把最大值当成答案返回。
9. **`check` 里不要真的去构造花束列表**：本题只需计数，用两个整型计数器即可，$O(1)$ 空间；用 `vector` 收集花束会在最坏情况多出 $O(m)$ 的内存与分配开销。

**延伸思考**：① 若每朵花有「保鲜期」（盛开后只能维持若干天），判定就不再单调，需要改成滑动窗口 + 区间维护，二分答案失效；② 若每束花的花可以在**任意**位置（不要求相邻），问题退化为「第 $m\cdot k$ 小的开花日」，只需排序后取第 $mk$ 个元素；③ 若要求恰好 $m$ 束而非至少 $m$ 束，可先证明「能做 $\ge m$ 束 $\Rightarrow$ 能做恰好 $m$ 束」（从已有方案中任取 $m$ 束即可），所以本题的判定对两个版本都成立；④ 若把 $k$ 改成每束要求**不同的**指定长度 $k_1, k_2, \dots, k_m$，问题变成带约束的段划分，需要 DP 或在分段上做贪心匹配，二分不再够用。
