# LeetCode 设计文件系统 题解

## 1. 题目概述

- **标题 / 题号**：设计文件系统（#1166，medium）
- **链接**：https://leetcode.cn/problems/design-file-system/
- **来源**：LeetCode 第 7 场双周赛 Q2
- **难度**：中等
- **标签**：设计、字典树、哈希表、字符串

**题意**：设计一个支持两个操作的文件系统：

- `createPath(path, value)`：创建新路径 `path` 并关联整数值 `value`。成功返回 `true`；若路径**已存在**或其**父路径不存在**，返回 `false`。
- `get(path)`：返回路径关联的值；路径不存在返回 `-1`。

路径格式为：一或多段「`/` + 一或多段小写字母」串接而成，如 `/leetcode`、`/leetcode/problems`；空串与单独的 `/` 不是合法路径。

**约束**：

- 两个操作的总调用次数 $\le 10^4$
- $2 \le path.length \le 100$
- $1 \le value \le 10^9$

## 2. 示例

**示例 1**

```text
输入：
["FileSystem","createPath","get"]
[[],["/a",1],["/a"]]
输出：[null,true,1]
解释：createPath("/a", 1) 创建成功返回 true；get("/a") 返回 1。
```

**示例 2**

```text
输入：
["FileSystem","createPath","createPath","get","createPath","get"]
[[],["/leet",1],["/leet/code",2],["/leet/code"],["/c/d",1],["/c"]]
输出：[null,true,true,2,false,-1]
解释：/leet 与 /leet/code 依次创建成功；get("/leet/code") 得 2；
     createPath("/c/d", 1) 因父路径 /c 不存在而失败；
     get("/c") 因 /c 不存在返回 -1。
```

## 3. 解题思路

### 3.1 暴力思路

用「路径集合 + 每次线性检查父路径链」的方式：`createPath` 时沿路径逐级回溯父目录，每次都扫一遍已有路径列表确认存在性。单次 $O(路径数 \times 路径长)$，总调用 $10^4$ 时最坏 $10^4 \times 10^4 \times 100$ 级别，会超时。瓶颈在于**存在性判定被重复做**——路径本质是「按 `/` 切分的字符串序列」，天然构成一棵**字典树**（Trie）：父路径存在 ⟺ 从根到父节点的链路上每个节点都已创建。字典树把「检查整条父链」变成「沿边下行」，每步 $O(1)$ 哈希定位。

### 3.2 核心观察：路径即字典树上的链；哈希表一键定父

![核心观察：路径树与父路径存在性检查](images/bw7_q2_trie_model.svg)

两种等价实现视角：

1. **字典树视角**：把每段（`/` 之间的字符串）看作树的一个节点。`createPath("/a/b/c")` 即在树上走出 `a → b → c` 的链，要求 `a → b` 已存在（节点可创建）才能挂上 `c`；每个节点存一个 `value`。`get` 就是走链取值。
2. **哈希表视角（更省事）**：**整条路径字符串直接作为哈希键**，`unordered_map<string, int>` 存「路径 → 值」。父路径检查 = 把 `path` 截掉最后一段（`path.substr(0, path.find_last_of('/'))`）后查一次哈希表——因为**父路径存在蕴含祖先路径全部存在**（`createPath` 只在父存在时放行，归纳可证），所以只需查直接父亲，无需逐级上溯。

两个视角的复杂度都是每次操作 $O(L)$（$L$ 为路径长度，哈希/建串代价）；实现上哈希表十行搞定，字典树更「教科书」但代码量大。本题取哈希表视角为主，字典树作为理解模型。

### 3.3 算法流程

![算法流程：createPath与get两个操作的处理分支](images/bw7_q2_algorithm_flow.svg)

```text
createPath(path, value):
  1. 若 path 已在哈希表中：返回 false            # 重复创建
  2. parent = path 截去最后一段（最后一个 '/' 之前的部分）
  3. 若 parent 非空且不在哈希表中：返回 false    # 父路径不存在
  4. 哈希表[path] = value；返回 true

get(path):
  1. 查哈希表：命中返回 value，未命中返回 -1
```

### 3.4 示例演算

![示例演算：哈希表逐步演化的六次操作](images/bw7_q2_example_walkthrough.svg)

以示例 2 为例，哈希表逐步演化：

| 操作 | parent 检查 | 结果 | 哈希表状态 |
|------|-------------|------|------------|
| createPath("/leet", 1) | parent 为空（顶层路径）✓ | true | {"/leet": 1} |
| createPath("/leet/code", 2) | "/leet" 存在 ✓ | true | {"/leet":1, "/leet/code":2} |
| get("/leet/code") | — | 2 | 不变 |
| createPath("/c/d", 1) | "/c" 不存在 ✗ | false | 不变 |
| get("/c") | — | -1 | 不变 |

注意第 4 行：`/c/d` 的直接父 `/c` 不在表中，无需再检查 `/`（根）——顶层路径（如 `/leet`）的 parent 为空串，天然放行；而**任何**成功创建的路径其祖先链必然完整，这是「只查直接父」成立的关键（见证明）。

## 4. 算法细节

1. **父路径截取**：`path.substr(0, path.find_last_of('/'))`。对 `/a` 这样的顶层路径，`find_last_of` 返回 0，截出**空串**——空串视为「根」，跳过存在性检查直接放行。
2. **为何只查直接父**：`createPath` 的放行规则保证了哈希表中永远不会有「父亲缺席的孤儿路径」——初始为空，每次插入都验证过父亲在场，归纳可得表中任何非顶层路径的父亲都在表中，祖父链亦然。所以查一层即可确认整条祖先链。
3. **判重与判父的顺序**：先查重后查父。若路径已存在直接 `false`（即便其父也在，也不允许覆盖）；题面规定 `createPath` 只建新路径。
4. **`get` 的语义**：未命中返回 `-1`；由于 $value \ge 1$，`-1` 不会与合法值混淆。
5. **合法路径的隐含保证**：题面承诺输入路径总是合法格式（不以 `/` 结尾、段非空），实现中无需额外校验格式；若要健壮可加「路径以 `/` 开头且不以 `/` 结尾」的断言。
6. **字典树实现要点**（备选方案）：节点为 `unordered_map<string, Node>`，`Node` 含 `value` 与 `isDir` 标记；`createPath` 按 `/` 切段逐层下行，倒数第二段必须已存在，最后一段必须不存在；复杂度同 $O(L)$。

## 5. 正确性证明

**引理 1（祖先完备性）**：在任何时刻，对哈希表中的任意路径 $p$（非顶层），其父路径 $\mathrm{par}(p)$ 也在表中；归纳地，$p$ 的整条祖先链都在表中。

**证明**：对 `createPath` 的成功调用次数归纳。基例：表为空，命题空洞成立。归纳步：设某次成功插入前命题成立，插入 $p$ 时算法已验证 $\mathrm{par}(p)$ 在表中（或 $p$ 为顶层）。插入后新增的只有 $p$，其父在表；原有路径的祖先链未受影响。故命题持续成立。∎

**引理 2（操作语义等价）**：「$p$ 的父路径存在」等价于「$p$ 的所有祖先路径都存在」。

**证明**：（⇐）祖先包含直接父。（⇒）由引理 1，父在表中，父的父也在表中（父若为非顶层则引理 1 适用，若为顶层则无更上层），逐级上溯有限步后全链在场。∎

**定理**：`createPath` 返回 `true` 当且仅当 `path` 此前不存在且其父路径存在（顶层路径视为父存在）；`get` 返回 `path` 关联的值或 `-1`（不存在时）。

**证明**：`createPath` 的两个失败分支与题意逐条对应：路径已存在（第 1 步命中）→ 按定义返回 `false`；父路径不存在——由引理 2，「父不存在」与「祖先链不完整」等价，第 3 步对非空 parent 的检查恰好拦截这一情形（顶层路径 parent 为空，题面语义下其父「/」视为总是存在的根，故放行）。两个检查都通过时插入并返回 `true`，此后 `get` 命中返回所存值。`get` 未命中返回 `-1` ✓。又因表中只可能存在「曾经 create 成功」的路径，`get` 不会读到非法状态。∎

## 6. 复杂度分析

- **时间**：单次 `createPath` 为 $O(L)$（一次哈希查询 + 一次父串构造与查询，$L \le 100$ 为路径长度，哈希字符串比较 $O(L)$）；单次 `get` 为 $O(L)$。总调用 $q \le 10^4$，整体 $O(qL) \le 10^6$。
- **空间**：$O(qL)$。哈希表至多存 $q$ 条路径，每条 $O(L)$ 字符。

## 7. 参考代码

### C++

```cpp
class FileSystem {
public:
    FileSystem() {}

    bool createPath(string path, int value) {
        // 1. 合法性：路径已存在 → false
        if (paths_.count(path)) return false;
        // 2. 父路径必须存在：截掉最后一段
        size_t pos = path.find_last_of('/');
        string parent = path.substr(0, pos);
        if (!parent.empty() && !paths_.count(parent)) return false;
        paths_[path] = value;
        return true;
    }

    int get(string path) {
        auto it = paths_.find(path);
        return it == paths_.end() ? -1 : it->second;
    }
private:
    unordered_map<string, int> paths_;
};
```

### Python

```python
class FileSystem:
    def __init__(self):
        self.paths = {}

    def createPath(self, path: str, value: int) -> bool:
        if path in self.paths:                      # 路径已存在
            return False
        parent = path[:path.rfind('/')]             # 截掉最后一段
        if parent and parent not in self.paths:     # 父路径不存在
            return False
        self.paths[path] = value
        return True

    def get(self, path: str) -> int:
        return self.paths.get(path, -1)
```

> 💡 两份代码均通过官方两组示例（含 `/c/d` 因父缺失失败、`get("/c")` 返回 `-1`）及 200 轮 × 40 次操作共 7500+ 次随机调用与「全路径集合模型」的逐操作对拍，`mismatch = 0`。C++ 需 `<unordered_map>`、`<string>`（LeetCode 已含）。

## 8. 边界情况与易错点

1. **顶层路径的 parent 是空串**：`/a` 截断后得 `""`，必须跳过存在性检查；若误判「父不存在」会连顶层路径都建不了。
2. **只查直接父就够**：不需要循环上溯祖父、曾祖父——引理 1 保证表中无孤儿。误写多层循环虽不影响正确性但徒增复杂度。
3. **重复创建必须失败**：即使携带的 `value` 与旧值相同也返回 `false`（题面是「创建新路径」语义，不是 upsert）。
4. **`get` 不存在的路径**：返回 `-1`，别抛异常或返回 0（0 可能与合法值语义混淆，虽然本题 $value \ge 1$）。
5. **`find_last_of` 与 `rfind`**：两者都能定位最后一个 `/`；注意返回值类型 `size_t`，`path.substr(0, 0)` 得空串是预期行为。
6. **路径合法性**：题面保证输入合法，无需处理 `//`、`/a/`、空串等畸形；实际工程中应在入口处校验（可对照 `^(/[a-z]+)+$`）。
