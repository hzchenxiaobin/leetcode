# LeetCode 避免洪水泛滥 题解

## 1. 题目概述

- **标题 / 题号**：避免洪水泛滥（#1488，medium）
- **链接**：https://leetcode.cn/problems/avoid-flood-in-the-city/
- **来源**：LeetCode 第 194 场周赛 Q3
- **难度**：中等
- **标签**：贪心，数组，哈希表，二分查找，堆（优先队列）

**题意**：有 $10^9$ 个湖，初始全空。第 $i$ 天的天气由 `rains[i]` 描述：`rains[i] = x > 0` 表示湖 $x$ 上下雨——若该湖此刻是空的就被灌满，若**已经是满的**就发生洪水；`rains[i] = 0` 表示当天不下雨，你**必须**挑一个湖把它抽干（抽满湖则变空，抽空湖则什么也不发生）。要求给每个零天指定一个湖号，使得任何时刻都不发生洪水；若不可能则返回空数组，若可行则返回任意一种方案。有雨的那天答案固定为 $-1$。

**约束**：

- $1 \le \text{rains.length} \le 10^5$
- $0 \le \text{rains}[i] \le 10^9$

湖的编号可以到 $10^9$，因此**不能**用数组按湖号存状态，必须用哈希表；$n \le 10^5$ 则要求 $O(n \log n)$ 以内的做法。

## 2. 示例

**示例 1**

```text
输入：rains = [1,2,3,4]
输出：[-1,-1,-1,-1]
解释：四天各淋湿一个不同的湖，没有零天可用，也没有湖被淋第二次，不会洪水。
```

**示例 2**

```text
输入：rains = [1,2,0,0,2,1]
输出：[-1,-1,2,1,-1,-1]
解释：第 2 天抽干湖 2、第 3 天抽干湖 1，
      之后第 4、5 天湖 2 与湖 1 都是空的，平安淋满。
      [-1,-1,1,2,-1,-1] 也是合法答案。
```

**示例 3**

```text
输入：rains = [1,2,0,1,2]
输出：[]
解释：只有第 2 天一个零天，而湖 1、湖 2 都要在第 1 天之后再次下雨，
      一个零天救不了两个湖，无论抽哪个都会让另一个淹掉。
```

## 3. 解题思路

### 3.1 暴力思路

最直白的是搜：每个零天枚举抽哪个湖。$k$ 个零天、$L$ 种编号就是 $L^k$ 种方案，$k$ 与 $L$ 都能到 $10^5$，指数级爆炸，连搜索树都建不出来。

换成匹配视角会好一些：把「每次非首次降雨」看成一个必须被处理的活，把零天看成资源，两者连边表示「这个零天来得及时」，然后跑二分图匹配。可惜边数最坏是 $O(n^2) = 10^{10}$，一样过不去。

还有一个几乎所有人第一反应的贪心：**每个零天抽「最近一次被灌满的那个湖」**（LIFO）。它在示例 2 上恰好是对的，但会被反例打穿：

```text
rains = [1,2,0,1,0,2]
LIFO：第 2 天抽最近的湖 2 → 第 3 天湖 1 仍是满的，洪水
正解：第 2 天抽湖 1，第 3 天湖 1 重新淋满，第 4 天抽湖 2，第 5 天湖 2 淋满
答案：[-1,-1,1,-1,2,-1]
```

问题出在「最近」这个序：真正决定生死的是**这个湖下一次什么时候再下雨**，不是它上一次什么时候被灌满。

### 3.2 核心观察：每次非首次降雨都是一段「待覆盖区间」

![任务区间模型：零天是唯一的处理器](images/wc194_q3_requirement_intervals.svg)

设第 $i$ 天下雨落在湖 $x$ 上，该湖**上一次**下雨是第 $l$ 天。在第 $l$ 天之后、第 $i$ 天之前，湖 $x$ 一直满着，只有某个零天把 $x$ 抽干才能腾出空间。于是这次降雨产生一个**任务**：必须占用一个零天 $d$，满足

$$l < d < i$$

并且一个零天只能服务一个任务（一天只能抽一个湖）。任务的**截止期**就是这次降雨的日子 $i$——晚了就淹了；**释放时间**是上一次降雨的日子 $l$。

于是问题被精确翻译成调度问题：**单位时长的任务，带释放时间与截止期，机器按时间顺序逐个到货**。经典结论在这里同样成立：**最早截止期优先（EDF）** 是最优策略——每个零天去服务「下次下雨最早」的那个满湖。

### 3.3 算法流程：EDF + 小顶堆

![EDF 流程图](images/wc194_q3_edf_flow.svg)

1. **预处理下一次降雨**：反向扫描 `rains`，用哈希表记录每个湖最近出现的下标，得到 `nxt[i]`——第 $i$ 天下雨时同湖下一次下雨的下标，若没有则记 $n$。它正是第 $i$ 天这次降雨的截止期。
2. **维护待办任务**：哈希表 `deadline[x]` 表示「湖 $x$ 现在是满的，且它的截止期是 `deadline[x]`」；小顶堆按截止期存 `(nxt[i], x)`。
3. **逐天处理**：
   - `rains[i] == 0`：堆非空就弹出堆顶 `(d, L)`，令 `ans[i] = L`，并把 $L$ 从 `deadline` 中删除；堆空说明没有任何湖等着被救，随便填一个湖号（如 $1$）即可，抽水只会让湖更空。
   - `rains[i] = x > 0`：若 $x$ 仍在 `deadline` 中，说明它从上次降雨起一直满着、截止期已过，**立刻返回空数组**；否则写入 `deadline[x] = nxt[i]`、把 `(nxt[i], x)` 压堆，并令 `ans[i] = -1`。
4. 循环结束，所有零天都填好了值，返回 `ans`。

### 3.4 示例演算

![示例演算：rains = [1,2,0,0,2,1] 与反例](images/wc194_q3_walkthrough.svg)

对 `rains = [1,2,0,0,2,1]` 走一遍：第 0、1 天分别把湖 1（截止期 5）、湖 2（截止期 4）压堆；第 2 天零天，堆顶是截止期 4 的湖 2，抽干它；第 3 天零天，抽干截止期 5 的湖 1；后两天两个湖都是空的，直接淋满。得到 `[-1,-1,2,1,-1,-1]`。

对反例 `rains = [1,2,0,1,2]`：第 2 天只有一个零天，堆顶是截止期 3 的湖 1（比湖 2 的 4 更早），抽湖 1 之后湖 2 的截止期 4 无人覆盖，第 4 天湖 2 淋雨时它仍是满的，返回空数组。可见「先服务截止期早的」并不是在选择「哪一天抽」上犯错——它恰恰是被逼到无解时最早暴露矛盾的那条路。

## 4. 算法细节

1. **`nxt` 的求法**：反向遍历，用哈希表 `pos` 记录每个湖在当前下标之后最近出现的位置。`nxt[i] = pos.get(rains[i], n)`，然后 `pos[rains[i]] = i`。只需一次 $O(n)$ 扫描。
2. **状态一致性**：堆里存 `(截止期, 湖号)`，`deadline` 存 `湖号 → 截止期`，两者必须同步——弹出堆顶后立刻从 `deadline` 删除；压堆时同时写入 `deadline`。否则「湖是否还是满的」判断会和堆脱节。
3. **每个湖最多一个堆条目**：湖被抽干后条目已弹出，再次降雨时才会重新压入，所以堆中不会出现同一湖的重复条目，也无需懒删除。
4. **判断洪水用「是否仍在 `deadline` 中」**，而不是「堆顶是否等于它」：堆里还可能有更晚截止期的湖，不能据此判断某个湖是否已被抽干。
5. **剩余零天填 $1$**：题目要求 `ans.length == rains.length` 且每个零天都必须给出湖号；堆空说明没有任何湖等着被救，此时抽哪个湖都不会引发洪水（抽空湖无事发生，抽满湖只会让它更安全），统一填 $1$ 最省事。
6. **$n$ 当无穷大**：最后一手降雨对应的湖没有任何下次，`nxt[i] = n`，它永远不会「到期」，堆里留着也不影响结果。
7. **不要用湖号做数组下标**：$10^9$ 个湖开不下，C++ 用 `unordered_map`（可 `reserve`）、Python 用 `dict`。

## 5. 正确性证明

**引理 1（任务模型等价）**：存在合法的抽水方案，当且仅当存在一个把每个任务（每次非首次降雨）分别分配到其区间 $(l, i)$ 内、且两两不同的零天的分配。

**证明**：

- （必要性）设方案合法。对任一任务，其区间 $(l, i)$ 内若没有任何零天抽干该湖，则湖从第 $l$ 天灌满后一直满着，第 $i$ 天再次淋雨必然洪水，矛盾；且一天只能抽一个湖，故不同任务占用的零天互不相同。
- （充分性）设分配满足条件。任意一天下雨时，该湖若此前下过雨，则由分配它已在区间内某零天被抽干；若此前没下过雨，它从未满过。抽水操作只会让湖变空或保持空，不会凭空灌水。故任意下雨时刻湖都是空的，永不洪水。∎

**引理 2（EDF 与可行方案兼容）**：设贪心当前遇到零天 $d$，待办堆中截止期最小的任务是 $A$。若存在可行分配 $S$ 与贪心在此前所有零天上的选择完全相同，则存在可行分配与贪心在 $d$ 上也相同。

**证明**：设 $S$ 在 $d$ 这一天服务任务 $C$，在某个更晚的零天 $d'$ 服务 $A$（$A$ 尚未被服务，故这样的 $d'$ 存在）。

- 把 $A$ 改到 $d$：$A$ 已在堆中，说明它的释放时间 $l_A < d$；它的截止期 $r_A$ 是某次降雨日，而 $d$ 是零天，若 $r_A \le d$ 则那次降雨发生时湖仍满，贪心早已返回空数组、与「$S$ 存在」矛盾，故 $r_A > d$。于是 $d \in (l_A, r_A)$。
- 把 $C$ 改到 $d'$：$C$ 在 $d$ 时已在堆中，故 $l_C < d < d'$；又 $A$ 是堆中截止期最小者，$C$ 当时也在堆中，故 $r_A \le r_C$，而 $d' < r_A$（$d'$ 是 $S$ 中服务 $A$ 的零天），于是 $d' < r_C$。故 $d' \in (l_C, r_C)$。

交换后两个任务各自仍在自己的区间内，其余任务不动，可行性与此前选择不变。∎

**引理 3（无解判定精确）**：算法返回空数组当且仅当不存在合法方案；否则算法构造的 `ans` 合法。

**证明**：

- 若算法在第 $i$ 天（有雨，湖 $x$）发现 $x$ 仍在 `deadline` 中：由引理 2 归纳可知，任何可行分配都与贪心在所有更早的零天上选择相同，于是 $x$ 从上次降雨起从未被抽干，第 $i$ 天必洪水，故无解。
- 若算法正常结束：每次弹堆时分配都落在任务区间内——任务的释放时间就是它上一次降雨的日子，任务只在降雨之后才进堆，故 $l_A < d$；又 $d < r_A$，因为 $r_A$ 是某次降雨的日子而 $d$ 是零天，若 $r_A < d$ 则那次降雨时湖仍满，算法早已返回空数组。同时每个零天最多服务一个任务，符合引理 1 的充分条件；堆空时填 $1$ 只是抽干一个无关湖，不改变任何湖的满/空状态。∎

**定理**：算法在可行时输出一个合法的 `ans`（长度与 `rains` 相同，雨天为 $-1$、零天为被抽干的湖），在不可行时输出空数组。

**证明**：由引理 3 直接得到；长度方面，循环对每个下标都赋了值。∎

## 6. 复杂度分析

- **时间**：$O(n \log n)$。反向预处理 $O(n)$；每天最多一次堆操作，每次 $O(\log n)$；哈希表操作为均摊 $O(1)$。
- **空间**：$O(n)$。`nxt` 数组 $O(n)$，`deadline` 哈希表最多 $O(n)$ 项，小顶堆最多 $O(n)$ 项，输出数组 $O(n)$。

## 7. 参考代码

### C++

```cpp
#include <vector>
#include <queue>
#include <unordered_map>
using namespace std;

class Solution {
public:
    vector<int> avoidFlood(vector<int>& rains) {
        int n = rains.size();
        vector<int> nxt(n, n);                 // 同湖下一次下雨的下标，n 视为无穷
        unordered_map<int, int> pos;
        for (int i = n - 1; i >= 0; --i) {
            if (rains[i] > 0) {
                auto it = pos.find(rains[i]);
                if (it != pos.end()) nxt[i] = it->second;
                pos[rains[i]] = i;
            }
        }

        vector<int> ans(n, -1);
        unordered_map<int, int> deadline;      // 满湖 -> 截止期（下次下雨日）
        priority_queue<pair<int, int>, vector<pair<int, int>>, greater<pair<int, int>>> pq;
        for (int i = 0; i < n; ++i) {
            if (rains[i] == 0) {
                if (!pq.empty()) {
                    int lake = pq.top().second; pq.pop();
                    ans[i] = lake;
                    deadline.erase(lake);
                } else {
                    ans[i] = 1;                // 抽干一个空湖，无副作用
                }
            } else {
                int x = rains[i];
                if (deadline.count(x)) return {};   // 它还是满的，洪水不可避免
                deadline[x] = nxt[i];
                pq.push({nxt[i], x});
            }
        }
        return ans;
    }
};
```

### Python

```python
import heapq
from typing import List

class Solution:
    def avoidFlood(self, rains: List[int]) -> List[int]:
        n = len(rains)
        nxt = [n] * n                      # 同湖下一次下雨的下标，n 视为无穷
        pos = {}
        for i in range(n - 1, -1, -1):
            x = rains[i]
            if x > 0:
                if x in pos:
                    nxt[i] = pos[x]
                pos[x] = i

        ans = [-1] * n
        deadline = {}                      # 满湖 -> 截止期（下次下雨日）
        heap = []                          # (截止期, 湖)
        for i, x in enumerate(rains):
            if x == 0:
                if heap:
                    d, lake = heapq.heappop(heap)
                    ans[i] = lake
                    del deadline[lake]
                else:
                    ans[i] = 1             # 抽干一个空湖，无副作用
            else:
                if x in deadline:
                    return []              # 它还是满的，洪水不可避免
                deadline[x] = nxt[i]
                heapq.heappush(heap, (nxt[i], x))
        return ans
```

## 8. 边界情况与易错点

1. **湖号过大**：`rains[i]` 可到 $10^9$，用数组当桶会直接 MLE；必须用哈希表存「湖 → 截止期 / 上次位置」。
2. **必须给每个零天填值**：漏填会让 `ans` 长度不符或出现 $0$（非法湖号）。堆空时统一填 $1$，因为抽干任何湖都不会造成洪水。
3. **洪水判定不能看堆顶**：堆里可能还有更晚截止期的湖，判定「湖 $x$ 是否仍满」只能查 `deadline`。
4. **用 $n$ 当无穷大**：最后一手降雨的湖 `nxt[i] = n`，不会被当作「马上要到期的任务」；若误写成 $-1$ 或 $10^9$，堆的排序与判定都会出错。
5. **同一湖多次降雨**：每次非首次降雨都会产生新任务，弹堆后必须同步 `deadline.erase`，否则下次降雨会被误判为「湖还满着」而错误地返回空数组。
6. **零天在雨前**：例如 `rains = [0,1]`，第 0 天堆是空的，答案填 $1$；这类「白送的零天」不影响后面的判断。
7. **栈式直觉的陷阱**：LIFO（每个零天抽最近灌满的湖）在 `[1,2,0,1,0,2]` 上翻车，正确依据是**下一次下雨时间**而不是上一次。
