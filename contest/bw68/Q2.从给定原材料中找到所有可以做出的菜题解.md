# LeetCode 从给定原材料中找到所有可以做出的菜 题解

## 1. 题目概述

- **标题 / 题号**：从给定原材料中找到所有可以做出的菜（#2115，medium）
- **链接**：https://leetcode.cn/problems/find-all-possible-recipes-from-given-supplies/
- **来源**：LeetCode 第 68 场双周赛 Q2
- **难度**：中等
- **标签**：图、拓扑排序、数组、哈希表、字符串、有向无环图

**题意**：有 $n$ 道菜。`recipes[i]` 是第 $i$ 道菜的名字，`ingredients[i]` 是做它所需的**全部**原材料；一份菜也可以充当**其他菜的原材料**。初始拥有 `supplies` 中的全部原材料且**每种无限多**。返回所有可以做出的菜，顺序任意。

**约束**：

- $n == recipes.length == ingredients.length$，$1 \le n \le 100$
- $1 \le ingredients[i].length, supplies.length \le 100$
- $1 \le$ 各字符串长度 $\le 10$，只含小写字母
- `recipes` 与 `supplies` 中的值互不相同
- `ingredients[i]` 内的字符串互不相同

## 2. 示例

**示例 1**

```text
输入：recipes = ["bread"], ingredients = [["yeast","flour"]], supplies = ["yeast","flour","corn"]
输出：["bread"]
解释：yeast 和 flour 都在初始供应里，bread 可以做出来。
```

**示例 2**

```text
输入：recipes = ["bread","sandwich"], ingredients = [["yeast","flour"],["bread","meat"]],
     supplies = ["yeast","flour","meat"]
输出：["bread","sandwich"]
解释：先做出 bread，再把它当作原料做出 sandwich。
```

**示例 3**

```text
输入：recipes = ["bread","sandwich","burger"],
     ingredients = [["yeast","flour"],["bread","meat"],["sandwich","meat","bread"]],
     supplies = ["yeast","flour","meat"]
输出：["bread","sandwich","burger"]
解释：bread → sandwich → burger 依次解锁。
```

**示例 4**

```text
输入：recipes = ["bread"], ingredients = [["yeast","flour"]], supplies = ["yeast"]
输出：[]
解释：缺 flour，bread 做不出来。
```

## 3. 解题思路

### 3.1 暴力思路

按题面直译做**不动点传播**：反复整轮扫描所有未做出的菜，只要某道菜的全部原料当前都「在手上」（初始供应 ∪ 已做出的菜），就把它做出来、加入手中集合；直到某一整轮没有任何新增为止。设 $n$ 道菜、每道菜平均 $L$ 个原料，最坏要扫 $n$ 轮，每轮 $O(nL)$，总计 $O(n^2 L)$——本题 $n \le 100$ 能过，但它是「无信息地重试」：一轮里同一道菜的依赖可能早已齐备，却要等到下一轮才被发现。把它升级为一次系统遍历，就是拓扑排序。

### 3.2 核心观察：依赖关系建图 + 入度归零

![核心观察：原料为「免费节点」，菜之间的依赖构成 DAG，入度 = 缺失原料数](images/bw68_q2_topo_model.svg)

把「做出菜 $j$」看作解锁节点 $j$，解锁条件是它的每个原料都已就绪：

- 原料若是**初始供应**——免费，不构成任何依赖；
- 原料若是**另一道菜** $i$——连边 $i \to j$，表示「$i$ 做出来后 $j$ 的一个缺口被补上」；
- 原料若是**根本不存在的东西**（既不在供应也不在食谱里）——永远补不上的缺口，把 $j$ 卡死。

于是定义 $indeg[j]$ = 菜 $j$ 的原料中**非初始供应**的个数，即缺口数。$indeg[j] = 0$ 的菜一开始就能做；每做出一道菜 $i$，它就作为一种「新原料」抵达所有依赖它的菜，把它们的入度减一。这正是 **Kahn 拓扑排序**：入度归零 → 入队 → 出队即产出。做不出来的菜（含**互相依赖成环**的菜、缺幽灵原料的菜）入度永远到不了 0，天然被排除。

### 3.3 算法流程

![算法流程：Kahn 拓扑排序三步——建图统计入度、入度为 0 入队、出队减度](images/bw68_q2_kahn_flow.svg)

```text
1. have = supplies 的哈希集合
2. 对每道菜 i、每个原料 ing ∈ ingredients[i]：
       若 ing ∈ have：跳过（免费）
       否则：need[ing] 追加 i；indeg[i] += 1
3. 所有 indeg[i] == 0 的菜入队
4. 队列非空时：
       出队 i，加入答案
       对 need[recipes[i]] 中的每个 j：--indeg[j]，减到 0 则入队
5. 返回答案（顺序任意）
```

### 3.4 示例演算

![示例演算：示例 3 的 bread → sandwich → burger 解锁过程](images/bw68_q2_example_walkthrough.svg)

以示例 3 为例。初始入度：`bread` 依赖 yeast、flour（都在 supplies）→ $indeg = 0$；`sandwich` 依赖 bread、meat → 缺 bread → $indeg = 1$；`burger` 依赖 sandwich、meat、bread → 缺 sandwich、bread → $indeg = 2$。

| 出队 | 答案 | 对剩余菜的解锁 |
|------|------|----------------|
| bread | bread | sandwich 的 bread 缺口补上：$indeg = 1 \to 0$，入队 |
| sandwich | bread, sandwich | burger 的 sandwich 缺口补上：$indeg = 2 \to 1$（bread 缺口上轮已补） |
| burger | bread, sandwich, burger | 队列空，结束 |

若把 `supplies` 里的 `flour` 拿走（示例 4），`bread` 的 $indeg = 1$（缺口是 flour，且没有任何菜产出 flour），队列为空，返回 `[]`。若两道菜互相以对方为原料（成环），双方的入度互相挂着，永不到 0，都不会被输出。

## 4. 算法细节

1. **入度的准确定义**：数的是「**非初始供应**的原料个数」，而不是「原料总个数」。初始就有的原料是免费资源，若计入入度会导致永远无法归零。
2. **`need` 映射的方向**：`need[原料] → [依赖它的菜下标]`，与直觉的「菜 → 原料列表」相反，这样菜 $i$ 出队时能 $O(1)$ 定位到要减度的所有后继。原料是**另一道菜的名字**时，出队后用 `need[recipes[i]]` 查询——名字作键，天然把「菜作为原料」和「菜作为菜」对上。
3. **幽灵原料不用特判**：不存在于 `recipes` 中的原料会让依赖它的菜入度永不到 0，语义自动正确；不需要先扫描一遍构造「合法原料白名单」。
4. **哈希加速**：字符串原料判断用 `unordered_set` / Python `set`，单次 $O(1)$。
5. **输出顺序**：BFS 出队序即一种合法返回序；题目接受任意顺序。
6. **图不必显式建出**：邻接结构完全隐含在 `ingredients` 里，只需要 `need` 与 `indeg` 两个辅助结构，代码量极小。

## 5. 正确性证明

**引理 1（可做菜集合 = 依赖图的闭包）**：设 $S_0$ = 初始供应集合，$S^*$ = 最终能做出的菜的集合。则 $j \in S^*$ 当且仅当存在菜序列 $j_1, j_2, \dots, j_t$（$j_t = j$），使得对每个 $j_k$，其全部原料都在 $S_0 \cup \{j_1, \dots, j_{k-1}\}$ 中（该序列同时是按此顺序实际做出的方案）。

**证明**：（⇐）对序列归纳：$j_1$ 的原料全在 $S_0$，可做出；设前 $k-1$ 道都能按序做出，则 $j_k$ 的原料都在已拥有集合中，可做出。（⇒）设 $j \in S^*$。按「可做」的定义逐道归纳：任何被做出的菜做出时其原料全部在手，而手中的非供应物都是此前做出的菜；把做出的菜按做出顺序排列，截尾到 $j$ 即得所求序列。∎

**引理 2（Kahn 出队即闭包）**：Kahn 过程中，每当菜 $i$ 入队时，其全部原料已就绪（在 $S_0 \cup$ 此前出队的菜中）；且任何满足引理 1 条件的菜最终都会出队。

**证明**：对出队序归纳。初始入队的菜 $indeg = 0$，其所有原料都是初始供应 ✓。设已出队的菜都满足条件。菜 $j$ 入队当且仅当 $indeg[j]$ 从初值（非供应原料数）被减到 0；每次减一都对应某个依赖原料（是某道菜）出队，即该原料已就绪。入度归零说明**每一个**非供应原料都已就绪，加上初始供应部分，全部原料就绪 ✓。反之，设 $j \in S^*$ 且其引理 1 序列为 $j_1, \dots, j_t$。归纳可证每个 $j_k$ 都会出队：$j_{k}$ 的非供应原料都是 $j_1..j_{k-1}$ 或更早出队的菜（或本身在 $S_0$），当它们全部出队后 $indeg[j_k]$ 减到 0，$j_k$ 必然入队并出队。∎

**定理**：算法输出集合恰为 $S^*$。

**证明**：由引理 2，凡出队的菜都属 $S^*$（其原料就绪，可实际做出），无多报；凡 $S^*$ 中的菜都会出队，无漏报。∎

## 6. 复杂度分析

- **时间**：$O\big((n + \sum |ingredients[i]|)\cdot \bar{L}\big)$ 量级，其中 $\bar{L}$ 为字符串平均长度——建图时每个原料一次哈希 $O(\bar{L})$，每条依赖边被建立、消耗各一次，加上出队后按名字哈希查询后继。代入 $n, L \le 100$、字符串 $\le 10$，总量约 $10^4$ 级别，轻松通过。
- **空间**：$O(n \cdot L)$ 量级——`need` 映射与入度数组共线性于依赖边数，加哈希集合 $O(|supplies| \cdot \bar{L})$。

## 7. 参考代码

### C++

```cpp
class Solution {
public:
    vector<string> findAllRecipes(vector<string>& recipes, vector<vector<string>>& ingredients, vector<string>& supplies) {
        int n = recipes.size();
        unordered_map<string, vector<int>> need;       // 原料名 -> 依赖它的菜下标列表
        unordered_set<string> have(supplies.begin(), supplies.end());
        vector<int> indeg(n, 0);
        for (int i = 0; i < n; ++i) {
            for (const string& ing : ingredients[i]) {
                if (have.count(ing)) continue;        // 初始就有的原料不构成依赖
                need[ing].push_back(i);               // ing 就绪后给菜 i 减一度
                ++indeg[i];
            }
        }
        queue<int> q;
        for (int i = 0; i < n; ++i)
            if (indeg[i] == 0) q.push(i);             // 只靠初始原料就能做的菜
        vector<string> ans;
        while (!q.empty()) {
            int i = q.front(); q.pop();
            ans.push_back(recipes[i]);
            for (int j : need[recipes[i]])            // 菜 i 做出来 → 它是一种「新原料」
                if (--indeg[j] == 0) q.push(j);
        }
        return ans;
    }
};
```

### Python

```python
from collections import deque

class Solution:
    def findAllRecipes(self, recipes: list[str], ingredients: list[list[str]], supplies: list[str]) -> list[str]:
        n = len(recipes)
        have = set(supplies)
        need = {}                                   # 原料名 -> 依赖它的菜下标
        indeg = [0] * n
        for i in range(n):
            for ing in ingredients[i]:
                if ing in have:
                    continue                        # 初始原料不构成依赖
                need.setdefault(ing, []).append(i)
                indeg[i] += 1
        q = deque(i for i in range(n) if indeg[i] == 0)
        ans = []
        while q:
            i = q.popleft()
            ans.append(recipes[i])
            for j in need.get(recipes[i], ()):      # 菜 i 就绪 → 充当新原料
                indeg[j] -= 1
                if indeg[j] == 0:
                    q.append(j)
        return ans
```

> 💡 两份代码均通过全部官方示例（`["bread"]`、`["bread","sandwich"]`、`["bread","sandwich","burger"]`、`[]`），并与「逐轮不动点扫描」的暴力模拟对拍 2000 组随机数据（含互相依赖成环、自我依赖、幽灵原料、链条长至 12 等形态），结果作为集合完全一致。

## 8. 边界情况与易错点

1. **入度数错对象**：把「原料总数」当入度（不排除初始供应），所有菜的入度永远高于 0，返回全空。这是本题最容易犯的错。
2. **成环**：$a$ 依赖 $b$、$b$ 依赖 $a$（或自依赖 $a$ 用到 $a$ 自己）——两者入度互相锁死，都不会输出；算法不需要任何环检测代码，拓扑排序天然把不在闭包里的点排除。
3. **幽灵原料**：原料字符串既不在 `supplies` 也不是任何 `recipes` 中的名字——它对应 `need` 里一个永远不会被触发的键，依赖它的菜被正确卡死。
4. **菜做出后是「无限原料」**：一道菜做出后可以被任意多道菜引用，`need[recipes[i]]` 记录了全部后继，减度时不要只减一个。
5. **返回顺序**：任意序都可以；但本地对拍时注意**按集合比较**而非按序列比较。
6. **字符串哈希的键**：`recipes[i]` 与 `ingredients` 里的名字必须**逐字符一致**——题目保证全小写、无前后缀差异，无需规范化；若在变体题里出现大小写混用，先统一再建图。
