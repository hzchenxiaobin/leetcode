# LeetCode 设计一个验证系统 题解

## 1. 题目概述

- **标题 / 题号**：设计一个验证系统（#1797，medium）
- **链接**：https://leetcode.cn/problems/design-authentication-manager/
- **来源**：LeetCode 第 48 场双周赛 Q2
- **难度**：中等
- **标签**：设计、哈希表、链表、双向链表

**题意**：实现验证码（token）管理系统 `AuthenticationManager`：

- `AuthenticationManager(timeToLive)`：构造并设置有效期 $ttl$（秒）；
- `generate(tokenId, currentTime)`：在 `currentTime` 时刻生成一个新验证码，它在该时刻后 $ttl$ 秒过期；
- `renew(tokenId, currentTime)`：将**未过期**的验证码 `tokenId` 续期到 `currentTime + ttl`；若它不存在或已过期则**忽略**本次操作；
- `countUnexpiredTokens(currentTime)`：返回该时刻**未过期**的验证码数目。

**过期优先规则**：若验证码在时刻 $t$ 过期，而另一操作恰好在时刻 $t$ 发生，则**过期事件优先**——即"在时刻 $t$ 已过期"意味着此时它已经不可续期、也不计入未过期数。

**约束**：

- $1 \le timeToLive \le 10^8$
- $1 \le currentTime \le 10^8$
- `generate` 的所有 `tokenId` 互不相同
- 所有调用的 `currentTime` **严格递增**
- 总调用次数不超过 2000

## 2. 示例

**示例 1**

```text
输入：
["AuthenticationManager","renew","generate","countUnexpiredTokens","generate",
 "renew","renew","countUnexpiredTokens"]
[[5],["aaa",1],["aaa",2],[6],["bbb",7],["aaa",8],["bbb",10],[15]]
输出：[null,null,null,1,null,null,null,0]
解释：
构造 ttl=5；
renew("aaa", 1)：不存在，忽略；
generate("aaa", 2)：过期时刻 2+5=7；
countUnexpiredTokens(6)：7 > 6 未过期 → 1；
generate("bbb", 7)：过期时刻 12；
renew("aaa", 8)：8 ≥ 7 已过期，忽略；
renew("bbb", 10)：12 > 10 未过期，续到 10+5=15；
countUnexpiredTokens(15)：15 ≥ 15 已过期 → 0。
```

## 3. 解题思路

### 3.1 朴素思路与其瓶颈

最"实在"的做法是每个 token 存"生成时刻"，再维护一个**过期队列**：`generate` 入队，`renew` 移除旧时刻重新入队，每次操作前把队头已过期的统统弹出。由于 `currentTime` 严格递增，用一个最小堆（按过期时刻）也可以。这些做法都对，但引入了堆/队列结构，其实题目只需要回答三件事：某 token 的**过期时刻**是多少、它**是否**还活着、活着的有**几个**——一张哈希表就够了。

### 3.2 核心观察：惰性删除——不真删，判活即可

![验证码生命周期：generate 定寿命，renew 只对未过期延长](images/bw48_q2_token_timeline.svg)

把每个 token 的**过期时刻**存进哈希表 `expire[tokenId]`，三类操作全部围绕一个统一的判活规则：

$$\text{存活} \iff \mathit{expire}[tokenId] > currentTime$$

- `generate`：直接写入 $\mathit{expire}[tokenId] = currentTime + ttl$；
- `renew`：查表存在**且**判活成立才改写为 $currentTime + ttl$，否则什么都不做；
- `count`：遍历全表统计满足判活的条目数。

过期规则"时刻 $t$ 过期优先"意味着 `expire == currentTime` 已算过期，判活必须是**严格大于**。已过期的条目**不必真的删除**：它们的存在不影响任何操作的正确性（`renew` 会被判活拦下，`count` 不会计入），下一次同名 token 的 `generate` 会直接覆盖——这就是**惰性过期**（lazy expiration）。总调用 $\le 2000$，每次 `count` 全表扫也只有 $2000 \times 2000 = 4 \times 10^6$ 次比较，毫无压力。

### 3.3 算法流程

![三个操作的处理流程：一张哈希表 + 统一判活](images/bw48_q2_operations_flow.svg)

```text
构造：记录 ttl，expire = 空哈希表
generate(tokenId, now)：expire[tokenId] = now + ttl
renew(tokenId, now)：
    若 tokenId ∈ expire 且 expire[tokenId] > now：
        expire[tokenId] = now + ttl
    否则：忽略
countUnexpiredTokens(now)：统计 expire 中值 > now 的条目数
```

### 3.4 示例演算

![官方示例回放：8 次调用的哈希表变化](images/bw48_q2_walkthrough.svg)

以官方示例逐步走：`renew("aaa",1)` 查无此键，忽略；`generate("aaa",2)` 写入 $\{"aaa": 7\}$；`count(6)` 中 $7 > 6$ 计 1；`generate("bbb",7)` 写入 $\{"aaa":7, "bbb":12\}$；`renew("aaa",8)` 中 $7 > 8$ 不成立，忽略（"aaa" 的记录留在表里但永远判死）；`renew("bbb",10)` 中 $12 > 10$ 成立，改写为 15；`count(15)` 中 $7 \le 15$、$15 \le 15$ 均过期，返回 0。输出序列与官方一致。

## 4. 算法细节

1. **判活用严格大于**：`expire > now`。"恰好等于"意味着此刻正好过期，过期事件优先，既不能续也不能计数。这是本题唯一的"坑点"，边界语义必须与题面逐字对齐。
2. **`renew` 的两道闸门**：键存在 + 未过期，缺一不可；不存在时的"忽略"不是报错，是静默 no-op。
3. **`generate` 无条件写入**：题目保证 `generate` 的 `tokenId` 互不相同，但即使重复调用，"新生成覆盖旧记录"的语义也自然成立——旧的过期时刻被替换，无需特殊处理。
4. **要不要在 `count` 里顺手清理**：可以（遍历时把 $\le now$ 的键删除），能防止表无限膨胀；但本题调用数 $\le 2000$，清理与否都不影响复杂度结论，写成清理版需要在遍历中安全删除，C++ 用迭代器 `erase` 时注意返回下一个迭代器。
5. **数据结构选型**：`unordered_map<string,int>` 均摊 $O(1)$ 增改查；`map<string,int>` 是 $O(\log m)$，$m \le 2000$ 同样轻松。若追求工程优雅可用双向链表 + 哈希定位做 $O(1)$ 过期弹出（LRU 骨架），但依赖 `currentTime` 严格递增才安全——见延伸思考。
6. **时间上限**：$currentTime \le 10^8$ 且 $ttl \le 10^8$，和不超过 $2 \times 10^8$，`int` 放得下，无需 64 位。

## 5. 正确性证明

**引理 1（过期时刻的充分刻画）**：设某 token 最近一次被 `generate` 或成功的 `renew` 操作的时刻为 $t_0$，则其真实过期时刻为 $t_0 + ttl$，且在时刻 $t$ 它未过期当且仅当 $t_0 + ttl > t$。

**证明**：`generate(tokenId, t_0)` 的语义为"$t_0$ 时刻后 $ttl$ 秒过期"，即存活区间 $[t_0, t_0 + ttl)$，时刻 $t$ 存活 $\iff t_0 \le t < t_0 + ttl \iff t_0 + ttl > t$（$t \ge t_0$ 因调用时刻递增）。`renew` 成功时按定义将存活区间替换为 $[t_0', t_0' + ttl)$，同理。故表项 $\mathit{expire}[tokenId] = t_0 + ttl$ 精确编码了该 token 的存活区间右端点（开）。∎

**引理 2（表的一致性）**：任意操作序列执行后，`expire` 中每个键 $id$ 的值等于该 token 当前真实存活区间的右端点；已被忽略的 `renew` 不破坏这一性质。

**证明**：对操作数归纳。`generate` 按定义写入右端点；`renew` 仅在键存在且 $\mathit{expire} > now$（即此刻真实存活）时改写为新的右端点，与"续期到 $now + ttl$"的语义一致；被忽略的 `renew`（键不存在或已过期）不改变任何表项，而对应 token 要么不存在、要么已死且今后永远判死（时刻只增不减），其表项虽残留但引理 1 的判活规则使它不再起作用。`count` 不修改表。∎

**定理**：`countUnexpiredTokens(now)` 返回此刻真实未过期的 token 数目。

**证明**：由引理 2，表项右端点全部正确；由引理 1，判活条件 $\mathit{expire} > now$ 与"未过期"逐字等价（含 $=$ 时过期的边界），统计其数目即为答案。∎

## 6. 复杂度分析

- **时间**：`generate`、`renew` 均摊 $O(1)$（哈希表一次定位）；`countUnexpiredTokens` $O(m)$，$m$ 为表中条目数（含惰性未删的过期项，$m \le$ 总调用数 $\le 2000$）。整体最坏 $2000 \times 2000 = 4 \times 10^6$ 次比较，远低于时限。
- **空间**：$O(m)$。哈希表至多存 2000 个条目；惰性不删使 $m$ 达到生成过的 token 总数而非存活数，量级相同。

## 7. 参考代码

### C++

```cpp
class AuthenticationManager {
    int ttl;
    unordered_map<string, int> expire;   // tokenId -> 过期时刻
public:
    AuthenticationManager(int timeToLive) : ttl(timeToLive) {}

    void generate(string tokenId, int currentTime) {
        expire[tokenId] = currentTime + ttl;        // 惰性写入，不主动清理
    }

    void renew(string tokenId, int currentTime) {
        auto it = expire.find(tokenId);
        if (it != expire.end() && it->second > currentTime)  // 未过期才续期
            it->second = currentTime + ttl;
    }

    int countUnexpiredTokens(int currentTime) {
        int cnt = 0;
        for (auto& [id, t] : expire)                // 过期优先：t == now 已过期
            if (t > currentTime) ++cnt;
        return cnt;
    }
};
```

### Python

```python
class AuthenticationManager:
    def __init__(self, timeToLive: int):
        self.ttl = timeToLive
        self.expire = {}                      # tokenId -> 过期时刻

    def generate(self, tokenId: str, currentTime: int) -> None:
        self.expire[tokenId] = currentTime + self.ttl

    def renew(self, tokenId: str, currentTime: int) -> None:
        t = self.expire.get(tokenId)
        if t is not None and t > currentTime:  # 未过期才续期
            self.expire[tokenId] = currentTime + self.ttl

    def countUnexpiredTokens(self, currentTime: int) -> int:
        return sum(1 for t in self.expire.values() if t > currentTime)
```

> 💡 两份代码均通过官方完整调用序列回放（输出 `[null,null,null,1,null,null,null,0]`），并额外通过边界用例：`renew` 恰在过期时刻被忽略、`count` 恰在过期时刻计数为 0（输出 `0 1 0 1`），与逐条手推一致。

## 8. 边界情况与易错点

1. **过期边界的开闭**：判活必须是 $\mathit{expire} > now$（严格大于）。若写成 $\ge$，官方示例中 `renew("bbb",10)` 与 `count(15)` 的语义就全错了——15 恰是 "bbb" 的过期时刻，按"过期优先"应答 0。
2. **对不存在的 token `renew`**：静默忽略，不创建、不报错。
3. **对已过期 token `renew`**：同样忽略——过期记录残留在表里正是惰性方案的一部分，别"顺手"把它复活。
4. **`generate` 覆盖语义**：题目保证新 `tokenId` 唯一；若你的实现允许重复生成同名 token，"直接覆盖"就是正确行为。
5. **时刻严格递增是免费午餐**：它保证了惰性方案的正确性（旧记录只可能越来越"死"）。若题目允许时刻回退，惰性判活依然正确（判活只看当前时刻与过期时刻的比较，与历史无关），但如果想做"过期即弹出"的队列/链表方案就必须依赖递增假设。
6. **复杂度不要想多**：不需要堆、不需要平衡树、更不需要线段树；任何把 `count` 做到 $O(\log m)$ 的结构在本题 $m \le 2000$ 的规模下都是过度设计。
7. **返回类型**：`count` 返回条数，`generate`/`renew` 无返回值，接口与 `metaData` 中 `void` / `int` 严格对齐。
