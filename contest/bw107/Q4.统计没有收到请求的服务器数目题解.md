# LeetCode 统计没有收到请求的服务器数目 题解

## 1. 题目概述

- **标题 / 题号**：统计没有收到请求的服务器数目（#2747，medium）
- **链接**：https://leetcode.cn/problems/count-zero-request-servers/
- **来源**：LeetCode 第 107 场双周赛 Q4
- **难度**：中等
- **标签**：数组、哈希表、排序、滑动窗口

**题意**：有 $n$ 台服务器，`logs[i] = [server_id, time]` 表示某服务器在时刻 `time` 收到一个请求。给定窗口长度 $x$ 与查询数组 `queries`，对每个查询 $q$ 统计**闭区间 $[q - x, q]$ 内没有收到任何请求**的服务器数目，按查询顺序返回。

**约束**：

- $1 \le n \le 10^5$
- $1 \le logs.length \le 10^5$
- $1 \le queries.length \le 10^5$
- $1 \le logs[i][0] \le n$，$1 \le logs[i][1] \le 10^6$
- $1 \le x \le 10^5$，$x < queries[i] \le 10^6$

## 2. 示例

**示例 1**

```text
输入：n = 3, logs = [[1,3],[2,6],[1,5]], x = 5, queries = [10,11]
输出：[1,2]
解释：q=10 窗口 [5,10]：服务器 1（t=5）、2（t=6）有请求 → 只有 3 号空闲；
      q=11 窗口 [6,11]：只有服务器 2（t=6）有请求 → 1、3 号空闲。
```

**示例 2**

```text
输入：n = 3, logs = [[2,4],[2,1],[1,2],[3,1]], x = 2, queries = [3,4]
输出：[0,1]
解释：q=3 窗口 [1,3]：三台服务器都有请求 → 0 台空闲；
      q=4 窗口 [2,4]：服务器 3 在窗口内无请求 → 1 台空闲。
```

## 3. 解题思路

### 3.1 暴力思路

对每个查询独立处理：扫一遍全部日志，把窗口内的 `server_id` 收进哈希集合，答案为 $n - |\text{集合}|$。单次 $O(L)$，总计 $O(Q \cdot L) = 10^{10}$，必然超时。问题出在**同一个窗口被反复扫描**：查询之间其实高度相关——窗口大小固定为 $x$，随着 $q$ 增大，窗口两端同时右移，日志只有「进入窗口」和「离开窗口」两种状态变化。

### 3.2 核心观察：窗口随查询单调滑动，离线 + 双指针

![核心观察：查询按右端点排序后，窗口两端单调右移](images/bw107_q4_window_slide.svg)

把查询**离线**，按 $q$ 升序处理，则每个查询的窗口 $[\,q - x,\ q\,]$ 的**左右端点都单调不减**——这正是滑动窗口适用的形状。把日志按 `time` 排序后用双指针维护「当前窗口内的日志段」：

- `right` 指针：把 `time ≤ q` 的日志依次纳入窗口；
- `left` 指针：把 `time < q - x` 的日志依次弹出窗口。

每条日志一生只进出窗口各一次，总代价 $O(L)$。窗口内**出现过多少台不同的服务器**用计数数组增量维护：`cnt[s]` 为服务器 $s$ 在窗口内的日志条数，`cnt[s]` 从 0 变 1 时「活跃服务器数」`active` 加一，从 1 变 0 时减一。答案即 $n - \text{active}$。计数用**条数**而非布尔值，才能正确处理「同一服务器多条日志先后离开窗口」的情形。

### 3.3 算法流程

![算法流程：排序 → 双指针滑窗 → 增量维护活跃服务器数](images/bw107_q4_two_pointer_flow.svg)

```text
1. idx = queries 的下标按 queries[i] 升序排列；logs 按 time 升序排序
2. cnt[1..n] 清零，left = right = active = 0
3. 按升序处理每个查询 qi（窗口 [q−x, q]）：
        while right < L 且 logs[right].time ≤ q：   # 纳入
            s = logs[right].id；cnt[s] 0→1 则 active++；cnt[s]++；right++
        while left < right 且 logs[left].time < q−x： # 弹出
            s = logs[left].id；cnt[s]--，1→0 则 active--；left++
        ans[qi] = n − active                        # 回填到原下标
4. 返回 ans
```

### 3.4 示例演算

![示例演算：两组官方样例的窗口移动与活跃计数](images/bw107_q4_example_walkthrough.svg)

**示例 1**（日志按时间排序为 $(1,3),(1,5),(2,6)$）：

| 查询 | 窗口 | 纳入（`right`→） | 弹出（`left`→） | 窗口内日志 | `active` | 答案 |
|------|------|------|------|------|------|------|
| $q=10$ | $[5,10]$ | $(1,5),(2,6)$ | $(1,3)$（$3<5$） | $(1,5),(2,6)$ | 2（1、2 号） | $3-2=1$ |
| $q=11$ | $[6,11]$ | 无 | $(1,5)$（$5<6$） | $(2,6)$ | 1（2 号） | $3-1=2$ |

**示例 2**（日志按时间排序为 $(2,1),(3,1),(1,2),(2,4)$，$x=2$）：

| 查询 | 窗口 | 纳入 | 弹出 | `active` | 答案 |
|------|------|------|------|------|------|
| $q=3$ | $[1,3]$ | $(2,1),(3,1),(1,2)$ | 无 | 3 | $0$ |
| $q=4$ | $[2,4]$ | $(2,4)$ | $(2,1),(3,1)$（$<2$） | 2（1、2 号） | $1$ |

注意 $q=4$ 时服务器 2 的两条日志一进一出，`cnt[2]` 从 2 降到 1，`active` 不变——这正是「计数条数」而非「布尔标记」的必要性。

## 4. 算法细节

1. **离线回填原下标**：查询排序打乱了输出顺序，必须先记录 `idx`（按值排序的原始下标序列），答案写回 `ans[原下标]`，最后按原顺序返回。
2. **闭区间边界**：纳入条件是 $t \le q$（右端闭合），弹出条件是 $t < q - x$（左端闭合，$t = q-x$ 的日志保留在窗口内）。边界差一个等号就整组答案错位。
3. **`cnt` 用数组不用哈希**：`server_id` 连续且 $\le n$，`vector<int> cnt(n+1)` 的读写远快于哈希表；$n$ 至多 $10^5$，开一个即可。
4. **`active` 的增减时机**：只在 `cnt` 跨过 0/1 边界时增减——即「首次纳入」与「最后一条离开」，而不是每条日志都调整。
5. **排序的稳定性无关紧要**：日志只按 `time` 排，`time` 相同的次序任意——窗口判定完全基于时间值，与先后无关。
6. **`left` 不越过 `right`**：弹出循环带 `left < right` 保护，防止空窗口时下标越界（逻辑上 $lo$ 增大时必然先清空再等新日志纳入，指针不会交叉）。
7. **另一种可行思路**（差分/树状数组版）：按查询右端点离线，`right` 指针推进时维护 $last[s]$ = 服务器 $s$ 最近一次请求时间（值域 $\le 10^6$，用树状数组按时间值计数），回答查询时统计 $last[s] \ge q - x$ 的服务器数。与滑窗等价，但多一个 $O(\log T)$；滑窗胜在实现短、完全线性。

## 5. 正确性证明

**引理 1（窗口单调性）**：按 $q$ 升序处理查询时，窗口左端点 $lo = q - x$ 与右端点 $hi = q$ 都单调不减。

**证明**：$q_i < q_j \Rightarrow q_i - x < q_j - x$ 且 $q_i < q_j$，两端点逐查询比较即得。∎

**定理（双指针不变量）**：回答第 $i$ 个查询（按升序）时，`[left, right)` 恰为**全部**满足 $lo \le t \le hi$ 的日志（按排序后的下标连续成段），`cnt[s]` 为其中服务器 $s$ 的条数，`active` 为 $\#\{s : cnt[s] > 0\}$，从而 `ans = n − active` 正确。

**证明**：对处理的查询个数归纳。基础：第一个查询前 `left = right = 0`，窗口空，`cnt` 全零，`active = 0`，不变量成立。归纳步：设处理查询 $i$ 前不变量成立，且由引理 1，本次 $lo, hi$ 均不小于上一查询。**纳入循环**：反复把 `time ≤ hi` 的日志加入——日志按 `time` 升序，循环终止时 `right` 指向第一条 `time > hi` 的日志（或末尾），故 $t \le hi$ 的日志已全部进入 `[left, right)`；`cnt` 与 `active` 的更新与条数定义逐条一致。**弹出循环**：反复弹出 `time < lo` 的日志——因队列按时间有序且这些日志自上一查询以来一直在 `[left, right)` 内（它们满足旧的 $t \le hi_{\text{旧}} \le hi$，且旧的 $t \ge lo_{\text{旧}}$……若 $t < lo_{\text{旧}}$ 早已在归纳前提中被弹出），循环终止时 `[left, right)` 中第一条日志 `time ≥ lo`，最后一条 `time ≤ hi`，且由有序性与两指针的单调推进，段内恰为 $\{t : lo \le t \le hi\}$ 的全部日志。`active` 的增减发生在 `cnt` 穿越零点时，与「窗口内是否出现过该服务器」严格同步。故 `active` = 窗口内有请求的不同服务器数，空闲数 $= n - \text{active}$。回填到原下标后归纳完成。∎

## 6. 复杂度分析

- **时间**：$O(L \log L + Q \log Q + L + Q)$。两个排序主导；双指针阶段 `right`、`left` 各自单调前进至多 $L$ 步，每查询 $O(1)$ 摊还之外的收尾工作也是常数。
- **空间**：$O(n + Q)$。`cnt` 数组 $O(n)$，查询下标与答案数组 $O(Q)$；日志排序若原地则不需额外空间（C++ `sort`），Python `sorted` 需 $O(L)$。

## 7. 参考代码

### C++

```cpp
class Solution {
public:
    vector<int> countServers(int n, vector<vector<int>>& logs, int x, vector<int>& queries) {
        int L = logs.size(), Q = queries.size();
        vector<int> idx(Q);
        iota(idx.begin(), idx.end(), 0);
        sort(idx.begin(), idx.end(), [&](int i, int j) { return queries[i] < queries[j]; });
        sort(logs.begin(), logs.end(), [](const vector<int>& a, const vector<int>& b) {
            return a[1] < b[1];
        });
        vector<int> cnt(n + 1, 0);
        vector<int> ans(Q);
        int left = 0, right = 0, active = 0;   // [left, right) 是窗口内日志
        for (int qi : idx) {
            int lo = queries[qi] - x, hi = queries[qi];
            while (right < L && logs[right][1] <= hi) {      // 纳入 t ≤ hi
                if (cnt[logs[right][0]]++ == 0) ++active;
                ++right;
            }
            while (left < right && logs[left][1] < lo) {      // 弹出 t < lo
                if (--cnt[logs[left][0]] == 0) --active;
                ++left;
            }
            ans[qi] = n - active;
        }
        return ans;
    }
};
```

### Python

```python
class Solution:
    def countServers(self, n: int, logs: list[list[int]], x: int, queries: list[int]) -> list[int]:
        order = sorted(range(len(queries)), key=lambda i: queries[i])
        logs = sorted(logs, key=lambda t: t[1])
        cnt = [0] * (n + 1)
        ans = [0] * len(queries)
        left = right = active = 0                # [left, right) 是窗口内日志
        for qi in order:
            lo, hi = queries[qi] - x, queries[qi]
            while right < len(logs) and logs[right][1] <= hi:   # 纳入 t ≤ hi
                s = logs[right][0]
                if cnt[s] == 0:
                    active += 1
                cnt[s] += 1
                right += 1
            while left < right and logs[left][1] < lo:         # 弹出 t < lo
                s = logs[left][0]
                cnt[s] -= 1
                if cnt[s] == 0:
                    active -= 1
                left += 1
            ans[qi] = n - active
        return ans
```

> 💡 两份代码均通过官方示例（`[1,2]`、`[0,1]`），并与「每查询独立扫全部日志收集哈希集合」的暴力对拍：C++ 侧 3000 组、Python 侧 800 组随机数据（含同一服务器多条日志、窗口边界相等时刻），`mismatch = 0`；另以 $n = L = Q = 10^5$ 做了压力测试，运行流畅。

## 8. 边界情况与易错点

1. **答案回填原下标**：排序处理查询后必须按原顺序输出，漏掉 `idx` 数组是本题最高频的翻车点。
2. **闭区间的两个等号**：纳入用 $t \le q$、弹出用 $t < q - x$；$t = q - x$ 的请求**算数**（收到过请求）。
3. **同一服务器多条日志**：`cnt` 必须计条数，`active` 只在 0/1 边界变化；用布尔标记会在「一条离开、另一条还在」时误减。
4. **窗口可能为空**：查询区间极偏时 `active = 0`，答案为 $n$，属正常输出而非特判。
5. **`x < queries[i]` 保证左端点 $\ge 1$**：无需处理 $lo \le 0$ 的情况（即便出现，算法逻辑也天然正确）。
6. **重复日志**：约束未禁止 `(id, time)` 重复，滑窗按条数计数不受影响；暴力对照时应同样允许。
7. **`n` 远大于日志数**：答案多为大数（接近 $n$），别把「窗口内日志条数」当答案——要去重后的服务器数。
