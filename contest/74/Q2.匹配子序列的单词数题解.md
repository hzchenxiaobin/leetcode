# LeetCode 匹配子序列的单词数 题解

## 1. 题目概述

- **标题 / 题号**：匹配子序列的单词数（#792，medium）
- **链接**：https://leetcode.cn/problems/number-of-matching-subsequences/
- **来源**：LeetCode 第 74 场周赛 Q2
- **难度**：中等
- **标签**：数组、哈希表、字符串、二分查找、Trie

**题意**：给定字符串 `s` 和字符串数组 `words`，统计 `words` 中有多少个单词是 `s` 的**子序列**（从 `s` 中删去若干字符、不改变其余字符相对顺序得到的新串）。一个单词可能有多种落位方式，但只计一次；`words` 中的重复单词各自独立计数。

**约束**：

- $1 \le \lvert s \rvert \le 5\times 10^4$
- $1 \le \lvert words \rvert \le 5000$
- $1 \le \lvert words[i] \rvert \le 50$
- `s` 与 `words[i]` 均只由小写英文字母组成

> 💡 关键规模：单词总长 $\sum_i \lvert words[i] \rvert \le 5000 \times 50 = 2.5\times 10^5$，而 $\lvert s \rvert$ 最大 $5\times 10^4$。若把每个单词都对着 `s` 从头扫一遍，上界是 $1.25\times 10^{10}$ 次比较——这就是本题必须跨过的坎。

## 2. 示例

**示例 1**

```text
输入：s = "abcde", words = ["a","bb","acd","ace"]
输出：3
解释：有三个单词是 s 的子序列："a"、"acd"、"ace"；"bb" 需要两个 b，而 s 只有一个。
```

**示例 2**

```text
输入：s = "dsahjpjauf", words = ["ahjpjau","ja","ahbwzgqnuk","tnmlanowax"]
输出：2
解释："ahjpjau" 与 "ja" 命中；另两个单词含有 s 中不存在的字符，无法匹配。
```

**补充示例**（用于检验边界）

```text
输入：s = "abcde", words = ["a","a","bc","bcc"]  →  3（重复的 "a" 各自计数，"bcc" 缺第二个 c）
输入：s = "aaaa", words = ["a","aa","aaa","aaaaa"]  →  3（"aaaaa" 超长）
```

## 3. 解题思路

### 3.1 暴力思路

对每个单词用双指针在 `s` 上贪心扫描：`j` 指向 `s`、`k` 指向单词，字符相等则双双后移，`k` 走到单词末尾即命中。

- 时间 $O\big(\lvert s\rvert \cdot \sum_i \lvert words[i] \rvert\big)$，最坏 $1.25\times 10^{10}$，必定超时。
- 即使按单词长度排序、把短词先判掉，最坏情况（单词都很长、且在 `s` 末尾才失败）仍是同样的上界。
- 浪费的根源：每个单词都**重新扫描 `s` 的前缀**，而这 5000 次扫描看到的字符序列完全一样。

所以优化方向不是「更快地判断单个单词」，而是**让所有单词共用同一次对 `s` 的扫描**。

### 3.2 核心观察：按「下一个待匹配字符」分桶

![按下一个待匹配字符分桶，一次扫描反哺所有单词](images/wc74_q2_bucket_model.svg)

一个未完成的单词，此刻真正需要的只有两样东西：**已经匹配到哪**（记为 `p`）和**下一个要匹配哪个字符**（即 `words[i][p]`）。于是把单词按「下一个待匹配字符」分进 26 个桶：

- 扫描 `s` 遇到字符 `c` 时，**只有 `bucket[c]` 里的单词能取得进展**，其余 25 个桶纹丝不动。
- 每条进度原地前进一格；若走完整个单词就命中计数，否则按新的 `words[i][p]` 重新入桶。
- 桶里只存 `(单词下标, 已匹配长度)` 这样的短记录，**不复制字符串**。

于是总推进次数从 $\lvert s\rvert \cdot \sum\lvert words[i]\rvert$ 降到 $\sum\lvert words[i]\rvert$：每个字符最多被消费一次。

> 💡 桶本质上是「所有单词的待办清单」：一个单词没做完就一直挂在某个桶里，不需要任何额外的失败判定或清理逻辑。

### 3.3 算法流程

![扫描 s、弹出当前桶、推进并重新入桶的循环](images/wc74_q2_scan_flow.svg)

1. 初始化 26 个空桶，把记录 `(i, 0)` 放进 `words[i][0]` 对应的桶。
2. 依次取出 `s` 的每个字符 `c`：
   - 令 `cur = bucket[c]`，同时把 `bucket[c]` 置为空列表（**先取出、再清空**）。
   - 对 `cur` 中每条 `(i, p)`：令 `p ← p + 1`；若 `p == len(words[i])` 则 `ans++`，否则把 `(i, p)` 放进 `words[i][p]` 对应的桶。
3. `s` 扫描结束后返回 `ans`。

注意第 2 步的「先取出再清空」不是风格问题：若某单词推进后的下一个字符**仍然是 `c`**（例如 `s = "aaaa"`、单词 `"aaab"`），这条记录必须等**下一次** `c` 出现才能再推进；边遍历边塞回同一个桶会让它在同一轮被重复弹出。

### 3.4 示例演算

![示例 1 的逐字符走查表](images/wc74_q2_walkthrough.svg)

以 `s = "abcde"`、`words = ["a", "bb", "acd", "ace"]` 为例：

| 步骤 | 读入字符 | 弹出的桶 | 推进与去向 | `ans` |
|------|----------|----------|------------|-------|
| 初始 | — | — | 桶 a：`a`、`acd`、`ace`；桶 b：`bb` | 0 |
| 1 | `'a'` | a | `a` 完成；`acd`→桶 c；`ace`→桶 c | 1 |
| 2 | `'b'` | b | `bb` 推进到 `p=1`，回到桶 b 等下一个 b | 1 |
| 3 | `'c'` | c | `acd`→桶 d；`ace`→桶 e | 1 |
| 4 | `'d'` | d | `acd` 完成 | 2 |
| 5 | `'e'` | e | `ace` 完成 | 3 |

`bb` 自始至终留在桶 b 里：它需要的第二个 `b` 永远不会到来，于是自然不被计数，也**不需要**任何显式的「失败清理」。

## 4. 算法细节

1. **记录只存 `(下标, 已匹配长度)`**：单词内容随时用 `words[id]` 取，避免每轮复制最长 50 字符的串。整个算法的移动成本只与「推进次数」有关。
2. **必须先取出、再清空当前桶**：Python 里写 `cur, bucket[c] = bucket[c], []`，C++ 里写 `std::move(bucket[c])` 后 `bucket[c].clear()`。反过来写（边遍历边 `push_back` 回 `bucket[c]`）在本轮就可能把新记录再次弹出，轻则重复推进、重则死循环。
3. **用 26 个数组桶而不是哈希表**：字符集固定为小写字母，`vector<vector<pair<int,int>>>` 的常数最小、无哈希开销；只有字符集未知时才退回 `unordered_map<char, vector<...>>`。
4. **完成条件用 `p == len(words[i])`**：题目保证 $\lvert words[i]\rvert \ge 1$，所以初始化时取 `words[i][0]` 不会越界；判定用「等于」而不是「大于等于」，因为指针每次只前进一格。
5. **命中即出桶**：完成的记录直接被计数、不再入桶，因此每个单词至多贡献 1 次 `ans`，重复单词也不会串味。
6. **重复单词可以不做特判**：总字符数只有 $2.5\times 10^5$，直接逐条跑即可；若想进一步压常数，可先用哈希表统计频次，对唯一单词跑一遍再乘权重。
7. **大输入下的容器操作**：单轮弹出的记录数最多可达 5000 条，用移动语义/引用交换（而不是整体拷贝）避免把 $O(m)$ 的拷贝放大成 $O(m\lvert s\rvert)$。

**等价视角：预处理「下一个出现位置」**。预处理 $nxt[t][c]$ 表示 `s` 中下标 $\ge t$ 的最小位置 $j$ 使 $s[j]=c$（不存在记为 $n$）。每个单词从 $t=0$ 出发，对它的每个字符 $c$ 执行 $t = nxt[t][c] + 1$；只要某一步查到 $nxt[t][c] = n$，说明该字符在 $s[t..]$ 中已不存在，判定失败。

![next 表：每一步跳到该字符的最早出现位置](images/wc74_q2_next_pos_table.svg)

预处理 $O(26\lvert s\rvert)$、单次查询 $O(\lvert w\rvert)$，总复杂度与分桶同阶，但要额外占用 $26\lvert s\rvert$ 个整数（约 5 MB），常数也更大。分桶法胜在**不需要预处理、边扫边算**。

## 5. 正确性证明

**引理 1（贪心匹配最优）**：设 $w$ 的字符依次落在 $s$ 的下标 $j_0 < j_1 < \dots < j_{k-1}$。若贪心匹配（每个字符取当前位置之后第一个相同字符）得到位置 $g_0 < g_1 < \dots < g_{k-1}$，则对每个 $t$ 有 $g_t \le j_t$。特别地，贪心成功当且仅当 $w$ 是 $s$ 的子序列。

**证明**：对 $t$ 归纳。$t=0$ 时 $g_0$ 是 $s$ 中第一个 $w_0$，而 $j_0$ 也是 $w_0$ 的一个位置，故 $g_0 \le j_0$。设 $g_{t-1} \le j_{t-1} < j_t$，则 $j_t$ 是下标 $\ge g_{t-1}$ 处的一个 $w_t$，贪心取的是其中最小的，故 $g_t \le j_t$。因此贪心永远不会比任何合法匹配「更晚」卡住；若贪心在某字符失败，说明不存在任何合法匹配。∎

**引理 2（分桶不变式）**：扫描完 `s` 的前 $t$ 个字符后，每个**未完成**单词在桶中恰好出现一次，形如 $(i, p_i)$ 且位于字符 $words[i][p_i]$ 的桶中，其中 $p_i$ 等于「只用 $s[0..t-1]$ 做贪心匹配时 $words[i]$ 已确定的前缀长度」，且 $0 \le p_i < \lvert words[i]\rvert$。

**证明**：对 $t$ 归纳。$t=0$ 时所有 $p_i = 0$，记录位于各自首字符桶，成立。设状态满足不变式，读入 $c = s[t]$，记 $U$ 为位于字符 $c$ 桶中的记录集合。对 $(i,p) \in U$，由不变式 $words[i][p] = c$，贪心可用 $s[t]$ 把前缀长度推进到 $p+1$；若 $p+1 = \lvert words[i]\rvert$ 则该词完成并计一次，否则它以字符 $words[i][p+1]$ 的身份进入对应桶。对不在 $c$ 桶的记录 $(i,p)$，有 $words[i][p] \ne c$，故 $s[t]$ 对它的贪心匹配无用，$p$ 不变、桶不变。两种情形都不产生副本、也不丢记录，故 $t+1$ 时不变式仍成立。∎

**引理 3（计数不重不漏）**：每个单词至多被计数一次，且当且仅当它完成时被计数；完成的单词不会再进入任何桶。

**证明**：由引理 2，任一时刻每个未完成单词恰有一条记录。记录只在 $p+1 = \lvert words[i]\rvert$ 时被计入 `ans` 并丢弃，丢弃后不存在其它副本，故不会被再次计数；全部字符扫描完毕仍留在桶中的单词从未被判完成。∎

**定理**：算法返回值等于 `words` 中是 `s` 子序列的单词个数。

**证明**：由引理 2，扫描完全部 $\lvert s\rvert$ 个字符后，单词 $i$ 完成的充要条件是：对 $s[0..\lvert s\rvert-1]$ 的贪心匹配走完了整个单词，由引理 1 这等价于 $words[i]$ 是 $s$ 的子序列。再由引理 3，每个这样的单词恰好被计入一次，反之不计入，故 `ans` 即所求。∎

## 6. 复杂度分析

- **时间**：$O\big(\lvert s\rvert + \sum_i \lvert words[i] \rvert\big)$。扫描 `s` 的每个字符只做一次桶引用与清空（$O(1)$ 均摊）；每条记录每被推进一次就消耗单词的一个字符，总推进次数不超过单词总长 $2.5\times 10^5$，而单轮弹桶的总条数也被这个总量约束。
- **空间**：额外空间 $O(\lvert words\rvert + 26)$。任一时刻每个未完成单词至多一条记录，加上 26 个桶，与 $\lvert s\rvert$ 无关（不计输入本身）。
- **对比**：暴力 $O(\lvert s\rvert\sum\lvert words[i]\rvert)$；`next` 表法时间同阶但额外空间 $O(26\lvert s\rvert)$；分桶法在时间与空间上都最省，且无需预处理。

## 7. 参考代码

### C++

```cpp
class Solution {
public:
    int numMatchingSubseq(string s, vector<string>& words) {
        // 桶里存 (单词下标, 已匹配长度)，按「下一个待匹配字符」分组
        vector<vector<pair<int, int>>> bucket(26);
        for (int i = 0; i < (int)words.size(); ++i)
            bucket[words[i][0] - 'a'].push_back({i, 0});

        int ans = 0;
        for (char ch : s) {
            int c = ch - 'a';
            vector<pair<int, int>> cur = std::move(bucket[c]);  // 先取出
            bucket[c].clear();                                  // 再清空
            for (auto& [id, p] : cur) {
                ++p;
                if (p == (int)words[id].size()) {
                    ++ans;                                      // 整个单词走完
                } else {
                    bucket[words[id][p] - 'a'].push_back({id, p});
                }
            }
        }
        return ans;
    }
};
```

### Python

```python
class Solution:
    def numMatchingSubseq(self, s: str, words: list[str]) -> int:
        bucket = [[] for _ in range(26)]
        for i, w in enumerate(words):
            bucket[ord(w[0]) - 97].append([i, 0])

        ans = 0
        for ch in s:
            c = ord(ch) - 97
            cur, bucket[c] = bucket[c], []      # 先取出，再清空
            for i, p in cur:
                p += 1
                w = words[i]
                if p == len(w):
                    ans += 1                    # 整个单词走完
                else:
                    bucket[ord(w[p]) - 97].append([i, p])
        return ans
```

## 8. 边界情况与易错点

1. **首字符不在 `s` 中**：单词永远挂在桶里、不会被计数。不要为了「清理」去扫描或丢弃桶内记录，后续还可能存在能推进的单词。
2. **单词比 `s` 长**：如 `s = "ab"`、单词 `"abc"`，前两个字符依次命中，第三个字符的记录进入桶 c 后再没有字符来推进它，自然挂起，最终不计数。
3. **同一字符需要多次**：`s = "abcde"`、单词 `"bb"`——第一次 `b` 用掉后记录回到桶 b 等待**下一次** `b`，本例中不会再来，故不计数。
4. **重复单词**：`s = "a"`、`words = ["a","a","a"]` 应返回 3。用 `(i, p)` 区分每条记录，不要用字符串集合去重（除非另行乘以频次）。
5. **下一字符仍是当前字符**：`s = "aaaa"`、单词 `"aaab"` 是「先取出再清空」的经典反例；若在同一轮里把记录塞回 `bucket[c]`，会重复消费当前字符，导致错误计数甚至死循环。
6. **长度为 1 的单词**：`p` 从 0 直接跳到 1 就完成，判定必须写 `p == len(w)`；写成 `p > len(w)` 或忘记自增都会漏计。
7. **全部命中**：`s` 全为 `'a'`、`words` 全为 `"a"` 时应返回 5000。注意 `ans` 只增不减，且桶操作的中间结果不要覆盖它。
8. **容器拷贝放大**：C++ 中 `auto cur = bucket[c];` 是深拷贝（每轮最多 5000 条），必须用 `std::move` 或 `swap`；Python 中整数与引用都便宜，但仍应写成元组赋值以避免不必要的列表复制。
